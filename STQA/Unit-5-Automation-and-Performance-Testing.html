5.1 Automation testing fundamentals

Syllabus: What is automation testing, automated testing process, automation frameworks, benefits, how to choose automation testing tools.

Q4Construct / explain / illustrate the different automated testing process (with neat diagram).

6 marks★★★★★ 5×

Asked in: 2022 Nov Q5(c) [6] · 2023 May Q6(b) [6] · 2023 Nov Q6(a) [6] · 2024 May Q6(b) [6] · 2025 Nov Q5(c) [6]

In simple words: Automation testing means a tool runs the test steps instead of a person.
The automated testing process is the plan a team follows to build those automated tests.
It starts by asking “can this app be automated at all?” and ends by running the scripts and studying the results.

Why we do this

A team can waste months on the wrong tool or the wrong test cases. This process forces the team to check feasibility, cost and fit before it writes hundreds of scripts. It also gives every project the same repeatable path, so results are easier to compare and improve.

Words you need first

  • Automation testing: using a software tool to run test steps and compare results instead of a human doing every step.
  • Feasibility analysis: a study that asks whether the application can be automated with reasonable effort.
  • Test tool: software that drives the application, feeds data and records pass or fail.
  • Framework: the rules and reusable code that decide how all test scripts are written and run.
  • Proof of concept (POC): a small end-to-end trial that proves the chosen tool can automate the key functions.
  • Test script: a set of instructions that tells the tool what to click, type and check.
  • Regression testing: re-running old tests to make sure a new change did not break old features.
  • Locator: the address a script uses to find a button, link or text box on a page.
  • Data-driven framework: a framework that reads test data from a file, so one script can run with many inputs.
  • Keyword-driven framework: a framework where words such as “login” or “click” in a table tell the tool what to do.

Step-by-step

  1. Check feasibility. Ask whether the application and its technology can be automated at all. Why: some screens, devices or legacy systems block automation, and no tool can fix that.
  2. Select the tool. Match the tool to the application’s technology, features and expected usage. Why: a tool that cannot recognise the app’s controls will fail on the first test.
  3. Evaluate the framework. Choose how scripts will be organised, for example data-driven or keyword-driven. Why: the framework decides how easy the suite will be to maintain.
  4. Build a proof of concept. Automate one full scenario, such as login plus checkout. Why: a small trial exposes tool gaps before the team commits the budget.
  5. Build the framework. Create the shared functions, test data files and reporting rules. Why: this is the foundation every later script will reuse.
  6. Develop, run and analyse scripts. Write scripts, execute them, study failures and log defects. Why: a script that runs is useless until someone checks whether the result is correct. The lessons feed the next cycle.

Detailed explanation

Definition: The automated testing process is the sequence of activities followed to decide whether an application can be automated, select the tool and framework, prove the concept, build the framework and then develop, execute and analyse the test scripts. 2. Steps in detail

  1. Test automation feasibility analysis: the first step is to check whether the application can be automated or not. Not all applications can be automated because of limitations.
  2. Appropriate tool selection: the next important step is the selection of equipment. It depends on the technology on which the application is built, its features and its usage.
  3. Evaluate the suitable framework: after choosing the tool, choose a suitable framework. There are different types of frameworks, and each framework has its own importance.
  4. Build the proof of concept (POC): the POC is developed in an end-to-end scenario to evaluate whether the device can support automation of the application. It ensures that the key functions can be automated.
  5. Develop automation framework: after the POC is built, framework development is done. This is a critical step for the success of any test automation project. The framework should be built after carefully analysing the technology used by the application and its key features.
  6. Develop test script, execute and analyze: once script development is complete, the scripts are executed, the results are analysed and any errors are logged. Test scripts are usually version controlled.

3. Example

A retail project first checks that its web screens can be automated, selects Selenium, evaluates a data-driven framework, and proves the concept on the login and checkout flows. It then builds the framework and develops regression scripts. The scripts run, results are analysed and broken locators are logged — and the cycle repeats on the next build.

What this means: The diagram is a cycle: feedback from step 6 sends the team back to step 1. Feasibility protects the budget, the POC protects the schedule, and the framework protects long-term maintenance.

Real-life analogy: A factory installs a robot arm. First it checks the robot can reach the workbench, then it picks the right arm, plans the routine, tests one part, builds the full line, and finally runs and inspects the output.
Common confusion: Many students start the answer with “select Selenium”. The book starts with feasibility. A proof of concept is also not the full framework — it is a small end-to-end trial that proves the tool can do the job.

Q3Identify / list and explain different benefits of Automation testing.

6 marks★★★★ 4×

Asked in: 2022 Nov Q6(b) [6] · 2023 May Q6(a) [6] · 2024 May Q5(b) [6] · 2025 Nov Q5(a) [6]

In simple words: Automation testing saves time, money and effort once the scripts exist.
It runs the same checks again and again without getting bored or tired.
It also finds defects earlier, covers more cases and gives faster feedback to the team.

Why we do this

Managers approve automation only when they can see the return. These benefits explain why the upfront cost is worth it. They also answer the exam question directly, so learn them as named points with one example each.

Words you need first

  • Return on investment (ROI): the value a team gets back compared with what it spent.
  • Regression suite: the collection of old tests that is re-run after every change.
  • Test coverage: the share of features, code or requirements that the tests actually check.
  • Defect: any result that does not match the requirement or the customer’s expectation.
  • Test data: the input values a test uses, such as usernames, prices or dates.
  • Stakeholder: anyone who cares about the product, such as a customer, manager or support team.
  • Time to market: how long it takes to release the product to customers.
  • Bottom line: the company’s profit after all costs.
  • Brand recall: how easily customers remember a brand when they need its product.
  • Post-release phase: the period after the product has gone live to users.

Step-by-step

  1. Group the benefits. Put them under time, quality and money. Why: a grouped answer is easier to remember and easier for the examiner to mark.
  2. Name the benefit. Use the book’s label, such as “swifter feedback” or “increase in coverage area”. Why: the label proves you know the source.
  3. Explain what changes. Say what the team can now do that it could not do by hand. Why: this shows understanding, not just memory.
  4. Give one example. For regression, say “500 login tests run in 20 minutes instead of two days”. Why: a number makes the benefit concrete.
  5. Add the balance line. State that automation has a high initial cost and does not remove manual testing. Why: it shows judgement and matches the book’s caution.

Detailed explanation

  1. Enhanced results: automation saves a lot of time even for complex and large systems. It allows repeatable testing and gives better, faster results with significantly less effort and less time.
  2. Swifter feedback system: automation is very critical in the validation phase. It increases communication between developers, designers and product marketers, gives room for immediate correction of possible defects, and raises the efficiency of the development team.
  3. Brand enhancement: automated tests reuse quality test data again and again, which saves cost from project management and maintenance. It adds value to all stakeholders, enhances system capability, improves the brand name and brand recall, and therefore increases customer retention.
  4. Cost-effective: the initial investment is high, but automation saves money in the long run because less time is needed to conduct tests. It also raises work quality, as there is no chance of negligence or human error, and reduces defect fixing in the post-release phase.
  5. Efficiency testing: automation can be left virtually unattended, leaving room to monitor results at the end of the process. This increases the overall efficiency of the application.
  6. Increase in coverage area: more tests can be allocated to the application, which leads to higher testing coverage and fewer defects. More features and complex applications can be tested; a manual scenario would need a large team and heavy time.
  7. Detailed testing: testers have different approaches and focus areas. Automation focuses equally on all areas of inspection, so the final product gets the best quality with emphasis on every aspect.
  8. Reusability: test automation is iterative in nature. Automated test cases are fully reusable and can test any aspect of the code depending on its importance and the approach used.
  9. Earlier detection of defects: the tool records defects, so the development and support teams can consider them together and give quick output. This speeds up the project; the earlier a fault is found, the cheaper and easier it is to fix and deploy.
  10. Time to market: automation reduces the time-to-market launch of an application. It gives consistent execution of test cases, and the test library runs much faster and longer after automation.

Balance line: the book also notes that automation demands a significant investment of money and resources, and its goal is to reduce manual test cases — not to remove manual testing.

What this means: Read the ten benefits as three promises: faster feedback, wider coverage and lower long-term cost. The upfront investment is real, so the benefit grows with every repeat run.

Real-life analogy: A restaurant buys an industrial dishwasher. It costs money on day one, but it washes hundreds of plates every night, never gets tired, and lets the staff serve customers instead of scrubbing.
Common confusion: Automation is not free or instant. The first version costs more than manual testing because someone must build the framework. The benefit comes from repeated runs, which is why automation is a poor fit for a test that will run only once.

Q1What is automation testing in software testing? Explain in brief. / Explain it with an example.

6 marks★★ 2×

Asked in: 2023 May Q5(a) [6] · 2024 May Q6(a) [6]

In simple words: Automation testing uses software to click, type and check the application for you.
A person still designs the tests and reads the results.
The tool handles the repetitive steps, so the team can test more in less time.

Why we do this

Repeating the same 200 checks by hand is slow and error-prone. A tool does it the same way every time and reports the result. This frees testers to explore new areas and to judge usability, which a tool cannot do well.

Words you need first

  • Test case: one set of steps, input data and an expected result.
  • Test suite: a group of test cases that are run together.
  • Test data: the values fed into the application, such as a username or a price.
  • Expected result: what the test says should happen.
  • Actual result: what really happened when the test ran.
  • System under test (SUT): the application or component being tested.
  • Script: the coded instructions that tell the tool what to do.
  • Smoke test: a quick check that the main functions work before deeper testing starts.
  • Pull request (PR): a proposed code change that teammates review before it is merged.

Step-by-step

  1. Pick a suitable test. Choose a stable, repeated, rule-based case such as a login or a payment calculation. Why: automation pays off only when the test runs many times.
  2. Write the script. Record or code the steps and the expected result. Why: the tool needs exact instructions, not general advice.
  3. Feed the test data. Read values from a file or a database. Why: one script can then check many input combinations.
  4. Run the script. Let the tool open the app and perform the steps. Why: this replaces the slow human clicks.
  5. Compare and report. The tool checks actual against expected and writes a report. Why: the team needs evidence of what passed and what failed.
  6. Review the failures. A human decides whether a failure is a real defect or a broken script. Why: automation reports differences; it does not judge them.

Detailed explanation

Definition: Automation testing is a software testing technique that uses specialized automated testing software tools to execute a test case suite. Manual testing, in contrast, is performed by a human sitting in front of a computer and carefully executing the test steps.

The automation software can feed test data to the test-under-test, compare expected and actual results and generate detailed test reports. Software test automation demands a significant investment of money and resources.

Goal: to reduce the number of test cases that have to be run manually — not to eliminate manual testing altogether.

1. What tests should be automated (§5.1.1)

Test typeWhy automate it
A. Regression testingRegression suites keep growing, and the same variables are filled in many times to make sure new features do not disturb old functions.
B. Complex functionalitiesTests that need complex calculations and are prone to human error.
C. Smoke testingQuickly checks the quality of key functions and shows whether a build needs more in-depth testing.
D. Data-driven testingThe same operation has to be validated repeatedly with multiple data sets.
E. Performance testingMonitors software performance under different conditions — very laborious and time-consuming by hand.
F. Functional testingEvery developer PR needs quick functional feedback; this is impossible without automation as the organisation grows.

What this means: The table draws the boundary: automate stable, repeated, rule-based and high-risk checks; keep exploratory and usability work with people. Automation complements manual testing instead of replacing it.

2. Example — login page with 100 records

A login page has to be checked with 100 username/password pairs. A Selenium script feeds each pair from an Excel file, enters the data, clicks Login and compares the actual page with the expected page. The tool generates the report: 97 pass, 3 fail, in a few minutes. The same work would take a tester hours and is prone to human error.

3. Conclusion

Automation suits stable, repetitive, rule-based and high-risk tests. Exploratory and usability tests still need a human. Automation complements manual testing; it does not replace it.

Real-life analogy: Automation is a robot that does repetitive clicks on a keyboard. You teach it the sequence once; it repeats the sequence all day without losing focus.
Common confusion: Automation does not mean “no human needed”. A person designs the test, writes the script and investigates failures. Automation also cannot judge whether a page “looks nice” or “feels confusing” — that still needs a human tester.

Q6How to choose an Automation tool / automation testing tools? Explain briefly.

6 marks★★ 2×

Asked in: 2023 Nov Q5(a) [6] · 2025 May Q6(b) [6]

In simple words: Choosing an automation tool is like buying a machine for a workshop.
First know the job, then compare the machines, then check whether the cost is worth it.
Finally, test the machine in your own workshop before you buy it.

Why we do this

The wrong tool can fail on the application’s technology, cost more than the testing saves, or lock the team into poor support. A structured selection process lowers that risk and gives management evidence for the purchase decision.

Words you need first

  • Test tool: software that helps plan, run, track or report tests.
  • Vendor: the company that sells or supports a commercial tool.
  • Open-source tool: a tool whose source code is free to use and change, usually with no licence fee.
  • Commercial tool: a paid tool sold with vendor support and extra features.
  • Custom tool: a tool built inside the organisation for a special need that existing tools cannot meet.
  • Pilot or trial: a short real use of the tool before the team buys it.
  • Cost-benefit analysis: a comparison of what the tool costs against the value it delivers.
  • Licence: the legal permission, often paid, to use a commercial tool.
  • Test manager: the person who plans the test effort, budget and tool choices.

Step-by-step

  1. Identify the requirement. Write down what the tool must do, which technologies it must support and which reports are needed. Why: you cannot compare tools without a clear target.
  2. Evaluate tools and vendors. List commercial and open-source options, then shortlist them. Check support, reputation and update frequency. Why: a cheap tool with no support can cost more in the long run.
  3. Estimate cost and benefit. Add licence, training, hardware and maintenance costs; compare them with the time saved. Why: a tool that costs more than the testing it replaces is a bad buy.
  4. Run a trial. Use the shortlisted tool on a real scenario in the actual environment, such as the login flow before buying 50 licences. Why: a demo can hide problems that appear with your own application.
  5. Make the final decision. Balance strong and weak points, then get agreement from the project team and management. Why: the team that uses the tool must be able to live with it.
  6. Review after use. Check whether the promised benefits appeared. Why: the next project can reuse the lesson.

Detailed explanation

Success in any test automation depends on identifying the right tool. Choosing the “right” testing tool for the project is the best way to achieve the project target. The book gives a four-step tool selection process (Fig. 5.5.1).

1. Tool selection process

StepWhat the Test Manager does
Step 1 — Identify the requirement for toolsYou cannot choose a tool if you do not know what you are looking for. Identify the test-tool requirements precisely and document them; the project team and management board review them.
Step 2 — Evaluate the tools and vendorsAnalyse commercial and open-source tools available in the market against the project requirement. Create a shortlist. Consider the vendor’s reputation, after-sales support and tool-update frequency. Judge quality by trial usage and a pilot; many vendors provide trial versions.
Step 3 — Estimate cost and benefitDo a cost-benefit analysis before acquiring or building a tool. Balance the cost against the value and benefit it brings to the team. If the cost is too high compared with the value, the balance may change the final decision (Fig. 5.5.2).
Step 4 — Make the final decisionHave a strong awareness of the tool — its strong and weak points. Balance cost and benefit, test the tool in the actual operating environment before buying a licence, and meet the project team and consultants for in-depth knowledge (Fig. 5.5.3).

What this means: The four steps move from “what do we need?” to “is it worth it?” to “prove it here”. Skipping the requirement step is the most common reason teams buy a tool they later abandon.

2. Types of test tools to consider (§5.5.2)

  • Open-source tools: the source code is openly published for use and/or modification, free of charge. They are available for almost every testing phase, from test-case management to defect tracking, but may have fewer features than commercial tools.
  • Commercial tools: software produced for sale or commercial purposes. They give more support and more features from a vendor.
  • Custom tools: when the testing environment or process has special characteristics and no open-source or commercial tool meets the requirement, the manager considers developing a custom tool.

Remember for 6 marks: identify requirement → evaluate tools and vendors → estimate cost and benefit → final decision, plus the three types of tools.

Real-life analogy: A delivery company buys a van. It lists the load and route, compares models, calculates fuel and maintenance against extra earnings, and takes a test drive before signing the order.
Common confusion: The most popular tool is not automatically the right tool, and “free” does not mean zero cost. Open-source tools still need training, setup and maintenance. A trial licence is also not the final purchase decision.

Q2Differentiate between Manual Testing and Automation Testing.

6 marks★ 1×

Asked in: 2024 May Q5(a) [6]

In simple words: Manual testing is a person clicking through the steps.
Automation testing is a tool clicking through the same steps.
Both are real testing; they are good at different jobs and work best together.

Why we do this

A team has limited time and money. Manual testing is flexible and good at judging user experience. Automation is fast and repeatable, but only for checks that can be written as clear rules. The comparison helps a manager choose the right mix.

Words you need first

  • Manual testing: a human executes the test steps and compares the results.
  • Automation testing: a tool executes the steps and compares the results.
  • Exploratory testing: learning about the product while testing, without a fixed script.
  • Usability testing: checking whether the product is easy and pleasant for a real user.
  • Regression testing: re-running old tests after a change to catch damage to old features.
  • Repeatability: getting the same result when the same test is run again.
  • Coverage: how much of the product or code the tests actually exercise.
  • Human error: a mistake caused by fatigue, distraction or a skipped step.
  • Test case: steps, data and an expected result for one check.
  • Test data: the input values used by a test.
  • Script: the coded steps a tool or person follows.

Step-by-step

  1. Define both terms. Start with one line for each. Why: the examiner needs a clear base before the comparison.
  2. Choose 8–10 points. Use who executes, test data, result checking, reports, cost, speed, repeatability, human error, coverage and best use. Why: too few points lose marks; too many waste time.
  3. Draw a two-column table. Put manual on the left and automation on the right. Why: matching rows make the difference obvious.
  4. Give one example per side. Manual: judge a confusing checkout screen. Automation: run 500 login cases overnight. Why: examples show the difference in practice.
  5. End with the balance. Say automation reduces manual work but does not remove manual testing. Why: this is the book’s conclusion and a common exam point.

Detailed explanation

Manual testing is performed by a human sitting in front of a computer and carefully executing the test steps. Automation testing is a software testing technique that uses specialized automated testing tools to execute a test case suite.

PointManual testingAutomation testing
Who executesA human tester, step by stepSpecialized testing tools and scripts
Test dataThe tester enters the data by handThe tool feeds test data to the test-under-test
Result checkingThe tester compares expected and actual resultsThe tool compares expected and actual results
ReportsPrepared manuallyDetailed test reports generated automatically
Initial investmentLowSignificant investment of money and resources
SpeedSlow; one step at a timeSaves a lot of time even for complex and large systems
RepeatabilityEach run may vary with tester attentionAllows repeatable testing with less effort and less time

What this means: The table is a set of trade-offs, not a scorecard. Automation wins on speed and repeatability; manual wins on judgement and flexibility. The best project uses each where it is stronger.

Goal of automation: the book states clearly that automation is meant to reduce the number of test cases run manually, not to eliminate manual testing altogether. The two are complementary.

Real-life analogy: Walking and driving both get you to a place. Walking reaches narrow lanes and lets you notice details; a car is faster on long highways. A sensible traveller uses both.
Common confusion: Automation will not replace all manual testers. Someone must design the tests, maintain the scripts and judge unclear results. Manual testing is also not “random clicking” — it follows a plan and written cases.

Q5Explain different manual testing process.

6 marks★ 1×

Asked in: 2025 Nov Q6(a) [6]

In simple words: The manual testing process is the route a tester follows from reading the requirements to closing the tests.
It covers planning, writing cases, setting up the environment, running tests, logging defects and retesting fixes.
Each step produces a document the next step needs.

Why we do this

Without a process, testing becomes random clicking. Important areas get missed, defects are not tracked, and nobody can say whether the product is ready. A defined process makes the work visible, repeatable and auditable.

Words you need first

  • Software requirements specification (SRS): the document that states what the software must do.
  • Test plan: the document that sets scope, schedule, approach, environment and risks.
  • Test case: steps, test data and an expected result for one check.
  • Test environment: the hardware, software, network and accounts used for testing.
  • Defect report: a record of what went wrong, with steps to reproduce it.
  • Severity: how much damage the defect causes.
  • Priority: how urgently the defect should be fixed.
  • Retest: running the same test after a fix to confirm the defect is gone.
  • Regression test: re-running related tests to confirm the fix broke nothing else.
  • Entry and exit criteria: the conditions for starting and finishing a test phase.
  • Black-box testing: testing the behaviour without looking at the code.
  • White-box testing: testing with knowledge of the code and its internal paths.

Step-by-step

  1. Study the requirements. List what can be tested and note anything unclear. Why: a test can only be correct if the expected behaviour is known.
  2. Plan the testing. Set scope, effort, schedule, environment, risks and exit criteria. Why: the team needs to agree on what “done” means.
  3. Design test cases and data. Write steps and expected results, using black-box and white-box techniques. Why: good cases catch defects that random clicking misses.
  4. Set up the environment. Install the build and prepare browsers, devices, accounts and data. Why: a bad environment produces false failures.
  5. Execute the tests. Follow each step and record the actual result. Why: evidence is needed before a defect can be raised.
  6. Compare and log defects. Match actual against expected, then record severity, priority and steps. Why: developers need a reproducible report, not a vague complaint.
  7. Retest and run regression. Check the fix and re-run affected tests. Why: fixes often create new defects elsewhere.
  8. Close the phase. Summarise coverage, open defects and lessons learned. Why: the next project can avoid the same gaps.

Detailed explanation

Manual testing is testing in which a human sits in front of a computer and carefully executes the test steps. The book defines it in §5.1 and treats automation as its helper — automation reduces the number of cases run manually, but does not eliminate manual testing. In simple words: RPA is a software clerk that copies data between applications by following fixed rules.
It logs in, reads a form, types the values into another system and logs out.
The “robot” is virtual software, not a machine on a factory floor.

Why we do this

Staff spend hours moving the same data from email to spreadsheets to accounting systems. RPA does that boring, rule-based work faster and without fatigue. It also creates an audit trail, which matters for compliance. RPA is not testing — it performs the work, while test automation checks the work.

Words you need first

  • RPA (Robotic Process Automation): software bots that perform repetitive, rule-based computer tasks.
  • Bot: a program that performs a set of steps automatically.
  • Rule-based: the task follows clear if-then rules, with little or no judgement.
  • Attended bot: a bot that runs with a person watching or triggering it.
  • Unattended bot: a bot that runs on a schedule without a person present.
  • Probot: a simple bot that follows repeatable rules to process data.
  • Knowbot: a bot that searches for information and returns it to the user.
  • Chatbot: a bot that replies to customer questions in real time.
  • Audit trail: a recorded history of who did what and when.
  • Compliance: following the rules and regulations that apply to the business.

Step-by-step

  1. Observe the process. Watch a person do the task and write down every step. Why: the bot can only copy a process that is understood.
  2. Check that it is rule-based. Confirm the steps do not need human judgement. Why: RPA is poor at exceptions and ambiguous cases.
  3. Write the bot’s rules. Define what to open, what to read, where to paste and when to stop. Why: the bot needs exact instructions for every branch.
  4. Connect the applications. Give the bot the right accounts and permissions. Why: it must log in like a user, but only to approved systems.
  5. Test on sample data. Run the bot on a small batch and compare results with the manual work. Why: a wrong rule can copy thousands of wrong values.
  6. Run and monitor. Schedule the bot and review its audit log. Why: a changed screen or rule can break the bot silently.
  7. Handle exceptions. Send unusual cases to a person. Why: some invoices or forms will never fit the standard rule.

Detailed explanation

Definition: RPA stands for Robotic Process Automation. It is the technology used for software tools that automate manual, rule-based or repetitive human tasks. Typically it is like a bot that does that kind of work at a much higher rate than a human.

1. What RPA bots do

  • RPA software bots never sleep and do not make mistakes.
  • They interact with in-house applications, websites and user portals.
  • They can log into applications, enter data, open emails and attachments, calculate and complete tasks, and then log out.
  • The “robot” in RPA is not a physical robot; it is a virtual system that automates repetitive manual computing or business process tasks.

2. Meaning of the three words (Fig. 5.8.1)

RoboticAn entity which has the capability to mimic human actions.
ProcessA sequence of steps that lead to a meaningful activity or task.
AutomationTasks that happen automatically, without human interaction.

What this means: The three-word table is the easiest memory hook: robotic = mimics a person, process = a sequence of steps, automation = runs without a human. If any of the three is missing, it is not really RPA.

3. RPA technologies (§5.8.2.1)

  1. Probots: bots that follow simple, repeatable rules to process data.
  2. Knowbots: bots that search user-specified information from the internet and respond to the user.
  3. Chatbots: bots that act and respond as virtual agents; they reply to customer queries in real time.

4. Benefits of RPA (§5.8.2.2)

  • Cost savings: RPA is cheaper than hiring an employee to do the same set of tasks.
  • Less error: it works on standard logic and is not bored, distracted or exhausted, so errors, rework and reputation risk are reduced.
  • Faster processing: it needs no breaks, meals or rest, so processing times are predictable and consistent.
  • Better regulatory compliance: it does only what is required by the given instructions, so the chance of non-compliance is minimal.
  • Better customer service: it frees employees to spend time on customer-related services and raises productivity.
  • Auditable and secure: bots access only authorised data and create a detailed audit trail of all activity.

5. Example

A bot logs into the invoice system, reads invoices from email attachments, enters the vendor, amount and PO number, calculates the total, completes the task and logs out. It runs the same rule-based process every day at a much higher rate than a human, and the audit trail records every action.

Real-life analogy: A junior clerk sits between the email inbox and the accounting system. Every morning they open each invoice email, copy the vendor and amount into the accounts software, and file a receipt. RPA is a software version of that clerk.
Common confusion: RPA is not test automation. RPA does the work; test automation checks the work. The “robot” is also not a physical machine, and RPA is not the same as artificial intelligence — a basic bot follows fixed rules and cannot learn on its own.

Q13What is Performance testing? Explain the uses of it as well.

6 marks★★★ 3×

Asked in: 2024 May Q5(c) [6] · 2025 May Q5(a) [6] · 2025 Nov Q5(b) [6]

In simple words: Performance testing checks how an application behaves when many people use it at once.
It looks at speed, stability, resource use and the maximum load the system can take.
It is like checking how a shop behaves during a festival rush, not on a quiet Tuesday.

Why we do this

An application can pass every functional test and still fail on launch day because 10,000 users arrive together. Performance testing finds the slow query, the memory leak or the server limit before customers do. It also gives the team evidence for capacity planning.

Words you need first

  • Performance testing: testing speed, response time, stability, scalability and resource use under a workload.
  • Load testing: testing the system at the expected number of users.
  • Stress testing: pushing beyond normal capacity to find the breaking point.
  • Endurance testing: running the expected load for a long time to find leaks or slowdowns.
  • Spike testing: suddenly raising the load to see how the system reacts.
  • Volume testing: testing with a very large amount of data in the database.
  • Scalability: the ability to handle more users by adding resources.
  • Bottleneck: the one part of the system that limits overall speed.
  • Response time: how long the system takes to answer one request.
  • Throughput: how many requests the system completes in a given time.
  • Resource utilization: how much CPU, memory, disk and network the system uses.
  • Workload: the amount and mix of work the system is asked to handle.

Step-by-step

  1. Define the goal. Write the expected users, response-time target and acceptable error rate. Why: without a target, any result looks acceptable.
  2. Prepare a realistic environment. Match production hardware, network and data size as closely as possible. Why: a tiny test server gives misleading results.
  3. Design the workload. Decide which user journeys to simulate and in what proportion. Why: real traffic is a mix, not one repeated request.
  4. Run the load. Start with a small load and increase it in steps. Why: a gradual rise shows where performance starts to fall.
  5. Monitor the system. Watch response time, errors, CPU, memory and database waits. Why: the slowest component explains the user’s experience.
  6. Analyse and tune. Fix the bottleneck, such as an index or a cache, then run the same test again. Why: a change must be measured, not assumed.
  7. Report and plan capacity. Record the safe load and the point where the system fails. Why: operations needs to know when to add servers.

Detailed explanation

Definition: Performance testing is a software testing process used to test a software application’s speed, response time, stability, reliability, scalability and resource utilization under specific workloads.

Main purpose: to identify and eliminate performance bottlenecks in the application. It is a subset of performance engineering and is also known as “perf testing”.

1. Focus of performance testing

  • Speed: determines whether the application responds quickly.
  • Scalability: determines the maximum user load the application can handle.
  • Stability: determines whether the application is stable under varying loads.

2. Types of performance testing (§5.9.1)

TypeWhat it checks
Load testingThe application’s ability to perform under anticipated user loads. The objective is to find performance bottlenecks before the application goes live.
Stress testingThe application under extreme workloads, to see how it handles high traffic or data processing and to identify its breaking point.
Endurance testingWhether the software can handle the expected load over a long period of time.
Spike testingThe software’s reaction to sudden large spikes in the load generated by users.
Volume testingBehaviour when a large amount of data is populated in the database; performance under varying database volumes.
Scalability testingThe application’s effectiveness in “scaling up” to support an increase in user load; helps plan capacity addition.

What this means: The table is a family of load shapes: expected, extreme, long, sudden and data-heavy. Each shape answers a different question, so a complete performance answer names the type and the risk it tests.

3. Uses of performance testing

  1. Find and remove bottlenecks before they reach production.
  2. Show that the system meets pre-defined performance criteria.
  3. Compare the performance of two software systems.
  4. Identify the parts of the system that degrade performance.
  5. Plan capacity — scalability testing shows how much load can be supported and when capacity must be added.
  6. Check readiness before go-live — load testing finds bottlenecks before the application is released.
  7. Check stability and reliability under sustained and varying loads (endurance, stress and spike testing).

4. Example

An online exam portal expects 10,000 students at 10:00 AM. A load test applies the anticipated load, then a stress test pushes beyond it to find the breaking point. The team watches response time, stability and resource utilization, removes the bottleneck, and retests before the exam.

Real-life analogy: A shop prepares for a festival. Load testing is the normal festival crowd, stress testing is letting in far more people than the shop can hold, spike testing is a flash sale that empties the door in seconds, and endurance testing is keeping the shop busy all day.
Common confusion: Performance testing is not functional testing. A function can work correctly and still be too slow. Load and stress are also different: load checks the expected peak, while stress goes beyond the peak until something breaks.

Q14Describe Apache JMeter based on: (i) Aim/Purpose (ii) Working (iii) Advantages.

6 marks★ 1×

Asked in: 2024 May Q6(c) [6]

In simple words: Apache JMeter is a free Java tool that sends many fake users to a server.
It records how fast the server answers, how many requests fail and how the system behaves under load.
Teams use it to test websites, databases and mail servers without hiring thousands of real users.

Why we do this

A team cannot invite 5,000 people to test a new site before launch. JMeter simulates those users and produces measurements. It is open source, runs on Windows, Mac and Linux, and supports many protocols, which makes it a practical first performance tool.

Words you need first

  • JMeter: an open-source Java tool for load and performance testing.
  • Thread group: the part of a JMeter test that defines the number of virtual users and how they start.
  • Sampler: one request that JMeter sends, such as an HTTP GET or a JDBC query.
  • Listener: the component that collects and displays results, such as a summary report.
  • Virtual user: a simulated user that sends requests.
  • GUI: a graphical user interface with windows, buttons and forms.
  • Protocol: the rules two systems use to exchange data, such as HTTP or JDBC.
  • JVM (Java Virtual Machine): the runtime that lets Java programs run on different operating systems.
  • Throughput: the number of requests completed per unit of time.
  • Distributed testing: running the load from several machines at once.
  • Ramp-up: the time over which virtual users are started.
  • HTTP and JDBC: protocols for web requests and database queries.
  • Assertion: a check that a response contains the expected result.

Step-by-step

  1. Plan the scenario. Decide which pages or services users hit and in what order. Why: the test must resemble real traffic.
  2. Add a thread group. Set the number of virtual users, the ramp-up time and the loop count; for example, 500 users for 10 minutes. Why: this controls how much load is applied and how quickly.
  3. Add samplers. Create the HTTP, JDBC or other requests. Why: each sampler is one action a virtual user performs.
  4. Add assertions. Check that the response contains the expected text or status. Why: a fast response is useless if it is an error page.
  5. Add listeners. Choose summary or aggregate reports. Why: the listener turns raw results into response time and error rate.
  6. Run and watch. Start with a small load, then increase it. Why: a sudden huge load can crash the test machine before it tests the server.
  7. Analyse and retest. Find the bottleneck, fix it and run the same plan again. Why: only a repeat run shows whether the fix helped.

Detailed explanation

The book answers this question in three parts: aim, working and advantages.

(i) Aim / purpose

Apache JMeter is used to test the performance of static and dynamic resources and dynamic web applications. It is completely designed in Java and is used to load functional test behaviour and measure application performance. It is an open-source tool, so users and developers can use the source code for the development of other applications.

It can test the strength of a large load on a server, object or network and a group of servers, or explore the full performance under multiple load types. Earlier it tested web applications; now it has been extended to other test functions. The book also lists JMeter as one of the leading tools for load testing of web and application servers.

(ii) Working

JMeter follows the general performance-testing process of §5.10:

  1. Identify the test environment: know the hardware, software and network configuration, and the tools available.
  2. Identify acceptance criteria: set goals and constraints for throughput, response time and resource allocation.
  3. Plan and design the test: identify key scenarios for all use cases, simulate a variety of end users, plan test data, and decide which metrics to gather.
  4. Configure the environment and implement the test design: prepare the environment and create the performance tests.
  5. Run the tests: execute and monitor them.
  6. Analyse, tune and retest: consolidate and share the results, fine-tune the system and test again. Improvements become smaller with each retest; stop when the bottleneck is the CPU, then consider increasing CPU power.

JMeter itself provides a user-friendly interactive GUI, supports functional, distributed and load testing, and can apply load to database servers (LDAP, JMS, JDBC), web servers (SOAP, HTTPS, HTTP) and mail servers (POP3).

(iii) Advantages

  • User-friendly GUI: interactive and simple to use.
  • Multiple testing approaches: functional, distributed and load testing.
  • Wide protocol support: database, web and mail servers as listed above.
  • Incredibly scalable: can apply load to multiple types of servers.
  • Platform-independent: designed in Java, so it runs on any platform that accepts the JVM — Windows, Mac and Linux.
  • Open source: no licence cost, and the source code is available for further development.
  • Large-load testing: can test the strength of a large load on a server, object or network and a group of servers.

What this means: JMeter has three building blocks: virtual users (thread group), requests (samplers) and reports (listeners). Once you can name those three, the working section becomes easy to remember.

Real-life analogy: JMeter is a traffic simulator. Instead of closing a road and waiting for thousands of real cars, it sends a controlled stream of virtual cars and measures where the traffic jams form.
Common confusion: JMeter is not a browser. Its normal HTTP sampler sends requests and measures responses, but it does not render a page or run all JavaScript like Chrome does. It is also not only for websites: it can load-test databases, mail servers and other services.

5.4 Syllabus-only automation tools

Not asked directly in the six papers: automation frameworks (linear, modular, library architecture, data-driven, keyword-driven, hybrid, behaviour-driven), SoapUI, Tosca and Appium. They are in the syllabus; learn one line each in case a 3–4 mark part appears.
TopicExam-ready answer
Linear frameworkAlso called the record-and-playback framework; used for small applications. No custom code is needed, but the data is context-sensitive, so the same case cannot be rerun with other data sets without adjustment.
Modular frameworkThe tester segments the whole programme into smaller parts as per customer requirements and writes scripts independently. Maintenance and scalability are easier, but finding reusable flows takes more time.
Library architectureReusable functions are kept in a library and called by the test scripts; the book lists it as one of the six framework types.
Data-driven frameworkThe script reads test data from external files such as Excel, text, CSV, ODBC sources and DAO objects and loads it into variables. Fewer scripts cover many data sets; a skilled tester is needed.
Keyword-driven frameworkAlso called table-driven testing; the keywords listed in the project’s Excel sheet drive the scripts. A single keyword can be reused in several scripts, but setting up the structure takes time and investment.
Hybrid frameworkCombines the advantages of keyword-driven and data-driven frameworks; needs more automation work because the tests are completely written.
Behaviour-drivenEncourages participation from developers, testers and business analysts; requirements can be written in plain, non-technical language, but the team needs technical know-how and test-driven development experience.
SoapUILeading open-source, cross-platform API testing tool. Runs automated functional, regression, compliance and load tests on Web APIs; also supports security testing and integration with Maven, Hudson, JUnit and Ant.
ToscaTricentis Tosca: model-based and risk-based automation for end-to-end functional and regression testing. Includes integrated test management, GUI, CLI and API.
AppiumOpen-source mobile automation tool from Sauce Labs for native, hybrid and web apps on simulators, emulators and physical devices. Converts Selenium WebDriver commands to UI Automator (Android) and UI Automation (iOS).
