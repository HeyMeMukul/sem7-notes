3.7 Functional vs non-functional testing

Syllabus: non-functional testing includes performance, memory, scalability, compatibility, security, cookies, session, recovery, installation, ad hoc, risk-based, I18N, L10N and compliance testing.

Q15Differentiate between Functional testing and Non-functional testing. / Illustrate Non-functional testing and explain performance testing with example.

6 marks★★★ 3×

Asked in: 2024 May Q1(c) [6] · 2025 Nov Q2(c) [6] · 2023 May Q1(c) [6, non-functional + performance example]

1. Functional testing

Functional testing addresses the overall behaviour of the program by testing transaction flows, input validation and functional completeness. It is considered black-box testing because no knowledge of the internal logic of the system is used to develop test cases. System testing, regression testing and user acceptance testing are types of functional testing.

Both functional and structural methods together validate the entire system. For example, a functional test case may be taken from the documentation that describes how to perform a certain function, such as accepting bar-code input. Comparing actual outputs against expected behaviour gives a clearer overall picture than testing modules in isolation, because interactions between modules are frequently the points where errors occur.

  • Advantages: simulates actual system usage; makes no system structure assumptions.
  • Disadvantages: potential of missing logical errors in software; possibility of redundant testing.

2. Non-functional testing

Non-functional testing verifies the non-functional requirements of the application, such as performance and usability. It assesses properties that are not critical to functionality but contribute to the end-user experience.

Performance and reliability under load are not functional components of a software system, but they can make or break the user experience. Something that fails a non-functional test does not always cause an issue that users would notice, but it can indicate a problem in the system, especially at scale.

  • Advantages: covers testing that cannot be covered by functional testing; ensures the application runs efficiently and is reliable enough; ensures the security of the application.
  • Disadvantages: every time the software is updated, non-functional tests must be performed again; this re-examination makes the software expensive.

3. Functional vs non-functional testing

PointFunctional testingNon-functional testing
PurposeConfirms that the code is doing the right things.Validates that the code is doing things the right way.
FocusUser requirements.User expectations.
ToolsCan be performed manually and with automation tools.Requires automation tools for effective testing.
OrderDefines all the process and is executed first.Executed only after functional testing, because the system must be defined first.
Test case typeEasy to execute black-box test cases.Easy to execute white-box test cases.
TypesUnit testing, integration testing, system testing.Performance, compatibility and usability testing.
InputsBusiness requirements.Parameters such as speed and scalability.

4. Performance testing with example

Performance testing is conducted after functional testing and is usually conducted for web applications. Its main objective is to get information about response time, throughput and utilization under a given load. It is normally used with load testing and stress testing.

Performance testing does not give a pass or fail result; it sets the benchmark and standard of the application against concurrency/throughput, server response time, latency and render response time. It determines how much resources are used and how scalable, reliable and speedy the product is.

Example: the login API must respond in under 2 seconds for 500 concurrent users, with an error rate below 1%. Ramp from 0 to 500 virtual users over 10 minutes, hold for 30 minutes, and measure average and 95th-percentile response time, throughput and errors. If the 95th percentile is 3.8 s, the requirement fails and the bottleneck (often the DB connection pool or CPU) is reported.

Q16How would you explain performance & security testing?

6 marks★★ 2×

Asked in: 2022 Nov Q2(c) [6, performance with example] · 2025 May Q1(b) [6, performance + security]

1. Performance testing

Performance testing is conducted after functional testing and is usually conducted for web applications. Its main objective is to get information about response time, throughput and utilization under a given load. It is normally used with load testing and stress testing.

Poor latency destroys the user experience; well-written performance tests catch problems before they become evident to users. Performance testing determines how much resources are used and how scalable, reliable and speedy the product is. It does not give a pass or fail result; it sets the benchmark and standard of the application against concurrency/throughput, server response time, latency and render response time.

It is a subset of performance engineering and is used to find performance issues in the design and architecture of the product. It is extensive and contains load testing, stress testing, capacity testing, volume testing, endurance testing, spike testing, scalability testing and reliability testing.

2. Load testing vs performance testing (book)

PointPerformance testingLoad testing
Load usedExpected number of users.More than the usual load.
AimGet a baseline and see behaviour under normal conditions; check whether the required response time is met.See whether the application can sustain the increased load or will crash and kill the servers.
MethodMeasure response time with the expected load.Start at low numbers and gradually increase to the desired load, then ramp down.
GoalSet the performance benchmark.Prove the system can handle the expected volume with minimal acceptable performance degradation.

A load test is sometimes referred to as volume testing because it ensures a web system can handle the expected volume of traffic.

3. Example

An e-commerce sale page must serve 2,000 users with page load under 3 s. JMeter ramps to 2,000 threads, holds for 30 minutes and reports 2.4 s average, 3.6 s p95 and 0.4% errors. The target is narrowly missed, so the image CDN is tuned.

4. Security testing

Security testing is a type of software testing that intends to uncover vulnerabilities of the system and determine that its data and resources are protected from possible intruders. It depends heavily on expertise and experience.

Software security is about making software behave correctly in the presence of a malicious attack. The difference between software safety and software security is the presence of an intelligent adversary bent on breaking the system.

Types of security testing (book):

  1. Network security — looking for vulnerabilities in the network infrastructure (resources and policies).
  2. System software security — assessing weaknesses in the OS and database system that the application depends on.
  3. Client-side application security — ensuring that the client cannot be manipulated.
  4. Server-side application security — making sure the server code and its technologies are robust enough to fend off any intrusion.

Example: log in as a normal user, change the URL /account?id=105 to /account?id=106, and confirm the server returns “403 Forbidden”, not another user's data. A search box given ' OR 1=1 -- must return no data and log the attempt.

Difference: performance asks “will it stay fast under load?”; security asks “can an attacker break it?”. Both are non-functional and both need a production-like environment.

Q19What is Cookies testing? Explain Cookies testing with an example.

6 marks★★ 2×

Asked in: 2024 May Q2(b) [6] · 2025 Nov Q2(b) [6]

Definition: A cookie is a file used to store the session content and other session-related information inside the browser. Some sites use cookies for the payment gateway and some sites use them for an authentication session.

Cookie testing is performed to test the cookies that are saved in the web browser whenever a web application is accessed by making use of its server. It is all about testing the cookies present at the client side — in local machines, computers or browsers. A basic understanding of the cookie is useful before going through the methods of cookie testing.

1. Types of cookies (book)

TypeDefinitionWhat cookie testing checks
Session cookieGets active on the call made by the web browser and is automatically deleted on termination of the session by that browser.The cookie exists during the session; it disappears when the browser/session is closed.
Persistent cookieResides permanently on the user's machine and has a specific time-period for expiration, which may last for a few months or a year.The cookie remains after the browser closes and expires only at the set date/time.

2. What to test

  1. Creation: the cookie is created when the web application is accessed or when the user logs in.
  2. Client-side storage: the cookie is stored in the browser on the local machine, not on the server.
  3. Session behaviour: a session cookie is active during the session and is deleted when the session terminates.
  4. Expiry: a persistent cookie stays until its specified expiry date and is removed after it.
  5. Purpose: cookies used for the payment gateway or authentication session work correctly and do not leak the session.
  6. Browser handling: the application behaves correctly when cookies are cleared or when the browser does not accept cookies.

3. Example — login and “remember me”

  1. Open the site and log in. The server sends a session cookie to the browser.
  2. Close the browser completely and open the site again. The session cookie should be deleted; the user should have to log in again.
  3. Log in again and tick “Remember me”. A persistent cookie with an expiry date (say 30 days) is stored.
  4. Close and reopen the browser. The persistent cookie is still there, so the user is remembered.
  5. Change the system date beyond the expiry date. The cookie must expire and the user must log in again.
  6. For a payment gateway, the payment cookie should be active only during the payment session and must be removed after the transaction ends.

Why it matters: cookies store session content and authentication sessions, so incorrect creation, expiry or deletion can cause a wrong session state, a failed payment or an exposed login session.

Q17Explain Risk Based Testing in detail.

6 marks★ 1×

Asked in: 2025 May Q1(c) [6]

Definition: Risk-based testing is an approach to software testing that relies on risk assessments to determine the best allocation of testing resources. Risk is the probability of occurrence of an undesirable outcome; this outcome is also associated with an impact.

Risk-based testing is a ranking of tests and subtests for functionality. Tools and techniques such as equivalence partitioning, state transition tables, decision tables, boundary value analysis, path flow testing and all-pairs testing help assess the most risk-prone areas.

It is done on a project at the very early stages. This helps identify the project risks that disclose the project quality. That information, in turn, leads to the testing of the planning, specifications, preparations and execution.

1. Risk formula

Risk = Probability of an undesirable outcome × Impact of that outcome

Probability depends on complexity, new technology, change frequency, developer experience and usage. Impact depends on money, safety, legal exposure, users affected and reputation.

2. Process of risk-based testing (book)

  1. Identify every requirement with regard to the risks associated with the project.
  2. When it comes to assessing risks, prioritize the needs.
  3. Prepare and outline the tests based on requirement prioritization.
  4. Perform the test as per prioritization as well as approval criteria.

3. Example — hospital application

RequirementProbabilityImpactPriorityTest effort
Wrong dosage calculationHigh (complex formula)Very high (patient safety)CriticalCode review, unit tests, boundary tests, independent clinical validation
Patient report downloadMediumMediumMediumFunctional and performance tests
Colour of the help iconLowLowLowTest once

4. Advantages (book)

  1. As all the critical functions of the application are tested, it improves the overall quality of the product.
  2. Early detection of potential problem areas, so effective preventive measures can be taken.
  3. Improved market opportunity (time to market) and on-time delivery.
  4. Improved service performance.
  5. Helps make testing a better planned and organized activity.

Limitation: risk scores are estimates and can be biased, so they must be reviewed and updated as the project changes.

Q18Can you explain compatibility testing & security testing?

6 marks★ 1×

Asked in: 2025 May Q2(b) [6]

1. Compatibility testing

Compatibility testing checks whether the software is capable of running on different hardware, operating systems, applications, network environments or mobile devices. It evaluates that the application is compatible with other hardware/software with the minimum and maximum configuration.

Why it is important (book):

  1. It ensures complete customer satisfaction.
  2. It provides service across multiple platforms.
  3. It helps identify bugs during the development process.

Two types:

TypeWhat is verifiedWhy it is easy or hard
Backward compatibilityBehaviour and compatibility of the developed hardware/software with older versions.Much more predictable, because all changes from previous versions are known.
Forward compatibilityBehaviour and compatibility with newer versions.Harder to predict, because the changes that will be made in newer versions are not known.
What is variedExample
Operating systemSame build on Windows 11 and Ubuntu.
Hardware / deviceDesktop, tablet, phone; different screen sizes.
Application / browserChrome, Firefox, Edge, Safari.
Network environment2G/3G/4G/Wi-Fi and high-latency links.
Minimum / maximum configurationLow-RAM machine and a high-end machine.

2. Security testing

Security testing intends to uncover vulnerabilities of the system and determine that its data and resources are protected from possible intruders. It depends heavily on expertise and experience. Software security means making software behave correctly in the presence of a malicious attack; the difference between safety and security is the presence of an intelligent adversary.

Types (book):

  1. Network security — vulnerabilities in the network infrastructure (resources and policies).
  2. System software security — weaknesses in the OS and database system the application depends on.
  3. Client-side application security — ensuring that the client cannot be manipulated.
  4. Server-side application security — ensuring the server code and its technologies are robust enough to fend off any intrusion.

Example: a user changes role=user to role=admin in the request; the server must reject it. A search box given ' OR 1=1 -- must return no data and log the attempt.

Tools used in practice: OWASP ZAP and Burp Suite (only on authorised systems).

Q20Can you illustrate Adhoc Testing with example.

6 marks★ 1×

Asked in: 2023 Nov Q2(a) [6]

Definition: Ad hoc testing is unstructured, random and requires no documentation. It is also referred to as random testing and monkey testing.

1. Characteristics (book)

  1. Random testing, done on any part of the application.
  2. It is a black box testing technique.
  3. It detects/uncovers bugs and loopholes that may be missed during automated testing.
  4. It requires a software tester with in-depth knowledge of the testing system.
  5. It is unplanned and unstructured.
  6. It does not require any documentation or formal test case execution.

2. Types of ad hoc testing

TypeHow it is done
Buddy testingDone with at least two members — one from the testing team and one from the development team. It is performed when unit testing is done on the application, and it helps both teams do their jobs.
Pair testingTwo testers work together on a module with the same test setup shared between them. One tester performs testing while the other observes and analyses the process; both share the work and document their observations.

3. Example

A tester opens a food-delivery app and randomly tries:

  1. adding 20 items to the cart, then removing them all;
  2. applying a coupon, going back, and applying it again;
  3. turning off Wi-Fi during payment;
  4. rotating the phone on the checkout screen;
  5. entering a 200-character address.

The app crashes during payment with Wi-Fi off and shows a blank coupon after the back-and-reapply step. Both are logged as defects. This is ad hoc testing because there was no plan, no written test case and no expected-result document.

4. Advantages

  1. Ad hoc testing can be done without following any fixed process.
  2. The tester can find more defects than in traditional testing because of the various innovative methods that can be applied.
  3. When in-depth testing is required in less time, ad hoc testing can be performed and still deliver a quality product on time.

5. Disadvantages

  1. It is dependent on the test engineer's product knowledge, because he/she must know the flow of the application.
  2. We cannot trace the requirements or check requirement/test coverage, as there is no traceability matrix or documentation.

6. Ad hoc vs exploratory testing

PointAd hoc testingExploratory testing
PlanningPerformed without planning or goal.Performed with a clear plan; structured.
Prior knowledgeThe tester needs complete knowledge of the software.No compulsion; the tester can work with or without knowledge of the subject.
TargetNo target or goal; everything is done randomly, without structure.Targets and goals can be set while still allowing free exploration.
DocumentationNo documentation; none of the steps are documented.Documentation/recording can be done, so bugs can be reproduced.

Q12What do you mean by unit and integration testing? What are the approaches used in integration testing?

6 marks★★★ 3×

Asked in: 2023 May Q1(b) [6] · 2023 Nov Q2(b) [6] · 2025 Nov Q1(c) [6]

1. Unit testing

A unit is the smallest testable piece of software. Unit testing is the level where individual units/components of a software are tested. The purpose is to validate that each unit performs as designed. It aims at testing each component that the system is built upon; if each works as defined, the system as a whole has a better chance of working together.

Unit testing is the first level of testing and is performed before integration testing. It is normally performed by the software developers themselves.

Advantages (book):

  1. Codes are more reusable.
  2. Increases confidence in changing/maintaining code.
  3. Development is faster.
  4. Debugging is easy.
  5. The cost of fixing a defect found during unit testing is less than at higher levels.

2. Integration testing

Integration testing is the phase in which individual software modules are combined and tested as a group. It occurs after unit testing and before validation testing. The entire system is viewed as a collection of subsystems determined during system and object design; the order in which subsystems are selected for testing and integration determines the testing strategy.

Example — three-layer call hierarchy (Fig. 3.7.2):

A Layer I / | \ B C D Layer II / \ | E F G Layer III

3. Steps in integration testing (book)

  1. Based on the integration strategy, select a component to be tested. Unit test all the classes in the component.
  2. Put the selected component together; do any preliminary fix-up necessary to make the integration test operational (drivers, stubs).
  3. Do functional testing: define test cases that exercise all use cases with the selected component.
  4. Do structural testing: define test cases that exercise the selected component.
  5. Execute performance tests.
  6. Keep records of the test cases and testing activities.
  7. Repeat steps 1 to 7 until the full system is tested.

Primary goal: identify errors in the current component configuration.

Who / when / where / why: done by developers/testers; test cases are written when the detailed specification is ready; testing is continuous throughout the project; done on the programmer's workbench; the reason is to discover inconsistencies in the combination of units.

4. Approaches used in integration testing

ApproachHow it worksAdvantageLimitation
Big-bangCombine all modules at once and test the whole group.Simple; no extra test code.Hard to locate faults; risky.
Top-downStart from the main module; replace lower modules with stubs; add real modules level by level.Early demonstration of the overall flow; major control logic tested first.Needs many stubs; low-level logic tested late.
Bottom-upStart from the lowest modules; use drivers to call them; build upward.Low-level logic tested early; fewer stubs.No early view of the overall system; needs drivers.
Sandwich / hybridCombine top-down and bottom-up; the two meet at a middle layer.Balances both approaches; good for large systems.Complex to plan.
Diagram to draw: the three-layer tree A → B, C, D → E, F, G. Mark stubs for top-down and a driver at the bottom for bottom-up.

Q13How would you explain System Testing and Acceptance Testing?

6 marks★★★ 3×

Asked in: 2022 Nov Q1(c) [6] · 2023 May Q2(c) [6] · 2025 Nov Q1(b) [6]

1. System testing

Definition: System testing is the process of testing an integrated system to verify that it meets the specified requirements. It tests the overall interaction of components and finds disparities between the implementation and the specification.

It is performed after integration testing and before acceptance testing. Normally, independent testers perform system testing. The system is tested for its non-functional requirements such as performance, portability, security, safety and interoperability of hardware/software.

System testing also identifies new faults that may have been introduced while current faults were being corrected. It verifies that a new version or release still performs the same functions in the same manner as an older version or release.

Example: for an e-commerce site, place an order end to end — search → cart → payment gateway → order record → confirmation e-mail — and check performance, security and portability.

2. Acceptance testing

Definition: Acceptance testing is a formal testing activity conducted to determine whether a system satisfies its acceptance criteria. There are two categories: user acceptance testing and business acceptance testing.

TypeWho does itPurpose
User acceptance testing (UAT)The customerEnsure the system satisfies the contractual acceptance criteria before it is signed off as meeting the needs.
Business acceptance testingThe development organization of the supplierEnsure that the system will eventually pass the user acceptance testing.

Acceptance testing can be done at the client's office or the developer's office. Its three major objectives are:

  1. Confirm that the system meets the agreed-upon criteria.
  2. Identify and resolve discrepancies, if there are any.
  3. Determine the readiness of the system for cut-over to live operations.

Acceptance tests are usually created by business customers and expressed in a business domain language. They are high-level tests that test the completeness of a user story played during a sprint/iteration. They are ideally created through collaboration between business customers, business analysts, testers and developers; the business customers (product owners) are the primary owners of these tests. They include both business logic tests and UI validation.

3. System vs acceptance testing

PointSystem testingAcceptance testing
Done byIndependent testersCustomer / business owners
BasisSpecified requirements (SRS)Acceptance criteria and business needs
ScopeWhole integrated system, including non-functional requirementsFitness for use; key business scenarios and user stories
ResultTest report and defect logFormal acceptance or rejection; sign-off

Q14Identify the importance of Regression Testing & explain it. / Why Regression Testing is important?

6 marks★★ 2×

Asked in: 2022 Nov Q2(b) [6] · 2023 Nov Q2(c) [6]

Definition: Regression testing refers to testing activities that occur after software changes. It usually refers to testing activities during the software maintenance phase. It is also referred to as verification testing.

Regression testing is initiated after a designer has attempted to fix a recognized problem or has added source code to a program that may have inadvertently introduced errors. It is a quality control measure to ensure that the newly modified code still complies with its specified requirements and that the unmodified code has not been affected by the maintenance activity.

1. Importance of regression testing

  1. Checks the modified code: the new or changed code still meets its specified requirements.
  2. Protects the unmodified code: it confirms that maintenance activity has not affected code that was working earlier.
  3. Catches side effects: a fix or new feature may introduce errors in another part of the program.
  4. Acts as quality control: it is a planned check during the maintenance phase, not an optional extra.
  5. Finds inadvertent errors: adding source code can introduce faults that were not present before.
  6. Supports new releases: it verifies that a new version performs the same functions as the older version.
  7. Saves cost and time: existing test cases are re-executed, so no new test cases are created and defects are caught before release.

2. Where it is performed

Regression testing can be performed during any level of testing — unit, integration, system or acceptance — but it is mostly relevant during system testing. During regression testing, new test cases are not created; previously created test cases are re-executed.

3. What is needed

  • Regression test models to support the definition of the regression test strategy, test cases and coverage criteria.
  • A selected set of existing tests that covers the changed area and the areas that depend on it.
  • Records of earlier test results so that the new results can be compared.
  • Automation where possible, because the same tests are run again and again.

4. Example

After changing the login password rule from 6 to 8 characters, re-run the existing registration, login, forgot-password, session-timeout and account-lock tests. If the forgot-password test now fails, the change has caused a regression.

Note: regression testing is not the same as retesting. Retesting checks that the specific defect is fixed; regression checks that other features still work after the change.

Q4What do you think about static techniques? / Identify how the different static test case design techniques are useful for software testing.

6 marks★★★ 3×

Asked in: 2022 Nov Q1(a) [6] · 2023 Nov Q1(a) [6] · 2023 Nov Q1(c) [6]

Definition: A test design technique is used to select a good set of tests from all possible tests for a given system. Static testing does not execute code — it manually checks work documents to find errors at an early stage. It checks the software product and related artifacts without executing them.

Static testing uses the white box method and may include reviews, walkthroughs, inspections and audits. Its main goal is to check whether the coding and algorithm work properly, point out code errors at the beginning of the testing process, and make further testing more efficient and productive.

1. Static testing methods

  1. Code inspections — software code is manually reviewed for defects.
  2. Code analyzers — a tool checks the code for type errors, memory leaks, syntax errors, etc.
  3. Compiling — compiling the code using the source compiler or interpreter.
  4. Modelling techniques — software requirements are modelled to verify that they are correct.

Static testing finds bugs before compilation. The earlier a bug is detected, the cheaper it is to fix.

2. How each static technique is useful

TechniqueWhat is doneUsefulness
Informal reviewThe author asks a colleague to review a document or code; a two-person team. It is not documented.Very cheap and quick; good for early drafts and small work products.
WalkthroughThe designer or programmer leads the team through the product; participants ask questions and comment on possible errors and violations of development standards.Semi-formal; spreads understanding; most effective at source-code level and on small work products.

Q5Explain the following test case design techniques: (i) Informal Reviews (ii) Walkthroughs (iii) Inspection.

6 marks★ 1×

Asked in: 2024 May Q2(a) [6] — technical review is also part of the syllabus list

1. Informal review

Informal reviews are applied at various times during the early stages in the life cycle of a document. A two-person team can conduct an informal review: the author asks a colleague to review a document or code. The peers try to find defects and discuss them in a review meeting. The goal is to help the author and improve the quality of the document. Informal reviews come in various shapes and forms, but they have one characteristic in common — they are not documented. The material may be as informal as a computer listing or hand-written documentation.

2. Walkthrough

A walkthrough is a semi-formal type of review. Products are reviewed by groups of people, mostly without preparation. A requirements traceability review is a walkthrough: it traces a requirement from customer requirements to the test procedures, and all issues found are documented on CAR forms.

It is a form of software peer review in which the designer or programmer leads members of the development team and other interested parties through the product. Participants ask questions and comment on possible errors, violation of development standards and other problems. The producer is the review leader, so the utility of a walkthrough depends on the real goal of the producer. Walkthroughs are most effective at the source code level and on other small work products.

3. Inspection

Software inspection is a disciplined engineering practice for detecting and correcting defects in software artifacts and preventing their leakage into field operations. It is a more formal process than a walkthrough and is used to collect metrics or statistics about the software process. A walkthrough is a more informal version of an inspection.

Inspections reduce variability and tighten process control. They address three major tasks of process management: planning, measurement and control. They collect quantitative quality data at defined points in the development process, which gives feedback to developers and feed-forward to future steps. Michael Fagan recommended inspections on detailed design, cleanly compiled code and completion of unit test.

At a minimum, a formal inspection includes a designated moderator, the author of the work and at least one peer inspector. Walkthroughs generally do not include a designated moderator and are often led by the author.

Steps of inspection: planning → overview → preparation → meeting → rework → follow-up.

4. Comparison

FocusImprove product.Find defects.
ActivitiesFind defects; examine alternatives; forum for learning; discussion.Find defects; only defect explanation allowed; learning through defects and inspection.
ProcessInformal.Formal.
QualityVariable; personalities can modify the outcome.Repeatable with a fixed process.

5. Technical review (extra point)

A technical review reviews the technical approach used during development. It is a peer review activity, less formal than audit and inspection. The product is examined and defects found are mainly technical. There is no management participation; a full report lists the issues. Its goals are to ensure technical concepts are used correctly, assess the value of technical concepts and alternatives, maintain consistency in their use and representation, and inform participants about the technical content of the document.

3.5 Experience-based techniques

Syllabus: Error guessing, Exploratory testing.

Q11State in your own words Error guessing and Exploratory testing. / What do you think about Exploratory testing.

6 marks★★★ 3×

Asked in: 2022 Nov Q1(b) [6] · 2023 May Q2(a) [6, experience-based techniques] · 2025 May Q2(c) [6, exploratory]

Experience-based testing is the technique of executing testing activities with the help of experience gained through several years. The tester verifies and validates software quality using past experience of testing a similar type of product in the same domain. People's knowledge, skills and background are of prime importance for the test conditions and test cases.

These techniques go together with specification-based and structure-based techniques. They are used when there is no specification, or when the specification is inadequate or out of date. They are used for low-risk systems.

When experience-based testing is required:

  1. Non-availability of requirements and specifications.
  2. Limited knowledge of the software product.
  3. Inadequate specification.
  4. Restricted amount of time to perform testing.

1. Error guessing

In error guessing, the tester applies his/her experience to guess the areas in the application that are prone to error. It makes use of the tester's skills, intuition and experience to anticipate errors, defects and failures that may not be easily captured by formal techniques such as boundary value analysis and equivalence partitioning.

The success of error guessing is very much dependent on the skill of the tester; good testers know where defects are most likely to be. Every application has a history, based on the people working on it and the functionality or integration points it has; an experienced tester knows the type of errors that occurred in the past.

Book's example: in an e-commerce application, the discount logic has often failed when a random discount code is applied. The tester tries different combinations of valid and invalid discounts and checks that the logic works fine. That insight comes only when the tester has enough experience in the application to know its historical issues.

2. Exploratory testing

Exploratory testing is a testing technique and, at the same time, a progressive learning approach to perform maximum testing with minimal planning. During exploratory testing, the tester constantly studies and analyses the software product and applies his/her skills, traits and experience to develop a strategy and test cases and carry out the necessary testing.

Exploratory testing is all about testers exploring an application to identify and document potential bugs. Testers embark on a process of investigation and discovery to test a product effectively.

  • It is often used in Agile models because it links with discovering, investigating and gaining a greater understanding of the code under test.
  • It is valuable when new testers join the team — they bring knowledge, expertise and a fresh perspective.
  • Its best use is when specifications and requirements are inadequate and time is severely limited.

3.1 White box testing (and grey box testing)

Q1Explain White box testing and Grey box testing in detail.

6 marks★★ 2×

Asked in: 2024 May Q1(a) [6] · 2025 May Q1(a) [6, white box only]

1. White box testing — definition

White box testing builds upon the internals of a software component. It is a detailed investigation of the internal logic and structure of the code, so the tester must have full knowledge of the source code (Fig. 3.1.1).

The book defines it as a test case design method that uses the control structure of the procedural design to derive test cases. It can uncover implementation errors such as poor key management, and it is applicable at unit, integration and system levels.

2. White box techniques (name them)

  • Control flow testing
  • Branch testing
  • Basis path testing
  • Data flow testing
  • Loop testing

3. Advantages of white box testing

  1. Can be done by the development team.
  2. Does not require a completed GUI.
  3. Highly systematic and easy to reproduce.
  4. Thorough — it can test every possible path.
  5. Can uncover errors early in the development process.

4. Disadvantages of white box testing

  1. Time required of developers.
  2. Code updates can invalidate test cases.
  3. Hard to separate the program from the testing environment.

5. Grey box testing — definition

Grey box testing is a combination of black box and white box testing. The grey box tester has knowledge of the code, but not completely. The tester is not required to design test cases; test cases are created from algorithms that evaluate internal states, program behaviour and application architecture knowledge, and the tester carries out and interprets the results.

Purpose: improve the quality of the product by covering both functional and non-functional testing together, which saves time and the lengthy process of testing the application.

6. Grey box techniques

  • Matrix testing — examines all variables in an application.
  • Regression testing — verifies whether changes or bug fixes have caused errors in existing components.
  • Orthogonal array testing — used when inputs are too many or too complex; optimises test cases and balances coverage with effort.
  • Pattern testing — evaluates past defects to identify patterns that lead to defects.

7. Advantages and disadvantages of grey box testing

Q2State in your own words Black Box Testing.

6 marks★ 1×

Asked in: 2025 May Q2(a) [6]

Definition: Black box testing looks at the available inputs for an application and the expected outputs that should result from each input. It is also called functional testing.

1. Main idea

Define the initial component state, the input and the expected output for the test. Set the component in the required state, give the defined input, observe the output and compare it with the expected output (Fig. 3.1.2).

No knowledge of the internals of the code is required. Test cases are designed from the specification; the tester ignores the internals and focuses on the relationship between inputs and outputs.

2. Example — search engine

You type a search term in the search bar and press “Search”; results are returned. You do not know or see the specific process used to obtain those results — you simply give an input and receive an output. That is black box testing.

3. Advantages

  1. Easy to use.
  2. Quicker test case development.
  3. Efficient for a large code segment.
  4. Tester perception is very simple.

4. Disadvantages

  1. Only a selected number of test scenarios are performed, so there is limited coverage.
  2. Without a clear specification, test cases are difficult to design.
  3. Testing can be inefficient.

5. Result rule and a small test table

A black box test passes input to the system, records the actual output and compares it with the expected output. If actual output = expected output, the test passes; otherwise it fails.

InputExpected outputActual outputResult
Valid search term “STQA”Matching results shownMatching results shownPass
Blank searchMessage: “Enter a search term”Same message shownPass
Very long stringNo crash; message or resultsPage crashesFail

In one line: black box testing is testing from a functional or behavioural perspective to ensure the program meets its specification; it is focused on results, not on how the code works.

1. Equivalence class partitioning (ECP)

ECP reduces the number of test cases that need to be developed. We do not want to write several test cases that test the same aspect of the program. Equivalence partitioning divides the input domain into classes. For each class, the set of data should be treated the same by the module under test and should produce the same answer. Test cases are designed so that the inputs lie within these classes.

The program computes the sum of the first |value| integers as long as the sum does not exceed maxint; otherwise an error is reported. If value is negative, it takes the absolute value.

3. Boundary value analysis (BVA)

Boundary value is defined as a data value that corresponds to a minimum or maximum input, internal, or output value specified for a system or component. Programmers often make mistakes on the boundaries of equivalence classes / the input domain.

  1. Choose one (n) arbitrary value in each equivalence class.
  2. Choose values exactly on the lower and upper boundaries of the equivalence class.
  3. Choose values immediately below and above each boundary (if applicable).

Q7Can you explain statement coverage testing & branch coverage testing?

6 marks★ 1×

Asked in: 2023 May Q2(b) [6]

1. Statement coverage testing

Statement coverage is a white box testing technique. It involves the execution of all statements at least once in the source code. It is a metric used to calculate and measure the number of statements in the source code that have been executed.

It aims to test all the statements in the program. It is a good measure of testing each part in terms of statements, but it is not a good technique for testing control flow. For example, one node can be reached from multiple other nodes, but since the aim is only to cover statements, those conditions are not covered.

Statement coverage (%) = (Number of statements executed as a part of the application's code ÷ Total number of statements in the application's source code) × 100

Statement coverage is put into practice as part of code validation during the build and development phases.

2. Branch coverage testing

Branch coverage is a requirement that, for each branch in the program (e.g. if statements, loops), each branch is executed at least once during testing. A branch is one of the possible execution paths the code can take after a decision statement.

Branch coverage is also known as decision coverage testing. It aims to test all branches or edges at least once, or to test each branch from a decision point at least once. It provides a solution to the problem faced in statement coverage.

Branch coverage helps validate all branches and makes sure that no branching leads to abnormal behaviour. A low branch coverage shows that some scenarios lack testing; such scenarios may contain defects that appear only in edge cases in production.

3. Worked example

1  read a, b
2  if (a > b) then
3      max = a
4  else
5      max = b
6  end if
7  print max
Test caseInputStatements executedBranch taken
TC1a = 5, b = 31, 2, 3, 6, 72 → true
TC2a = 2, b = 71, 2, 4, 5, 6, 72 → false

TC1 + TC2 execute every statement (100% statement coverage) and both outcomes of the if (100% branch coverage).

4. Why branch coverage is stronger

The book gives the example of an if ... then statement with no else. Executing it when the condition is true tests only one of two branches in the flow graph. Branch testing seeks to ensure that every branch is executed.

Pros of branch coverage (book):

  1. Approves that all branches in the code are reached.
  2. Guarantees that no branch prompts any irregularity in the program's operation.
  3. Kills issues that happen with statement coverage testing.

Q8Can you explain path coverage testing & conditional coverage testing.

6 marks★ 1×

Asked in: 2022 Nov Q2(a) [6]

1. Path coverage testing

Path coverage aims to test the different paths from entry to the exit of the program. A path is a combination of different decisions taken in sequence. The number of paths can be too many to test — for example, a loop can go on and on — so cyclomatic complexity is used to find and avoid redundant test cases.

In this technique, the test case is executed in such a way that every path is executed at least once. All possible control paths are taken, including loop paths taken zero, once and multiple (ideally maximum) times. Test cases are prepared from the logical complexity measure of the procedural design, and every statement is guaranteed to execute at least once.

A flow graph, cyclomatic complexity and graph metrics are used to arrive at the basis path. The objective is that each independent path through the program is executed at least once. An independent path traverses at least one new edge in the flow graph, which means exercising one or more new conditions. Both the true and false branches of all conditions must be executed.

2. Limitation of path coverage (book's warning)

  • Testing all paths does not mean the programmer will find all bugs.
  • Many bugs arise because programmers forgot to include some processing in the code, so there are no paths to execute.
  • Some bugs are related to the order in which code segments execute. If segments a, b and c run as <a, b, c> the program may work, but as <a, c, b> an error may appear. It is practically impossible to test all orders and all program paths.

3. Conditional coverage testing

Condition coverage aims to test individual conditions with the possible different combinations of Boolean input for the expression. The possible outcomes — true and false — for each condition are tested at least once, so each individual condition is one time true and one time false.

The outcome of the decision point is only relevant for checking the conditions; the combinations of conditions are not relevant.

4. Example — if (a > 0 AND b < 5)

Testaba > 0b < 5Decision
TC113TTTrue
TC2−17FFFalse

TC1 + TC2 give 100% condition coverage: each atomic condition takes both true and false. The decision also takes both outcomes here.

5. Condition coverage without decision coverage

TC1: a=1, b=7 → T, F → decision false. TC2: a=−1, b=3 → F, T → decision false. Every condition takes true and false, so condition coverage is 100%, but the decision is never true, so decision coverage is 0%. This shows why condition coverage alone is not enough — use it with decision coverage.

Q9Discuss Loop coverage testing and types of it in detail.

6 marks★ 1×

Asked in: 2024 May Q2(c) [6]

Definition: Loop testing is an example of white box testing. It is used to test software loops and is one type of control structure testing.

Goal: test while-do, do-while and any other loops thoroughly — ensure each loop is executed at minimal, typical and maximal values, and try to “break” the program by having a loop executed with fewer than the minimum and larger than the maximum number of iterations.

1. Why loop testing is performed (book's reasons)

  1. It helps resolve loop repetition observation.
  2. It can estimate conditions in performance and facility.
  3. The loop's uninitialized variables can be detected by testing loops.
  4. It aids in the classification of loop starting issues.
  5. Testing can return the loop to routine issues.
  6. Loop testing can reveal production/capability bottlenecks.
  7. It serves to classify the loop's beginning queries.

2. Types of loops to be tested
