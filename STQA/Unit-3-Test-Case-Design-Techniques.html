3.1 White box testing (and grey box testing)

Syllabus: White Box Testing, Black Box Testing, Grey Box Testing.

Q1Explain White box testing and Grey box testing in detail.

6 marks★★ 2×

Asked in: 2024 May Q1(a) [6] · 2025 May Q1(a) [6, white box only]

1. White box testing — definition

White box testing tests the internal structure and logic of the code. The tester can see the source code, control flow and data flow. It is also called structural testing, glass-box testing or clear-box testing.

Goal: execute every statement, branch, condition, path and loop at least once, and remove dead code and logic errors.

2. White box process

  1. Read the code and identify all input and output points.
  2. Draw the control flow graph (CFG) — nodes are statements, edges are control transfers.
  3. Find independent paths and compute cyclomatic complexity V(G) = E − N + 2.
  4. Design test data to cover statements, branches, conditions, paths and loop boundaries.
  5. Execute the tests and measure coverage. Add tests until the target coverage is reached.

3. White box techniques (name them in the exam)

  • Statement coverage — every executable statement runs once.
  • Branch / decision coverage — every true and false outcome of every decision runs.
  • Condition coverage — every atomic condition takes both true and false.
  • Path coverage — every independent path from entry to exit runs.
  • Loop coverage — zero, one, two, many and boundary iterations run.

4. Grey box testing — definition

Grey box testing is a partial white box approach. The tester knows some internal details — database schema, architecture, API contracts, data structures — but not the full source code. Testing is done at the interface level with this partial knowledge.

Example: test a web login by knowing the user table columns (user_id, password_hash, status) and the API URL, but without reading the Java service code. The tester checks SQL injection through the API and verifies database state after login.

5. White vs grey box

Q2State in your own words Black Box Testing.

6 marks★ 1×

Asked in: 2025 May Q2(a) [6]

Definition: Black box testing checks what the software does, not how it does it. The tester sees only the input, the output and the requirement. The code is hidden, so it is also called behavioural, functional or specification-based testing.

How it is done

  1. Read the SRS and list input fields, rules and expected outputs.
  2. Identify valid and invalid input classes.
  3. Select test data using BVA, equivalence partitioning, decision table, state transition, cause-effect graph or use cases.
  4. Run the test, compare actual output with expected output, and log a defect on mismatch.

Example — ATM withdrawal

InputExpected outputType
Amount ₹2,000, balance ₹10,000Cash dispensed; balance ₹8,000Valid
Amount ₹0“Enter a valid amount”Invalid
Amount ₹30,000, balance ₹10,000“Insufficient balance”Invalid
Amount ₹1,500 (not a multiple of ₹500)“Amount must be multiple of 500”Boundary/rule

Advantages and limitations

  • Advantages: works without code; tests user-visible behaviour; can start early from SRS; good for large systems and third-party software.
  • Limitations: cannot test hidden paths; may miss dead code; test data quality depends on the specification; duplication of tests is possible.

3.2 Static techniques and reviews

Syllabus: Informal Reviews, Walkthroughs, Technical Reviews, Inspection.

Q4What do you think about static techniques? / Identify how the different static test case design techniques are useful for software testing.

6 marks★★★ 3×

Asked in: 2022 Nov Q1(a) [6] · 2023 Nov Q1(a) [6] · 2023 Nov Q1(c) [6]

Definition: Static techniques test a work product without executing it. They examine requirements, design, code, test cases and documents by reading and reviewing them. They find defects early, before code runs.

Main static techniques and their usefulness

TechniqueWhat happensUsefulness
Informal reviewAuthor asks one or two colleagues to read the document; no formal record.Very cheap; quick feedback; good for early drafts and small teams.
WalkthroughAuthor explains the document or code step by step to a small group.Spreads understanding; finds unclear logic; good for training new team members.
Technical reviewPeer group with technical experts checks whether the product follows standards and is technically sound.Checks architecture, design, interfaces and compliance; decision-making review.

  • Defects are found before coding or testing, so the cost of fixing is low.
  • No test environment or executable build is needed.
  • Improves document quality, coding standards and team knowledge.
  • Complements dynamic testing — it finds defects that execution may hide.
Limitation: static techniques cannot check run-time behaviour, performance, memory use or real user interaction. They must be combined with dynamic testing.

Q5Explain the following test case design techniques: (i) Informal Reviews (ii) Walkthroughs (iii) Inspection.

6 marks★ 1×

Asked in: 2024 May Q2(a) [6] — technical review is also part of the syllabus list

PointInformal reviewWalkthroughInspection
FormalityLowestLow–mediumHighest
Led byAuthorAuthorModerator (not the author)
Participants1–2 peers3–6 team membersTrained inspection team (3–6)
PreparationNoneRead the materialIndividual preparation with checklist
RecordingUsually noneNotes may be takenFormal defect log and minutes
OutputVerbal commentsList of questions and suggestionsDefect list, severity, action owners
Best used forDrafts, small documentsCode logic, design teachingCritical requirements, design, code

(i) Informal review

The author gives a document to a colleague and asks for comments. There is no agenda, no checklist and no formal record. It is fast and cheap. Example: a developer asks a teammate to read a test-case sheet before sending it to the client.

(ii) Walkthrough

The author walks the group through the document or code. The group asks questions and suggests improvements. The aim is understanding and informal defect finding, not approval. Example: a programmer explains a payment module to testers so they can design integration tests.

(iii) Inspection

A formal, six-phase review: planning → overview → individual preparation → inspection meeting → rework → follow-up. Each reviewer checks against a checklist; a moderator controls the meeting; a recorder logs every defect. The author fixes defects and the moderator verifies closure. Inspection is the most effective static technique because it is systematic and measured.

(iv) Technical review (extra point)

A group of technical experts reviews the product for technical correctness and standards compliance. It may approve or reject the design. It is less formal than inspection but more technical than a walkthrough.

3.3 Dynamic structural techniques (coverage)

Syllabus: Statement, Branch, Path, Conditional and Loop Coverage Testing. These are white-box techniques: the test data is derived from the code structure.

Q6Interpret the different Dynamic Test Design Techniques.

6 marks★ 1×

Asked in: 2023 Nov Q1(b) [6]

Dynamic testing executes the software with test data and compares actual results with expected results. Dynamic structural techniques use the internal code structure to choose that data.

Q7Can you explain statement coverage testing & branch coverage testing?

6 marks★ 1×

Asked in: 2023 May Q2(b) [6]

1. Statement coverage

Every executable statement in the program must run at least once.

Statement coverage (%) = (statements executed ÷ total executable statements) × 100

2. Branch coverage

Every decision must take both the true and false path. It is also called decision coverage.

Branch coverage (%) = (branches exercised ÷ total branches) × 100

3. Worked example

1  read a, b
2  if (a > b) then
3      max = a
4  else
5      max = b
6  end if
7  print max
Test caseInputStatements executedBranch taken
TC1a = 5, b = 31, 2, 3, 6, 72 → true
TC2a = 2, b = 71, 2, 4, 5, 6, 72 → false

TC1 + TC2 give 100% statement coverage (all 7 statements) and 100% branch coverage (both outcomes of the if).

4. Important difference

Statement coverage can be 100% while branch coverage is only 50%. Consider:

if (x > 0) then
    y = 1
z = 2

With x = 5, statements y=1 and z=2 both run, so statement coverage is 100%. But the false branch of the if never runs, so branch coverage is 50%. Branch coverage is therefore stronger.

Use: statement coverage for quick smoke checks; branch coverage as the minimum unit-test gate in safety-critical code.

Q8Can you explain path coverage testing & conditional coverage testing.

6 marks★ 1×

Asked in: 2022 Nov Q2(a) [6]

1. Path coverage

Every possible path from entry to exit through the control flow graph must execute at least once. A path is a sequence of nodes and edges.

Path coverage (%) = (paths executed ÷ total feasible paths) × 100

Cyclomatic complexity gives the number of independent paths:

V(G) = E − N + 2 = number of predicate nodes + 1

Example: two independent if statements give V(G) = 3 independent paths, but up to 2² = 4 actual paths (TT, TF, FT, FF). Test all four if feasible.

Strength: strongest structural criterion — it exercises combinations of decisions. Weakness: the number of paths can grow exponentially; loops can make it infinite, so only a bounded subset is used.

2. Condition coverage

Every atomic condition inside a compound decision must take both true and false at least once.

Condition coverage (%) = (condition outcomes exercised ÷ total condition outcomes) × 100

Example: if (a > 0 AND b < 5) has two atomic conditions, so four outcomes are needed: a>0 T/F and b<5 T/F.

Testaba > 0b < 5Decision
TC113TTTrue
TC2−17FFFalse

TC1 + TC2 give 100% condition coverage and 100% decision coverage.

3. Condition coverage without decision coverage

TC1: a=1, b=7 → T, F → decision false. TC2: a=−1, b=3 → F, T → decision false. Every atomic condition takes T and F, so condition coverage is 100%, but the decision is never true, so decision coverage is 0%. This is why condition/decision coverage (CDC) is used in critical systems.

Q9Discuss Loop coverage testing and types of it in detail.

6 marks★ 1×

Asked in: 2024 May Q2(c) [6]

Definition: Loop coverage (loop testing) checks the boundaries of loops. Most loop defects are off-by-one errors — the loop runs one time too many or one time too few.

1. Loop test cases (for a simple loop with maximum n)

CaseIterationsWhat it checks
Zero0Loop body is skipped; initialisation is correct.
One1First iteration and exit condition.
Two2Second iteration; loop variable update.
Typicaln/2Normal working case.
MaximumnLast valid iteration; array bound.
Maximum + 1n+1Overflow / extra iteration defect.

2. Types of loops

  • Simple loop — one loop, fixed or variable bound. Use the six cases above.
  • Nested loop — a loop inside a loop. Test inner loop with outer at minimum, typical and maximum; then test outer boundaries.
  • Concatenated loop — two loops one after another. Test each independently, then test the boundary where the first ends and the second starts.
  • Unstructured loop — goto-based or irregular jumps. Redesign it if possible; otherwise test every jump path.

3. Example

sum = 0
for i = 1 to n do
    sum = sum + marks[i]
print sum

Test with n = 0 (empty array), n = 1, n = 2, n = 50 (typical), n = 100 (maximum), n = 101 (maximum+1 → should be rejected, not crash).

Benefits: catches off-by-one, wrong initialisation, missing update and array-overflow defects. Limitation: does not test the logic inside the body — combine with branch and path coverage.

3.4 Black-box test design techniques

Syllabus: Boundary Value Analysis, Equivalence Class Partition, State Transition, Cause-Effect Graph, Decision Table, Use Case Testing. The two most repeated are BVA and ECP.

Q10Discuss Boundary Value Analysis and Equivalence Class Partition.

6 marks★★ 2×

Asked in: 2024 May Q1(b) [6] · 2025 Nov Q2(a) [6]

1. Equivalence class partitioning (ECP)

Divide the input domain into classes that are expected to behave the same way. Test one value from each class instead of every value. This reduces the number of test cases without losing defect-finding power.

  • Valid class — input the program should accept.
  • Invalid class — input the program should reject with a proper message.

2. Boundary value analysis (BVA)

Defects cluster at the edges of input ranges. BVA tests the value at the boundary, just below it and just above it. For a range a ≤ x ≤ b, test a−1, a, a+1 and b−1, b, b+1.

3. Common example — age field accepts 18 to 60

3.5 Experience-based techniques

Syllabus: Error guessing, Exploratory testing.

Q11State in your own words Error guessing and Exploratory testing. / What do you think about Exploratory testing.

6 marks★★★ 3×

Asked in: 2022 Nov Q1(b) [6] · 2023 May Q2(a) [6, experience-based techniques] · 2025 May Q2(c) [6, exploratory]

1. Error guessing

Definition: The tester uses experience and intuition to guess where the program is likely to fail, then writes tests for those areas. There is no formal model; it depends on the tester's skill.

Typical guesses: empty input, zero, negative numbers, very long strings, special characters, divide by zero, duplicate IDs, wrong date format, network failure, double-click on Submit.

Example: for a “percentage” field, an experienced tester immediately tries 0, 100, 101, −1, abc and a blank value.

Advantages: very fast, needs no documentation, finds unusual defects. Limitation: not repeatable, coverage cannot be measured, depends heavily on the tester.

2. Exploratory testing

Definition: Testing in which learning, test design and test execution happen together. The tester explores the application, designs the next test from what was just learned, and records findings — usually in a time-boxed session.

How it is done (session-based):

  1. Write a charter — what area to explore and why (e.g. “explore the refund flow for partial cancellations”).
  2. Set a time box — typically 60–120 minutes.
  3. Explore, test, note defects and coverage ideas as you go.
  4. Debrief: summarise what was covered, what was found and what remains.

Example: charter “explore coupon codes on checkout”. The tester tries stacking two coupons, expired coupons, a coupon above cart value, back-button after apply, and refresh after apply.

3. Other experience-based techniques (one line each)

  • Checklist-based testing: the tester follows a list of common defect types for that domain.
  • Fault attack: deliberately inject likely faults (null, timeout, bad data) and observe behaviour.
  • Pair testing: two testers explore together and challenge each other's assumptions.

4. Error guessing vs exploratory testing

PointError guessingExploratory testing
BasisPast experience and intuitionSimultaneous learning, design and execution
StructureInformal list of likely errorsCharter + time box + session notes
DocumentationMinimalSession sheet and debrief
Best forQuick checks, regression of known risk areasNew features, unclear requirements, Agile projects

3.6 Levels of testing

Syllabus: Unit, Integration, System, User Acceptance, Sanity/Smoke, Regression, Retest.

Q12What do you mean by unit and integration testing? What are the approaches used in integration testing?

6 marks★★★ 3×

Asked in: 2023 May Q1(b) [6] · 2023 Nov Q2(b) [6] · 2025 Nov Q1(c) [6]

1. Unit testing

Definition: Testing the smallest testable piece of software — a function, method, class or module — in isolation. It is usually white-box and is done by the developer.

  • Driver: dummy code that calls the unit under test and passes input.
  • Stub: dummy code that replaces a module the unit calls.
  • Checks: correct output, boundary values, error handling, code coverage.
  • Tools: JUnit, TestNG, NUnit, PyTest.

2. Integration testing

Definition: Testing groups of modules together to verify that interfaces, data flow and control flow work correctly. It focuses on the “seams” between units, not on individual logic.

Defects found: wrong parameter order, mismatched data types, missing fields, incompatible protocols, shared-state problems.

3. Integration approaches

ApproachHow it worksAdvantageLimitation
Big-bangCombine all modules at once and test.Simple; no extra code.Hard to locate faults; risky.
Top-downStart from the main module; replace lower modules with stubs; add real modules level by level.Early demo of overall flow; tests major control logic first.Needs many stubs; low-level logic tested late.
Bottom-upStart from lowest modules; use drivers to call them; build upward.Low-level logic tested early; fewer stubs.No early view of overall system; needs drivers.
Sandwich / hybridCombine top-down and bottom-up; meet at a middle layer.Balances both; good for large systems.Complex to plan.

Q13How would you explain System Testing and Acceptance Testing?

6 marks★★★ 3×

Asked in: 2022 Nov Q1(c) [6] · 2023 May Q2(c) [6] · 2025 Nov Q1(b) [6]

1. System testing

Definition: Testing the complete, integrated system against the Software Requirements Specification (SRS). It is done in an environment close to production, by an independent test team, after integration testing.

  • Functional: every requirement, use case and business rule.
  • Non-functional: performance, load, security, usability, compatibility, recovery.
  • End-to-end: complete workflows across modules and databases.
  • Entry: all modules integrated and smoke test passed. Exit: all critical defects closed, test summary report signed.

Example: for an e-commerce site, place an order end to end — search → cart → payment gateway → order record → confirmation e-mail — and check performance with 500 users.

2. Acceptance testing

Definition: Testing by the customer or end user to decide whether the system is acceptable for release. It checks business fitness, not technical correctness.

TypeWho does itPurpose
User acceptance (UAT)End users / business teamDoes it support the real business process?
Alpha testingInternal testers at developer siteFind defects before external release.
Beta testingReal users at their own siteGet field feedback from a limited release.
Contract / regulationCustomer or auditorVerify contractual and legal requirements.

Acceptance criteria: all agreed test cases pass, no open critical/high defects, performance targets met, user sign-off obtained.

Q14Identify the importance of Regression Testing & explain it. / Why Regression Testing is important?

6 marks★★ 2×

Asked in: 2022 Nov Q2(b) [6] · 2023 Nov Q2(c) [6]

Definition: Regression testing re-runs a selected set of existing tests after a change — bug fix, new feature, configuration change or environment upgrade — to make sure nothing that worked earlier is broken.

Why it is important

  1. Detects side effects: a small fix in tax calculation may break invoice rounding.
  2. Protects old functionality when new features are added.
  3. Supports continuous delivery: every build can be checked automatically.
  4. Reduces release risk and avoids emergency patches after go-live.
  5. Builds confidence in refactoring and technology upgrades.
  6. Saves cost: finding a regression in testing is far cheaper than finding it in production.

How to select tests

  • Retest-all: run the whole suite — safest but slow.
  • Impact analysis: run tests that touch the changed module and its callers.
  • Priority-based: run critical and high-risk tests first.
  • Automated suite: use Selenium/JUnit for repeatable, fast regression.

Example: after changing the login password rule from 6 to 8 characters, re-run registration, login, forgot-password, session timeout and account-lock tests.

Note: regression testing is not the same as retesting. Retesting checks that the specific defect is fixed; regression checks that other features still work.

3.7 Functional vs non-functional testing

Syllabus: non-functional testing includes performance, memory, scalability, compatibility, security, cookies, session, recovery, installation, ad hoc, risk-based, I18N, L10N and compliance testing.

Q15Differentiate between Functional testing and Non-functional testing. / Illustrate Non-functional testing and explain performance testing with example.

6 marks★★★ 3×

Asked in: 2024 May Q1(c) [6] · 2025 Nov Q2(c) [6] · 2023 May Q1(c) [6, non-functional + performance example]

1. Functional testing

Checks what the system does — whether each function produces the expected output for a given input, as stated in the SRS. It answers: “Does the login accept a valid user?”

Techniques: BVA, ECP, decision table, state transition, use case testing.

2. Non-functional testing

Checks how well the system behaves — speed, load, security, usability, reliability and portability. It answers: “How fast is login with 1,000 users?”

3. Comparison

FocusFunctions and business rulesQuality attributes / behaviour

4. Main non-functional types (name them)

  • Performance: response time and throughput under load.
  • Memory: RAM use, leaks, garbage collection.
  • Scalability: behaviour when users/data grow.
  • Compatibility: OS, browser, device, database versions.
  • Security: authentication, authorisation, confidentiality.
  • Cookies/session: cookie scope, expiry, session timeout, hijack resistance.
  • Recovery: restart after crash and restore data.
  • Installation: install, upgrade, uninstall, rollback.
  • Ad hoc: informal testing without written cases.
  • Risk-based: effort proportional to risk.
  • I18N/L10N: internationalisation and localisation.
  • Compliance: legal, accessibility and industry standards.

5. Performance testing example

Target: the login API must respond in under 2 seconds for 500 concurrent users, with error rate below 1%.

Test: ramp 0 → 500 virtual users over 10 minutes, hold for 30 minutes, measure average and 95th-percentile response time, throughput and errors. If the 95th percentile is 3.8 s, the NFR fails and the bottleneck (usually DB connection pool or CPU) is reported.

Q16How would you explain performance & security testing?

6 marks★★ 2×

Asked in: 2022 Nov Q2(c) [6, performance with example] · 2025 May Q1(b) [6, performance + security]

1. Performance testing

Non-functional testing that measures speed, responsiveness and stability under a given workload. It does not check whether a function is correct; it checks whether it is fast enough and stable enough.

  • Load testing: expected peak load (e.g. 500 users).
  • Stress testing: beyond peak until the system fails; finds the breaking point.
  • Spike testing: sudden jump in users.
  • Endurance/soak: long run to find memory leaks.
  • Volume: large amounts of data.

Metrics: average and 95th-percentile response time, throughput (requests/sec), error rate, CPU/memory usage, hits/sec.

Example: an e-commerce sale page must serve 2,000 users with page load under 3 s. JMeter ramps to 2,000 threads, holds 30 minutes and reports 2.4 s average, 3.6 s p95, 0.4% errors — the target is narrowly missed, so the image CDN is tuned.

2. Security testing

Testing that the system protects confidentiality, integrity and availability (CIA). It tries to find weaknesses an attacker could use.

  • Authentication: weak passwords, brute force, MFA.
  • Authorisation: horizontal/vertical privilege escalation (IDOR).
  • Input validation: SQL injection, XSS, command injection.
  • Session/cookie: fixation, hijacking, missing Secure/HttpOnly flags.
  • Data protection: encryption in transit (TLS) and at rest.
  • Configuration: default accounts, verbose errors, open ports.

Example: log in as a normal user, change the URL /account?id=105 to /account?id=106 and confirm the server returns “403 Forbidden”, not another user's data.

Difference: performance asks “will it stay fast under load?”; security asks “can an attacker break it?”. Both are non-functional and both need a production-like environment.

Q17Explain Risk Based Testing in detail.

6 marks★ 1×

Asked in: 2025 May Q1(c) [6]

Definition: Risk-based testing (RBT) plans and prioritises testing according to risk — the chance that a part of the system will fail and the damage if it does. High-risk areas get more and earlier testing; low-risk areas get less.

1. Risk formula

Risk = Probability of failure × Impact of failure

Probability depends on complexity, new technology, change frequency, developer experience and usage. Impact depends on money, safety, legal exposure, users affected and reputation.

2. Risk matrix

Probability ↓ / Impact →LowMediumHigh
HighMediumHighCritical
MediumLowMediumHigh
LowLowLowMedium

3. Steps

  1. Identify product risks with business users and architects (brainstorming, checklists, past defects).
  2. Estimate probability and impact; assign a risk score.
  3. Rank risks and define a test approach for each level.
  4. Allocate effort: critical → exhaustive tests + reviews; high → broad tests; medium → standard; low → smoke only.
  5. Track and update risks as the project changes; re-prioritise each iteration.

4. Example

In a hospital app, “wrong dosage calculation” has high probability (complex formula) and very high impact (patient safety) → critical risk: code review, unit tests, boundary tests and independent clinical validation. “Colour of the help icon” has low probability and low impact → test once.

Benefits: focuses limited time on what matters, gives early warning, supports release decisions. Limitation: risk scores are estimates and can be biased.

Q18Can you explain compatibility testing & security testing?

6 marks★ 1×

Asked in: 2025 May Q2(b) [6]

1. Compatibility testing

Checks that the software works correctly across different environments — operating systems, browsers, devices, screen sizes, databases, network speeds and versions.

TypeWhat is variedExample
OSWindows, Linux, macOS, Android, iOSSame build on Windows 11 and Ubuntu.
BrowserChrome, Firefox, Edge, SafariCheckout page layout and JS behaviour.
DeviceDesktop, tablet, phone; resolutionsResponsive menu on 360 px width.
DatabaseMySQL, PostgreSQL, OracleSame query returns correct rows.
Network2G/3G/4G/Wi-Fi, high latencyApp does not timeout on slow links.
VersionOld and new client versionsv2.1 client works with v2.3 server.

Approach: build a compatibility matrix, pick the most used and most risky combinations, use virtual machines/emulators/cloud device farms.

2. Security testing

Checks that only authorised users can access data and functions, and that data is protected in transit and at rest. It covers confidentiality, integrity, availability, authentication, authorisation, non-repudiation.

  • Authentication: password policy, account lockout, MFA.
  • Authorisation: role checks, IDOR, privilege escalation.
  • Injection: SQLi, XSS, command injection, unsafe file upload.
  • Session: secure cookie flags, timeout, logout invalidation.
  • Transport/data: TLS, encryption at rest, no secrets in logs.
  • Error handling: no stack traces or database details to users.

Example: a user changes role=user to role=admin in the request; the server must reject it. A search box given ' OR 1=1 -- must return no data and log the attempt.

Tools: OWASP ZAP, Burp Suite, Nessus, SQLMap (only on authorised systems).

Q19What is Cookies testing? Explain Cookies testing with an example.

6 marks★★ 2×

Asked in: 2024 May Q2(b) [6] · 2025 Nov Q2(b) [6]

Definition: A cookie is a small text file stored by the browser on the user's machine. It holds session IDs, preferences or tracking data. Cookie testing checks that cookies are created, stored, sent, expired and deleted correctly and securely.

1. What to test

TestExpected behaviour
CreationCookie is created after login or “remember me”.
Name/valueCorrect name, encoded value, no plain-text password.
Domain and pathCookie sent only to the intended domain and path.
ExpirySession cookie dies on browser close; persistent cookie expires on date.
Secure / HttpOnlySecure = HTTPS only; HttpOnly = JavaScript cannot read it.
TamperingEdited cookie is rejected or re-authenticated.
DeletionLogout deletes the session cookie; “clear cookies” works.
Multiple tabsSame session is shared; no duplicate conflicting cookies.
Disabled cookiesSite shows a clear message or uses a safe fallback.

2. Example — shopping cart

  1. Open the site, add a shirt to the cart. A cookie such as cart_id=8f3a... is created.
  2. Close the browser and reopen. If the cookie is persistent, the cart still shows the shirt.
  3. Open DevTools → Application → Cookies; change cart_id to another value and refresh. The server must not show another user's cart.
  4. Log out. The session cookie must be removed; pressing Back must not restore the logged-in page.
  5. Set the system date beyond the expiry date; the cookie must expire and the cart must reset.

Why it matters: weak cookie handling causes session hijacking, cart leakage, “remember me” security holes and privacy-law violations.

Q20Can you illustrate Adhoc Testing with example.

6 marks★ 1×

Asked in: 2023 Nov Q2(a) [6]

Definition: Ad hoc testing is informal testing without written test cases, plan or documentation. The tester randomly tries inputs and actions to break the software, usually after formal testing is complete.

1. Features

  • No test plan, no test cases, no expected-result document.
  • Depends on tester experience and creativity.
  • Done once, not repeatable; defects are logged informally.
  • Useful as a quick check before release or after a bug fix.

2. Example

A tester opens a food-delivery app and randomly:

  1. adds 20 items, then removes them all;
  2. applies a coupon, goes back, and applies it again;
  3. turns off Wi-Fi during payment;
  4. rotates the phone on the checkout screen;
  5. enters a 200-character address.

The app crashes on step 3 and shows a blank coupon on step 2. Both are logged as defects.

3. Advantages and limitations

  • Advantages: very fast, no preparation cost, finds unusual defects and usability issues.
  • Limitations: cannot measure coverage, not repeatable, may miss core requirements, depends on the tester.

Difference from exploratory testing: exploratory testing is structured and time-boxed with a charter and session notes; ad hoc testing has no structure at all.

Coverage strength (weak → strong)

Statement < Branch < Condition/Decision < Path
  • Statement: every line runs once.
  • Branch: every if/loop takes T and F.
