Syllabus: non-functional testing includes performance, memory, scalability, compatibility, security, cookies, session, recovery, installation, ad hoc, risk-based, I18N, L10N and compliance testing.

Q15Differentiate between Functional testing and Non-functional testing. / Illustrate Non-functional testing and explain performance testing with example.

6 marks★★★ 3×

Asked in: 2024 May Q1(c) [6] · 2025 Nov Q2(c) [6] · 2023 May Q1(c) [6, non-functional + performance example]

In simple words: Functional testing checks what the software does.
Non-functional testing checks how well it does it — speed, safety and ease of use.
A login that works is functional. A login that works in one second for 500 people is also non-functional.

Why we do this

A feature can be correct and still be unusable. People leave when a page is slow, a site is unsafe or an app fails on their phone. We test both sides so the product is correct and pleasant to use at the same time.

Words you need first

  • Functional testing: checking what the software does against its written requirements.
  • Non-functional testing: checking quality attributes such as speed, security and usability.
  • Functional requirement: a statement of what the software must do, such as “the user can reset a password”.
  • Non-functional requirement: a statement of how well it must behave, such as “the page loads in under two seconds”.
  • Black-box testing: testing only through inputs and outputs, without looking at the code.
  • White-box testing: testing with knowledge of the internal code and structure.
  • Performance: how fast and reliably the system responds under a given load.
  • Throughput: how many requests the system completes in a fixed time.
  • Latency: the delay between sending a request and getting the first response.
  • Benchmark: an agreed target number used to judge measured results.
  • Concurrent users: users who use the system at the same moment.

Step-by-step

  1. Read the requirements and mark each one as “what it does” or “how well it must do it”. This separates the two kinds of testing before any test is written.
  2. Design functional tests from user actions: log in, search, pay, cancel. Give an input and state the expected output.
  3. Run the functional tests first. A system must do the right thing before its speed matters.
  4. Write measurable non-functional targets, such as “95% of logins finish in under two seconds with 500 users”.
  5. Run the non-functional tests in a production-like environment and record real numbers.
  6. Compare the numbers with the targets, report the gap and name the likely bottleneck.

What this means: functional testing proves the feature exists; non-functional testing proves the feature is usable at real scale. They answer different questions, and neither one replaces the other.

Performance testing with an example

Performance testing runs after functional testing and is usually done on web applications. It measures response time, throughput and resource use under a given load. It is normally used together with load testing and stress testing.

Performance testing does not give a simple pass or fail. It measures the system against a written benchmark: concurrency, server response time, latency and page render time. The result shows how scalable, reliable and speedy the product is.

Example: the login API must respond in under 2 seconds for 500 concurrent users, with an error rate below 1%. Ramp from 0 to 500 virtual users over 10 minutes, hold for 30 minutes, and record average and 95th-percentile response time. If the 95th percentile is 3.8 s, the target is missed and the bottleneck (often the database connection pool or the CPU) is reported.

What this means: the 95th percentile is the time below which 95 out of 100 requests finish. It is more honest than an average, because a few very slow requests can hide inside an average.

Advantages and limits (book)

  • Functional — advantage: simulates actual system usage; makes no assumptions about the internal structure.
  • Functional — limit: can miss logical errors inside the code; may repeat the same check in several tests.
  • Non-functional — advantage: covers qualities that functional testing cannot; shows whether the app is efficient, reliable and secure.
  • Non-functional — limit: tests must be repeated after every update, which costs time and money.
Real-life analogy: a restaurant dish passes the functional test when it tastes correct. It passes the non-functional test when it reaches the table hot in ten minutes, the plate is clean and the price is fair.
Common confusion: “non-functional” does not mean “not important” or “extra features”. It means the quality attributes of a working feature — speed, security, usability and reliability.

Q16How would you explain performance & security testing?

6 marks★★ 2×

Asked in: 2022 Nov Q2(c) [6, performance with example] · 2025 May Q1(b) [6, performance + security]

In simple words: Performance testing asks “is it fast enough under load?”.
Security testing asks “can an attacker break in?”.
Both test quality, not features, and both need a realistic environment.

Why we do this

A system that is correct in a demo can still collapse on a sale day or leak private data. These two tests protect the two things users notice most: speed and trust.

Words you need first

  • Performance testing: measuring speed, throughput and resource use under a defined load.
  • Security testing: trying to find weaknesses that an attacker could use to read or change data.
  • Load: the number of users or requests the system is handling at one time.
  • Load testing: running the system at the expected busiest load to see whether it stays healthy.
  • Stress testing: pushing beyond the expected load until something breaks, to find the limit.
  • Response time: the time from sending a request to receiving the answer.
  • Throughput: the number of requests completed per second or minute.
  • Vulnerability: a weakness that an attacker can use to damage or enter the system.
  • SQL injection: an attack that puts database commands into an input box to read or change data.
  • Authorization: the rule that decides which user may see or change which data.

Step-by-step

  1. Write a measurable performance target: users, response time, error rate and test duration.
  2. Build a load profile that looks like real traffic, including quiet and peak periods.
  3. Ramp up slowly, hold the peak, then ramp down. This shows both the climb and the recovery.
  4. Record average and 95th-percentile response time, throughput and errors.
  5. Compare the numbers with the target and report the bottleneck. This is why we measure instead of guessing.
  6. For security, list what must be protected: accounts, payments, personal data and admin actions.
  7. Try to break each protection: change an ID in the URL, submit attack strings, call an admin action as a normal user.
  8. Log every attempt and fix the weakness. Retest to prove the fix works.

Performance vs load — the book table

PointPerformance testingLoad testing
Load usedExpected number of users.More than the usual load.
AimGet a baseline and check whether the required response time is met.See whether the application can sustain the increased load or will crash.
MethodMeasure response time with the expected load.Start low, increase gradually to the target load, then ramp down.
GoalSet the performance benchmark.Prove the system handles the expected volume with acceptable speed.

What this means: performance testing sets the baseline; load testing pushes the system to its expected busy limit. A load test is sometimes called volume testing because it checks a large volume of traffic.

Example

An e-commerce sale page must serve 2,000 users with page load under 3 s. JMeter, a load-testing tool, ramps to 2,000 threads, holds for 30 minutes and reports 2.4 s average, 3.6 s p95 and 0.4% errors. The average looks fine, but the p95 misses the target, so the image CDN is tuned.

Performance testing is broad. It includes load, stress, capacity, volume, endurance, spike, scalability and reliability testing.

What this means: always judge against the agreed percentile, not only the average. One slow group of users is still a real group of unhappy customers.

Security testing

Security testing tries to find vulnerabilities and prove that data and resources are protected from intruders. It depends heavily on the tester's expertise. Software security means the software behaves correctly even during a malicious attack. The difference between safety and security is the presence of an intelligent adversary.

Types of security testing (book):

  1. Network security — look for weaknesses in the network infrastructure, its resources and policies.
  2. System software security — check the operating system and database that the application depends on.
  3. Client-side application security — make sure the client or browser cannot be manipulated.
  4. Server-side application security — make sure the server code resists intrusion.

Example: log in as a normal user, change the URL /account?id=105 to /account?id=106, and confirm the server returns “403 Forbidden” instead of another user's data. A search box given ' OR 1=1 -- must return no data and must log the attempt.

Difference in one line: performance asks “will it stay fast under load?”; security asks “can an attacker break it?”. Both are non-functional and both need a production-like environment.

Real-life analogy: a bank must stay open and quick during the morning rush (performance) and must also stop a robber at the door (security). A fast bank with an open vault is not a good bank.
Common confusion: “the site uses HTTPS” does not mean it is secure. HTTPS protects data in transit; it does not stop a user from changing another user's ID or an admin from being tricked into a bad action.

Q19What is Cookies testing? Explain Cookies testing with an example.

6 marks★★ 2×

Asked in: 2024 May Q2(b) [6] · 2025 Nov Q2(b) [6]

In simple words: a cookie is a small note a website asks your browser to keep.
It helps the site remember you between clicks or visits.
Cookie testing checks that the note is created, stored, used and deleted correctly.

Why we do this

Cookies carry login sessions and payment state. If a cookie is created wrongly, expires too late or is deleted at the wrong time, a user can lose a cart, fail a payment or stay logged in on a shared computer.

Words you need first

  • Cookie testing: checking that cookies are created, stored, used and deleted correctly.
  • Cookie: a small file stored by the browser that holds session or preference data for a website.
  • Session: one period of use, from login until logout or browser close.
  • Session cookie: a cookie that lives only while the browser session is open and is deleted when the browser closes.
  • Persistent cookie: a cookie that stays on the machine until a set expiry date.
  • Expiry date: the date and time after which the browser must delete the cookie.
  • Authentication: the process of proving who a user is, usually by login.
  • Payment gateway: the service that handles card payment between the shop and the bank.
  • Client side: the user's own browser and machine, not the company's server.

Step-by-step

  1. Open the site and watch the browser's cookie list. A cookie should appear when the session starts. This proves creation works.
  2. Log in and confirm the cookie carries only the session identifier, not the password. This protects the user if the cookie is seen.
  3. Close the browser completely and reopen the site. A session cookie must be gone, so the user must log in again.
  4. Log in with “Remember me” and check that a persistent cookie with the correct expiry date is stored.
  5. Move the system date past the expiry date. The cookie must expire and the user must log in again.
  6. Clear cookies, or block cookies in the browser, and confirm the site fails safely instead of showing another user's data.
  7. During payment, confirm the payment cookie is active only for that payment and is removed when the transaction ends.

Types of cookies (book)

TypeDefinitionWhat cookie testing checks
Session cookieBecomes active when the browser makes a request and is automatically deleted when the session ends.The cookie exists during the session and disappears when the browser closes.
Persistent cookieStays permanently on the user's machine and has a fixed expiry period, which may be months or a year.The cookie survives a browser restart and expires only at the set date and time.

What this means: the type of cookie decides when it should die. Testing the wrong lifetime is the most common cookie defect.

What to test

  1. Creation: the cookie appears when the site is opened or the user logs in.
  2. Client-side storage: the cookie sits in the browser on the local machine, not on the server.
  3. Session behaviour: a session cookie is active during the session and is deleted when the session ends.
  4. Expiry: a persistent cookie stays until its expiry date and is removed afterwards.
  5. Purpose: cookies for payment or authentication work correctly and do not leak the session.
  6. Browser handling: the site behaves correctly when cookies are cleared or blocked.

Example — login and “remember me”

  1. Open the site and log in. The server sends a session cookie to the browser.
  2. Close the browser completely and reopen the site. The session cookie should be deleted, so the user must log in again.
  3. Log in again and tick “Remember me”. A persistent cookie with an expiry date, say 30 days, is stored.
  4. Close and reopen the browser. The persistent cookie is still there, so the user is remembered.
  5. Change the system date beyond the expiry date. The cookie must expire and the user must log in again.
  6. For a payment gateway, the payment cookie should be active only during payment and must be removed when the transaction ends.
Real-life analogy: a session cookie is a wristband for one party — cut it off when you leave. A persistent cookie is a membership card that stays in your wallet until its printed expiry date.
Common confusion: a cookie is not a virus or a program. It is passive data. The risk is that it can hold a session token, so it must be protected, expire correctly and never store a password.

Q17Explain Risk Based Testing in detail.

6 marks★ 1×

Asked in: 2025 May Q1(c) [6]

In simple words: risk-based testing tests the most dangerous parts first.
“Dangerous” means likely to break and costly if it breaks.
Low-risk parts are tested later or more lightly.

Why we do this

No project has enough time to test everything equally. Risk-based testing spends the testing budget where a failure would hurt the most, so the biggest dangers are found and fixed first.

Words you need first

  • Risk-based testing: an approach that ranks tests by risk so the most dangerous areas are tested first.
  • Risk: the chance of an unwanted event multiplied by how bad the event would be.
  • Probability: how likely the unwanted event is, based on complexity, new technology, change frequency and team experience.
  • Impact: the damage if it happens — money, safety, legal exposure, users affected and reputation.
  • Risk assessment: the activity of identifying risks and scoring their probability and impact.
  • Prioritization: putting the highest-scoring items first in the test plan.
  • Test effort: the amount of review, test design and execution given to an item.
  • Mitigation: an action that reduces either the chance or the impact of a risk.

Step-by-step

  1. List every requirement and ask two questions: how likely is a defect here, and how bad would it be? This turns vague worry into a score.
  2. Score probability and impact, then multiply them to rank the risks. A simple high/medium/low scale is enough for an exam answer.
  3. Put the highest-risk requirements first in the test plan. This is why the process saves time.
  4. Choose stronger techniques for high-risk items: reviews, boundary tests, independent validation.
  5. Run the tests in priority order and record results against each risk.
  6. Review the risk scores as the project changes. A risk that was low can become high after a late change.

Risk formula

Risk = Probability of an undesirable outcome × Impact of that outcome

Probability rises with complexity, new technology, frequent change, an inexperienced team and heavy usage. Impact rises with money loss, safety danger, legal exposure, the number of users affected and reputation damage.

Process of risk-based testing (book)

  1. Identify every requirement and the risks linked to it.
  2. Assess the risks and prioritize the needs.
  3. Prepare and outline tests in that priority order.
  4. Run tests in priority order and apply the agreed approval criteria.

Example — hospital application

RequirementProbabilityImpactPriorityTest effort
Wrong dosage calculationHigh (complex formula)Very high (patient safety)CriticalCode review, unit tests, boundary tests, independent clinical validation
Patient report downloadMediumMediumMediumFunctional and performance tests
Colour of the help iconLowLowLowTest once

What this means: the dosage feature gets several strong techniques because a mistake could kill someone. The icon gets one quick look. The testing budget is limited, but it is placed where it matters.

Advantages (book)

  1. Critical functions are tested first, so overall product quality improves.
  2. Problem areas are found early, so preventive action is possible.
  3. Improved market opportunity and on-time delivery.
  4. Improved service performance.
  5. Testing becomes a better planned and organised activity.

Limitation: risk scores are estimates and can be biased. They must be reviewed and updated as the project changes.

Real-life analogy: a city with a small repair budget fixes the bridge used by school buses before it repaints a park bench. The bridge is not more visible; it is simply more dangerous if it fails.
Common confusion: risk-based testing does not mean ignoring low-risk items. It ranks effort. Low-risk items still get a basic check; they just do not get the deepest tests.

Q18Can you explain compatibility testing & security testing?

6 marks★ 1×

Asked in: 2025 May Q2(b) [6]

In simple words: compatibility testing checks that the software runs on many devices and environments.
Security testing checks that an attacker cannot break in.
One makes the product work on the user's device; the other protects the user's data.

Why we do this

Users open the same app on old phones, new browsers and slow networks. A product that works only on the developer's laptop is not finished. Separately, any product that stores data must resist people who want to steal or change it.

Words you need first

  • Compatibility testing: checking that the software works on the promised devices, systems and networks.
  • Security testing: trying to break the system's protections before an attacker does.
  • Compatibility: the ability of the software to work correctly on different hardware, operating systems, browsers and networks.
  • Operating system (OS): the base software such as Windows, Android, iOS or Ubuntu that runs applications.
  • Backward compatibility: working with older versions of hardware or software.
  • Forward compatibility: working with newer versions that do not exist yet.
  • Minimum configuration: the weakest machine the product promises to support.
  • Vulnerability: a weakness an attacker can use.
  • Authorization: the rule that decides who may access which data or action.
  • SQL injection: an attack that inserts database commands through an input field.

Step-by-step

  1. List the supported platforms: operating systems, browsers, screen sizes, network types and the weakest supported machine.
  2. Pick a representative device or browser for each group. Testing every combination is usually impossible.
  3. Install the same build on each platform and run the key user journeys.
  4. Check layout, input, navigation, downloads and error messages on each platform.
  5. For security, list the assets: accounts, payments, personal data and admin actions.
  6. Try to break each protection: change an ID, submit attack text, call an admin action as a normal user.
  7. Log the result with the exact device, browser and version, so the defect can be reproduced.

1. Compatibility testing

Compatibility testing checks whether the software runs on different hardware, operating systems, applications, network environments and mobile devices. It checks the product on the minimum and maximum configuration.

Why it is important (book):

  1. It ensures complete customer satisfaction.
  2. It provides service across multiple platforms.
  3. It helps find bugs during development.
TypeWhat is verifiedWhy it is easy or hard
Backward compatibilityBehaviour with older versions of hardware or software.More predictable, because the old versions and their changes are known.
Forward compatibilityBehaviour with newer versions.Harder, because future changes are not known yet.
What is variedExample

Hardware / deviceDesktop, tablet and phone with different screen sizes.

What this means: compatibility is a matrix, not a single test. You choose representative rows and columns, then record exactly which combination passed or failed.

2. Security testing

Security testing tries to find vulnerabilities and prove that data and resources are protected from intruders. It depends heavily on expertise and experience. Software security means behaving correctly during a malicious attack; the difference between safety and security is the presence of an intelligent adversary.

Types (book):

  1. Network security — weaknesses in the network infrastructure, resources and policies.
  2. System software security — weaknesses in the operating system and database the app depends on.
  3. Client-side application security — making sure the client or browser cannot be manipulated.
  4. Server-side application security — making sure the server code resists intrusion.

Example: a user changes role=user to role=admin in a request; the server must reject it. A search box given ' OR 1=1 -- must return no data and must log the attempt.

Tools used in practice: OWASP ZAP and Burp Suite, used only on systems you are authorised to test.

Real-life analogy: compatibility is a key that opens every door in the building. Security is the lock that cannot be picked. A key that works everywhere is useful only if the locks still hold.
Common confusion: “it looks fine on my laptop” is not compatibility testing. Compatibility means a defined list of platforms, versions and configurations, each with a recorded result.

Q20Can you illustrate Adhoc Testing with example.

6 marks★ 1×

Asked in: 2023 Nov Q2(a) [6]

In simple words: ad hoc testing is testing with no plan and no written test case.
The tester pokes at the software like a curious user and follows whatever looks suspicious.
It finds odd bugs that scripted tests miss, but it cannot prove coverage.

Why we do this

Scripted tests only check what someone thought to write down. A tester who explores freely can hit strange combinations, interruptions and bad inputs that no plan predicted. Ad hoc testing is a cheap way to find those surprises.

Words you need first

  • Ad hoc testing: unplanned testing with no written test cases, where the tester follows whatever looks suspicious.
  • Ad hoc: done for a particular situation, without a fixed plan.
  • Monkey testing: another name for random ad hoc testing, like a monkey pressing buttons.
  • Black-box testing: testing through inputs and outputs without reading the code.
  • Buddy testing: a tester and a developer test together, usually after unit testing.
  • Pair testing: two testers share one setup; one drives, the other observes and analyses.
  • Traceability: the ability to link a test back to a requirement.
  • Exploratory testing: structured learning and testing at the same time, guided by a charter.

Step-by-step — how an ad hoc session runs

  1. Open the application and pick an area that feels risky, such as payment or sign-up. No script is written.
  2. Try unusual but realistic actions: add many items, go back, repeat a step, rotate the phone, cut the network.
  3. Watch for crashes, blank screens, wrong totals or stuck buttons. These are the signals of a defect.
  4. Write down the exact steps and the result immediately, even though the session was unplanned. This is the only way to reproduce the bug.
  5. Log each defect and tell the team which area was explored, so the gap in scripted coverage is known.

Characteristics (book)

  1. Random testing, done on any part of the application.
  2. It is a black-box technique.
  3. It finds bugs and loopholes that automated testing may miss.
  4. It needs a tester with in-depth knowledge of the system.
  5. It is unplanned and unstructured.
  6. It needs no documentation or formal test-case execution.

Types of ad hoc testing

TypeHow it is done
Buddy testingAt least two people — one tester and one developer. It is done when unit testing is complete and helps both teams understand the change.
Pair testingTwo testers share one setup. One tests while the other observes and analyses; both record what they find.

Example

A tester opens a food-delivery app and randomly tries:

  1. adding 20 items to the cart, then removing them all;
  2. applying a coupon, going back, and applying it again;
  3. turning off Wi-Fi during payment;
  4. rotating the phone on the checkout screen;
  5. entering a 200-character address.

The app crashes during payment with Wi-Fi off and shows a blank coupon after the back-and-reapply step. Both are logged as defects. This is ad hoc testing because there was no plan, no written test case and no expected-result document.

Advantages

  1. It can be done without following a fixed process.
  2. The tester can find more defects than in traditional testing because of the unusual methods used.
  3. When deep testing is needed in a short time, it can still deliver a quality product on schedule.

Disadvantages

  1. It depends on the test engineer's product knowledge, because the tester must know the application flow.
  2. We cannot trace requirements or measure requirement coverage, because there is no traceability matrix or documentation.

Ad hoc vs exploratory testing

PointAd hoc testingExploratory testing
PlanningPerformed without planning or a goal.Performed with a clear plan; structured.

DocumentationNo documentation; steps are not recorded.Notes are recorded, so bugs can be reproduced.

What this means: ad hoc testing is a quick, unrecorded poke. Exploratory testing is a planned investigation with notes. Both are useful, but only exploratory testing leaves evidence you can repeat.

Real-life analogy: a child handed a new toy presses every button, opens every flap and shakes it upside down. That is ad hoc testing — no instructions, no plan, and often the fastest way to find the part that falls off.
Common confusion: ad hoc testing is not the same as exploratory testing. Exploratory testing has a charter, a time box and notes; ad hoc testing has none of these.

Q12What do you mean by unit and integration testing? What are the approaches used in integration testing?

6 marks★★★ 3×

Asked in: 2023 May Q1(b) [6] · 2023 Nov Q2(b) [6] · 2025 Nov Q1(c) [6]

In simple words: unit testing checks one small piece of code on its own.
Integration testing checks that the pieces work together.
Unit testing finds a broken brick; integration testing finds a wall that does not fit.

Why we do this

A function can pass its own test and still fail when it receives real data from another function. Testing units first makes bugs easy to locate. Testing the joins afterwards catches the misunderstandings between modules.

Words you need first

  • Unit testing: testing one small piece of code on its own, before it is joined to anything else.
  • Integration testing: testing several tested units together to check the joins between them.
  • Unit: the smallest testable piece of software, usually one function, class or method.
  • Integration: joining tested units into a larger group and testing the group.
  • Interface: the agreed way two modules pass data or call each other.
  • Use case: one complete task a user performs with the system, from start to result.
  • Stub: a fake lower-level module used when the real one is not ready.
  • Driver: a small fake caller used to run a low-level module that has no real caller yet.
  • Big-bang integration: joining all modules at once and testing the whole group.
  • Top-down: starting from the main module and adding lower modules one level at a time.
  • Bottom-up: starting from the lowest modules and building upward.
  • Sandwich (hybrid): combining top-down and bottom-up so the two meet in the middle.

Step-by-step

  1. Take one unit and test it alone with clear inputs and expected outputs. This proves the unit before it is mixed with others.
  2. Choose an integration order: big-bang, top-down, bottom-up or sandwich. The order decides which risks you see first.
  3. Add the fake helpers the order needs — stubs for missing lower modules, drivers for missing callers.
  4. Test the interfaces: data types, order of calls, error values and empty inputs. Most integration bugs live here.
  5. Run functional tests for the use cases the group must support.
  6. Run structural and performance tests on the joined group.
  7. Record the tests and defects, then repeat steps 1 to 7 until the whole system is integrated.

1. Unit testing

A unit is the smallest testable piece of software. Unit testing checks each unit separately and confirms that it does what it was designed to do. It is the first level of testing, done before integration, usually by the developers themselves.

Advantages (book):

  1. Code becomes more reusable.
  2. Confidence rises when code is changed or maintained.
  3. Development becomes faster.
  4. Debugging is easier.
  5. A defect found here costs less to fix than at a higher level.

2. Integration testing

Integration testing combines individual modules and tests them as a group. It runs after unit testing and before validation testing. The system is viewed as a set of subsystems, and the order in which they are selected decides the integration strategy.

Example — three-layer call hierarchy (Fig. 3.7.2):

A Layer I / | \ B C D Layer II / \ | E F G Layer III

What this means: A calls B, C and D; B calls E and F; D calls G. Top-down starts at A and uses stubs below. Bottom-up starts at E, F and G and uses a driver above.

3. Steps in integration testing (book)

  1. Pick a component using the chosen strategy and unit test all its classes.
  2. Join the component and add the needed drivers or stubs so the test can run.
  3. Do functional testing: exercise all use cases that touch this component.
  4. Do structural testing: exercise the internal paths of the component.
  5. Run performance tests on the joined group.
  6. Record test cases and results.
  7. Repeat until the full system is tested.

Primary goal: find errors in the current component configuration. Integration testing is done by developers or testers on the programmer's workbench, and its reason is to discover inconsistencies in the combination of units.

Common confusion: integration testing is not system testing. Integration checks the joins between modules; system testing checks the complete product against the requirements.

Q13How would you explain System Testing and Acceptance Testing?

6 marks★★★ 3×

Asked in: 2022 Nov Q1(c) [6] · 2023 May Q2(c) [6] · 2025 Nov Q1(b) [6]

In simple words: system testing checks the complete product against its written requirements.
Acceptance testing checks whether the customer will accept it.
One is done by an independent test team; the other ends with a customer decision.

Why we do this

A system can pass every module test and still fail as a product. System testing checks the whole behaviour. Acceptance testing protects the customer and the contract: it decides whether the product is good enough to go live.

Words you need first

  • System testing: testing the fully integrated product against the specified requirements.
  • Acceptance testing: formal testing that decides whether the product meets the agreed acceptance criteria.
  • Acceptance criteria: the written conditions the customer will use to accept or reject the product.
  • UAT (user acceptance testing): acceptance testing done by the customer or end users.
  • Business acceptance testing: testing by the supplier's own organisation to check that the product will pass UAT.
  • UI (user interface): the screens, buttons and messages the user sees and uses.
  • SRS: the Software Requirements Specification, the written statement of what the system must do.
  • Sign-off: the customer's formal written approval.
  • Cut-over: the moment the old system is replaced by the new one in live operation.
  • Interoperability: the ability of two systems to exchange data and work together.
  • Independent tester: a tester who did not write the code and reports outside the development team.

Step-by-step

  1. Take the approved requirements and turn each one into a system test with a clear expected result.
  2. Run the tests on the fully integrated system in a production-like environment.
  3. Include non-functional checks: performance, security, portability, safety and interoperability.
  4. Log every difference between the implementation and the specification.
  5. Fix the defects and rerun. System testing ends when the exit criteria are met.
  6. Hand the product to the customer for acceptance testing against the acceptance criteria.
  7. Record the customer's decision: accept, accept with conditions, or reject. This is the formal sign-off.

1. System testing

Definition: system testing tests an integrated system to verify that it meets the specified requirements. It checks the overall interaction of components and finds differences between the implementation and the specification.

It runs after integration testing and before acceptance testing, normally with independent testers. It covers non-functional requirements such as performance, portability, security, safety and interoperability. It also finds new faults introduced while old faults were being fixed.

Example: for an e-commerce site, place an order end to end — search, cart, payment gateway, order record, confirmation e-mail — and check performance, security and portability.

2. Acceptance testing

Definition: acceptance testing is a formal activity that decides whether a system satisfies its acceptance criteria. It has two categories: user acceptance testing and business acceptance testing.

TypeWho does itPurpose
User acceptance testing (UAT)The customerEnsure the system satisfies the contractual acceptance criteria before sign-off.

Acceptance testing can happen at the client's office or the developer's office. Its three objectives are:

  1. Confirm that the system meets the agreed criteria.
  2. Identify and resolve any differences.
  3. Decide whether the system is ready for cut-over to live operation.

Acceptance tests are usually written by business customers in business language. They are high-level tests of complete user stories. Business customers, analysts, testers and developers create them together, but the business customers or product owners own them. They include both business logic checks and UI checks.

Real-life analogy: system testing is the factory's full inspection of a new car — engine, brakes, lights, safety. Acceptance testing is the customer's test drive and signature on the delivery form.
Common confusion: acceptance testing is not just “testing at the end”. It is a formal decision against agreed criteria, and business acceptance testing is done by the supplier to predict the customer's UAT — not by the customer.

Q14Identify the importance of Regression Testing & explain it. / Why Regression Testing is important?

6 marks★★ 2×

Asked in: 2022 Nov Q2(b) [6] · 2023 Nov Q2(c) [6]

In simple words: regression testing re-runs old tests after a change.
It checks that the new code did not break something that already worked.
Retesting checks the fix itself; regression checks everything around it.

Why we do this

A small fix can quietly break a feature that nobody touched. Regression testing is the safety net that catches these side effects before users do. It protects the quality of every release.

Words you need first

  • Regression: a new defect in something that used to work, caused by a change elsewhere.
  • Regression testing: re-running existing tests after a change to confirm old behaviour still works.
  • Retesting: running the specific failed test again after a fix to confirm that defect is closed.
  • Maintenance phase: the period after release when the software is fixed and improved.
  • Side effect: an unintended change in another part of the program.
  • Test suite: a collected set of test cases that are run together.
  • Automation: using a tool to run tests and compare results without manual effort.

Step-by-step

  1. Identify what changed: a fixed defect, a new feature or an updated rule.
  2. Select existing tests that cover the changed area and everything that depends on it.
  3. Check that the fix has its own test. Regression testing itself reuses existing tests rather than inventing new ones.
  4. Run the selected suite on the new build.
  5. Compare the results with the recorded results from the previous build.
  6. Investigate every new failure. A failure in an untouched area is a regression.
  7. Automate the suite where possible, because it will run again after every change.

1. Importance of regression testing

  1. Checks the modified code: the new or changed code still meets its requirements.
  2. Protects the unmodified code: maintenance has not damaged code that worked before.
  3. Catches side effects: a fix or feature may create an error elsewhere.
  4. Acts as quality control: it is a planned check during maintenance, not an optional extra.
  5. Finds inadvertent errors: adding source code can introduce faults that were not there before.
  6. Supports new releases: a new version performs the same functions as the old one.
  7. Saves cost and time: existing tests are reused, and defects are caught before release.

2. Where it is performed

Regression testing can run at any level — unit, integration, system or acceptance — but it matters most during system testing. During regression testing, no new test cases are created for the old behaviour; previously created tests are re-executed.

3. What is needed

  • Regression test models that define the strategy, test cases and coverage criteria.
  • A selected set of existing tests covering the changed area and the areas that depend on it.
  • Records of earlier results so the new results can be compared.
  • Automation where possible, because the same tests run again and again.

4. Example

After changing the login password rule from 6 to 8 characters, re-run the existing registration, login, forgot-password, session-timeout and account-lock tests. If the forgot-password test now fails, the change has caused a regression.

What this means: the password change was small, but its effects reached five other features. Regression testing follows those connections instead of testing only the changed line.

Real-life analogy: after a plumber replaces one pipe, you turn on every tap in the house. The repaired pipe is the retest; the other taps are the regression test.
Common confusion: regression testing is not the same as retesting. Retesting proves the reported defect is fixed. Regression proves the fix did not break other features.

In simple words: static testing checks documents and code without running them.
People read, question and inspect the work to find mistakes early.
Because nothing is executed, it can start before a single line of code works.

Why we do this

The earlier a mistake is found, the cheaper it is to fix. A wrong sentence in a requirements document costs minutes to correct. The same mistake found after release can cost a rebuild. Static testing finds those mistakes while they are still cheap.

Words you need first

  • Static testing: checking software work products by reading and analysis, without executing the code.

  2. Code analyzers — a tool checks for type errors, memory leaks and syntax errors.
  3. Compiling — the source compiler or interpreter checks the code.
  4. Modelling techniques — requirements are modelled to check that they are correct and complete.

Static testing can find bugs before compilation. The earlier a bug is found, the cheaper it is to fix.

Q5Explain the following test case design techniques: (i) Informal Reviews (ii) Walkthroughs (iii) Inspection.

6 marks★ 1×

Asked in: 2024 May Q2(a) [6] — technical review is also part of the syllabus list

In simple words: these are three human checks, from casual to formal.
An informal review is a colleague reading your work.
A walkthrough is you explaining it to the team.
An inspection is a formal team check with a checklist and records.

Why we do this

People spot different mistakes when they read with a purpose. A quick second pair of eyes catches obvious errors. A formal inspection with roles and checklists catches deeper defects and gives numbers the organisation can track.

Words you need first

  • Informal review: a simple, undocumented review by one colleague.
  • Walkthrough: a semi-formal session where the author leads others through the product.
  • Inspection: a formal review with defined roles, preparation, checklists and metrics.
  • Moderator: the neutral person who runs an inspection and keeps it on track.
  • Checklist: a list of common defect types that reviewers must check.
  • CAR form: a Corrective Action Request form used to record an issue found in a walkthrough.
  • Traceability: the ability to follow a requirement from the customer statement to its design, code and tests.
  • Metrics: measured numbers, such as defects found per page or per hour.
  • Rework: the effort spent correcting a defect.
  • Producer: the person who created the work product; in a walkthrough, the author who leads the session.

Step-by-step — a formal inspection

  1. Planning: choose the document, the team and the checklist. This keeps the inspection focused.
  2. Overview: the author explains the product and its context, so reviewers are not guessing.
  3. Preparation: each reviewer reads alone and records possible defects. This is where most defects are actually found.
  4. Meeting: the team discusses each issue and agrees whether it is a defect. The moderator prevents personal criticism.
  5. Rework: the author fixes the agreed defects.
  6. Follow-up: the moderator checks that every fix was made. Without this step, defects silently survive.

1. Informal review

Informal reviews happen at various times in the early stages of a document. A two-person team can do it: the author asks a colleague to review a document or code. The pair looks for defects and discusses them. The goal is to help the author and improve the document. Informal reviews take many shapes, but they share one trait — they are not documented. The material may be as casual as a printed listing or handwritten notes.

2. Walkthrough

A walkthrough is a semi-formal review. A group reviews the product, mostly without preparation. A requirements traceability review is a walkthrough: it follows a requirement from the customer statement to the test procedure, and issues are recorded on CAR forms.

In a walkthrough, the designer or programmer leads the development team and other interested people through the product. Participants ask questions and comment on errors, standard violations and other problems. The producer is the review leader, so the value of a walkthrough depends on the producer's real goal. Walkthroughs work best at the source-code level and on small work products.

3. Inspection

Software inspection is a disciplined engineering practice for finding and correcting defects before they reach the field. It is more formal than a walkthrough and collects metrics about the process. A walkthrough is a more informal version of an inspection.

Inspections reduce variation and tighten process control. They support three management tasks: planning, measurement and control. They collect quality data at fixed points, giving feedback to developers and feed-forward to later steps. Michael Fagan recommended inspections on detailed design, cleanly compiled code and completion of unit test.

A formal inspection has at least a designated moderator, the author and one peer inspector. Walkthroughs usually have no moderator and are often led by the author.

Steps of inspection: planning → overview → preparation → meeting → rework → follow-up.

4. Walkthrough vs inspection

PointWalkthroughInspection
FocusImprove the product.Find defects.
ActivitiesFind defects; examine alternatives; forum for learning; discussion.Find defects; only defect explanation allowed; learning through defects.
ProcessInformal.Formal.
QualityVariable; personalities can change the outcome.Repeatable with a fixed process.

What this means: a walkthrough can turn into a design discussion. An inspection stays on task: find defects, record them, fix them. That discipline is why inspections give repeatable numbers.

5. Technical review (extra point)

A technical review examines the technical approach used in development. It is a peer review, less formal than an audit or inspection. The product is examined and the defects found are mainly technical. There is no management participation, and a full report lists the issues. Its goals are to use technical concepts correctly, assess alternatives, keep their use consistent and inform participants about the technical content.

Real-life analogy: an informal review is a friend reading your letter. A walkthrough is you reading it aloud to the team. An inspection is a proofreading team with a checklist, a chairperson and a signed record of every correction.
Common confusion: an inspection is not “a longer walkthrough”. It has different roles, mandatory preparation and recorded metrics. The moderator, not the author, runs the meeting.

In simple words: experience-based testing uses the tester's past knowledge instead of a written specification.
Error guessing means “I have seen this break before, so I will test it first”.
Exploratory testing means learning the product while testing it, with a goal and notes.

Why we do this

Specifications are sometimes missing, outdated or too vague to design tests from. Experienced testers still know where software usually breaks. These techniques turn that knowledge into useful tests when formal methods have nothing to work from.

Words you need first

  • Experience-based testing: testing that relies on the tester's knowledge of similar products and past defects.
  • Error guessing: predicting the parts most likely to fail and testing them first.
  • Intuition: a feeling based on experience rather than a written rule.
  • Exploratory testing: learning, designing and running tests at the same time, guided by a goal.
  • Charter: a short written goal for an exploratory session, such as “test refunds for cancelled orders”.
  • Agile: a development style with short repeated cycles and frequent feedback.
  • Defect history: the record of what failed in this product or similar products before.

Step-by-step

  1. Check whether the specification is missing, weak or out of date. If it is usable, use formal techniques first and add these on top.
  2. List the areas with a history of defects: discounts, dates, payments, imports, permissions.
  3. For error guessing, write a short test for each likely mistake, such as an empty discount code or a negative quantity.
  4. Run the tests and record what happens. A guess that finds nothing still tells you the area is healthy.
  5. For exploratory testing, write a charter and a time box, then explore freely within that goal.
  6. Take notes as you go: what you tried, what you saw and what you did not finish.
  7. Turn the notes into defects and into future test ideas, so the next session starts smarter.

When experience-based testing is needed (book)

  1. Requirements and specifications are not available.
  2. The team has limited knowledge of the product.
  3. The specification is inadequate.
  4. There is very little time for testing.

1. Error guessing

In error guessing, the tester uses experience to guess which areas are prone to error. It relies on skill, intuition and experience to anticipate defects that formal techniques may not catch. Its success depends heavily on the tester's skill.

Every application has a history shaped by its people, features and integration points. An experienced tester knows the kinds of errors that occurred before.

Book's example: in an e-commerce application, the discount logic has often failed when a random discount code is applied. The tester tries combinations of valid and invalid codes and checks that the logic still works. That insight comes from experience with the application's history.

2. Exploratory testing

Exploratory testing is both a technique and a progressive learning approach: it aims for maximum testing with minimal planning. The tester studies the product and uses skill and experience to build a strategy and test cases while testing.

It is about exploring an application to find and document potential bugs. Testers investigate and discover rather than follow a fixed script.

  • It fits Agile work because it supports discovering and understanding the code under test.
  • It helps when new testers join, because they bring fresh knowledge and perspective.
  • It is most useful when specifications are inadequate and time is severely limited.

3.1 White box testing (and grey box testing)

Syllabus: White Box Testing, Black Box Testing, Grey Box Testing.

Q1Explain White box testing and Grey box testing in detail.

6 marks★★ 2×

Asked in: 2024 May Q1(a) [6] · 2025 May Q1(a) [6, white box only]

In simple words: white box testing looks inside the code.
Grey box testing looks at part of the inside, plus the product's behaviour.
Black box testing looks only at inputs and outputs.

Why we do this

Some defects hide in the logic: a branch that never runs, a loop that never ends, a value that is never initialised. You cannot see those from the outside. White box testing checks the structure. Grey box testing gives a useful middle ground when the tester has some internal knowledge but not full access.

Words you need first

  • White box testing: testing based on the internal logic and structure of the code.
  • Grey box testing: testing with partial knowledge of the code, architecture or internal states.
  • Black box testing: testing only through inputs and outputs, with no knowledge of the code.
  • Source code: the human-written instructions that make up the program.
  • Control flow: the order in which the program's statements and branches execute.
  • Branch: one possible path after a decision such as an if or a loop.
  • Basis path: a path through the code that adds at least one new edge to the flow graph.
  • Data flow: how data is created, changed and used as it moves through the program.
  • Loop testing: testing a loop at zero, one, typical and maximum iterations.
  • GUI: the graphical user interface — the screens, buttons and menus a user clicks.
  • Orthogonal array: a compact table that tests many input combinations without testing every combination.
  • Matrix testing: a table of all variables and their values, used to see which combinations matter.

Step-by-step

  1. Read the code and draw a flow graph: boxes for statements, arrows for control flow.
  2. Choose a white-box technique: statement, branch, basis path, data flow or loop coverage.
  3. Design inputs that force the chosen paths or branches to run. The code structure decides the tests.
  4. Run the tests and record which lines and branches were actually covered.
  5. For grey box, add what you know about the architecture, database or internal states, then test behaviour through the interface.
  6. Report uncovered code and untested states. Coverage numbers show what is still unknown.

1. White box testing — definition

White box testing builds on the internals of a software component. It is a detailed study of the internal logic and structure of the code, so the tester needs full knowledge of the source code.

The book defines it as a test case design method that uses the control structure of the procedural design to derive test cases. It can uncover implementation errors such as poor key management, and it applies at unit, integration and system levels.

2. White box techniques

  • Control flow testing
  • Branch testing
  • Basis path testing
  • Data flow testing
  • Loop testing

3. Advantages of white box testing

  1. Can be done by the development team.
  2. Does not need a finished GUI.
  3. Highly systematic and easy to reproduce.
  4. Thorough in principle — it can target every path, though very large programs make that impractical.
  5. Can uncover errors early in development.

4. Disadvantages of white box testing

  1. It takes developers' time.
  2. Code changes can invalidate test cases.
  3. It is hard to separate the program from the test environment.

5. Grey box testing — definition

Grey box testing combines black box and white box testing. The grey box tester has some knowledge of the code, but not complete knowledge. The tester does not have to design every test case from scratch: test cases come from algorithms that use internal states, program behaviour and architecture knowledge, and the tester runs and interprets them.

Purpose: improve product quality by covering functional and non-functional testing together, which saves time and avoids a long separate testing cycle.

6. Grey box techniques

  • Regression testing — checks whether changes or fixes broke existing components.
  • Orthogonal array testing — used when inputs are many or complex; reduces the number of tests while keeping good coverage.
  • Pattern testing — studies past defects to find patterns that lead to new defects.

Why we do this

Users care about what the software does, not how it is written. Black box testing checks the product from the user's side. It also lets testers who cannot program join the testing effort.

Words you need first

  • Black box testing: testing behaviour through inputs and outputs without seeing the internal code.
  • Functional testing: another name for black box testing; it checks what the software does.
  • Input: the data or action given to the software.
  • Expected output: the result the specification says should happen.

  • Specification: the written description of required behaviour.
  • Test case: a set of inputs, steps and expected results used to check one behaviour.

  2. Write the input, the steps and the expected output. This makes the test repeatable.
  3. Put the component in the required starting state.

Black box testing looks at the available inputs and the expected outputs for each input. It is also called functional testing. You define the starting state, the input and the expected output, set the state, give the input, observe the output and compare it with the expected result (Fig. 3.1.2).

No knowledge of the code is needed. Test cases come from the specification; the tester ignores the internals and focuses on the relationship between inputs and outputs.

2. Example — search engine

You type a search term and press “Search”. Results appear. You do not see the ranking algorithm or the database query; you only give an input and receive an output. That is black box testing.

3. Advantages

  2. Test cases can be written quickly.
  3. Efficient for a large codebase.
  4. The tester's view is simple: input, output, compare.

4. Disadvantages

  2. Without a clear specification, test cases are hard to design.
  3. Testing can be inefficient because some tests repeat the same path.

Q10Discuss Boundary Value Analysis and Equivalence Class Partition.

6 marks★★ 2×

Asked in: 2024 May Q1(b) [6] · 2025 Nov Q2(a) [6]

In simple words: ECP puts inputs that behave the same into one group, then tests one value from each group.
BVA tests the edges of those groups, where programmers make most mistakes.
ECP cuts the number of tests; BVA makes each edge safe.

Why we do this

You cannot test every possible input. A field that accepts 18 to 60 has millions of numbers, but only three meaningful groups: below 18, 18 to 60, and above 60. ECP finds those groups. BVA then checks the exact edges, because “17”, “18”, “60” and “61” are where off-by-one bugs live.

Words you need first

  • ECP (equivalence class partitioning): dividing inputs into groups that should behave the same, then testing one value from each group.
  • Equivalence class: a set of inputs that the software should treat the same way and answer the same way.
  • Valid class: a group of inputs the software should accept.
  • Invalid class: a group of inputs the software should reject with an error.
  • BVA (boundary value analysis): testing values on, just below and just above the edge of each class.
  • Boundary value: the smallest or largest value allowed for an input, internal value or output.
  • Off-by-one error: a mistake where a limit is one too high or one too low.
  • Input domain: the full set of values an input can take.
  • maxint: the largest integer the system can store before overflow.

Step-by-step

  1. Read each input rule and list the groups: too small, allowed, too large; wrong type; missing value.
  2. Mark each group valid or invalid. This tells you what the software should do.
  3. Pick one representative value from each group. This is ECP, and it keeps the test count small.
  4. For every edge, add boundary − 1, boundary, boundary + 1. This is BVA.
  5. Write the expected result for each value before running the test.
  6. Run the tests and compare. A rejected value that should be accepted, or the reverse, is a defect.

1. Equivalence class partitioning (ECP)

ECP reduces the number of test cases. We do not want several tests that check the same aspect of the program. ECP divides the input domain into classes. Inside one class, the module should treat every value the same and produce the same answer. Test cases are chosen so that inputs fall inside these classes.

Q7Can you explain statement coverage testing & branch coverage testing?

6 marks★ 1×

Asked in: 2023 May Q2(b) [6]

In simple words: statement coverage asks “did every line run?”.
Branch coverage asks “did every if take both the true and false path?”.
Branch coverage is stronger, because running a line does not prove both decisions were tested.

Why we do this

Code that never runs during testing is code you know nothing about. Coverage measures how much of the code the tests actually reached. It turns “we tested it” into a number that a team can check and improve.

Words you need first

  • Statement coverage: the percentage of source statements executed by the tests.
  • Branch coverage: the percentage of decision branches executed at least once; also called decision coverage.
  • Branch: one possible path after a decision, such as the true or false side of an if.
  • Decision: a condition in the code that chooses between paths.
  • Flow graph: a diagram of code as nodes and arrows, used to see paths.
  • Edge: an arrow in the flow graph that represents a possible transfer of control.
  • Coverage percentage: (items executed ÷ total items) × 100.

Step-by-step

  1. List the statements and decisions in the code. A flow graph makes the branches visible.
  2. Write one test that runs the main path, then check which statements it covered.
  3. Add tests for the statements or branches still not covered.
  4. For branch coverage, make sure every decision takes both true and false at least once.
  5. Calculate the percentage and record which items remain uncovered.
  6. Decide whether the remaining items are unreachable, defensive code or a real gap.

1. Statement coverage testing

Statement coverage is a white box technique. It requires every statement to run at least once. It measures how many source statements the tests executed.

It is a good measure of line-by-line testing, but it is not a good measure of control flow. One node can be reached from several other nodes, but if the aim is only to touch every statement, those different conditions may never be checked.

Statement coverage (%) = (Number of statements executed ÷ Total number of statements) × 100

Statement coverage is used as part of code validation during the build and development phases.

2. Branch coverage testing

Branch coverage requires that, for each branch in the program — every if and every loop — each branch runs at least once. A branch is one of the possible paths the code can take after a decision.

Branch coverage is also called decision coverage. It aims to test every branch or edge at least once. It solves a problem that statement coverage leaves open: a decision can be reached without both outcomes being tested.

Branch coverage confirms that every branch is reached and that no branch causes abnormal behaviour. A low branch coverage means some scenarios were never tested, and those scenarios may hold defects that appear only in production.

3. Worked example

1  read a, b

4  else

4. Why branch coverage is stronger

The book gives the example of an if ... then statement with no else. Running it when the condition is true tests only one of two branches in the flow graph. Branch testing makes sure every branch is executed.

Pros of branch coverage (book):

  1. Confirms that all branches in the code are reached.
  2. Confirms that no branch causes irregular behaviour.
  3. Fixes the weakness of statement coverage testing.
Real-life analogy: statement coverage is visiting every room in a building. Branch coverage is opening both doors at every fork in the corridor. You can visit every room and still never open one of the doors.
Common confusion: 100% statement coverage does not guarantee 100% branch coverage. A one-line if with no else can be fully covered by a single true test, while the false branch never runs.

Q8Can you explain path coverage testing & conditional coverage testing.

6 marks★ 1×

Asked in: 2022 Nov Q2(a) [6]

In simple words: path coverage runs every route from the start of the program to the end.
Conditional coverage makes each small condition inside a decision take both true and false.
Path coverage is the strongest but can explode; condition coverage is precise but can miss the overall decision.

Why we do this

Some bugs appear only on a particular combination of decisions. Path coverage tries to run every route. Other bugs hide inside one condition of a compound decision, so condition coverage checks each part separately. Together they reveal gaps that branch coverage alone can miss.

Words you need first

  • Path coverage: testing every route through the program from entry to exit at least once.
  • Path: one complete route through the program from entry to exit.
  • Independent path: a path that adds at least one new edge to the flow graph.
  • Flow graph: a diagram of code as nodes and directed edges.
  • Cyclomatic complexity: a number that estimates how many independent paths a program has.
  • Conditional coverage: testing each individual Boolean condition as both true and false.
  • Decision coverage: testing each whole decision as both true and false.
  • Boolean condition: a part of a decision that is either true or false, such as a > 0.
  • Combination: one specific set of true and false values across all conditions in a decision.

Step-by-step

  1. Draw the flow graph and find the decisions and loops.
  2. Compute cyclomatic complexity to estimate the number of independent paths. This stops you from chasing infinite loop paths.
  3. Choose test inputs that run each independent path at least once, including zero, one and many loop iterations.
  4. For each compound decision, list its individual conditions.
  5. Write tests so each condition is true once and false once.
  6. Check the whole decision too. Condition coverage alone can leave the decision stuck on one outcome.

1. Path coverage testing

Path coverage tests the different paths from entry to exit. A path is a combination of decisions taken in sequence. The number of paths can be enormous — a loop can run forever — so cyclomatic complexity is used to find and avoid redundant test cases.

In this technique, every path runs at least once. All control paths are taken, including loops run zero, one and multiple (ideally maximum) times. Test cases come from the logical complexity measure of the design, and every statement is guaranteed to run at least once.

A flow graph, cyclomatic complexity and graph metrics help find the basis paths. The aim is for each independent path to run at least once. An independent path crosses at least one new edge, which means it exercises one or more new conditions. Both the true and false branches of every condition must run.

2. Limitation of path coverage (book's warning)

  • Testing all paths does not mean every bug will be found.
  • Many bugs happen because programmers forgot to include some processing, so there is no path to execute.
  • Some bugs depend on the order in which code segments run. If a, b and c run as <a, b, c> the program may work, but as <a, c, b> it may fail. Testing every order and every path is practically impossible.

3. Conditional coverage testing

Condition coverage tests individual conditions with different Boolean inputs. Each condition takes true and false at least once. The whole decision's outcome matters only for checking the conditions; the combinations of conditions are not the focus.

Q9Discuss Loop coverage testing and types of it in detail.

6 marks★ 1×

Asked in: 2024 May Q2(c) [6]

In simple words: loop coverage tests a loop at its edges.
Run it zero times, once, a normal number of times, the maximum, and one beyond the maximum.
Most loop bugs are off-by-one, missing updates or overflow at the last iteration.

Why we do this

Loops repeat work, so a small mistake repeats many times. A loop that runs one time too many can read past the end of an array. A loop that never runs can leave a total at zero. Testing the edges exposes both.

Words you need first

  • Loop testing: testing a loop at its minimum, typical and maximum number of repetitions, plus one beyond each edge.
  • Loop: code that repeats a block while a condition holds or for a set number of items.
  • Iteration: one complete run of the loop body.
  • Simple loop: a loop whose body contains no other loop.
  • Nested loop: a loop placed inside the body of another loop.
  • Concatenated loop: loops that follow one another, where the next starts after the previous ends.
  • Off-by-one error: a loop that runs one too few or one too many times.
  • Initialisation: setting a variable to its starting value before the loop.
  • Overflow: a value growing beyond the space or range reserved for it.
  • Array: a numbered list of values stored together under one name.

Step-by-step

  1. Find every loop and classify it as simple, nested or concatenated.
  2. For a simple loop, run it at minimum − 1, minimum, typical, maximum and maximum + 1 iterations.
  3. For a nested loop, test the inner loop at its edges while the outer loop is at its minimum. Then test the outer edges.
  4. For concatenated loops, test each loop alone, then test the hand-off where one ends and the next begins.
  5. Check the values before the loop, inside the loop and after it. This catches missing initialisation and missing updates.
  6. Confirm that an out-of-range count is rejected safely instead of crashing.

1. Why loop testing is performed (book's reasons)

  1. It helps resolve loop repetition observation.
  2. It can estimate conditions in performance and facility.
  3. Uninitialised variables in the loop can be detected.
  4. It helps classify loop starting issues.
  5. Testing can return the loop to routine issues.
  6. Loop testing can reveal production or capability bottlenecks.
  7. It helps classify the loop's beginning queries.

TypeDefinition (book)How to test
Simple loopA loop whose body contains no other loop.Run at minimum, minimum − 1, typical, maximum and maximum + 1 iterations.
Nested loopLoops combined so that each is inside the body of the next.Test the inner loop at minimum, typical and maximum while the outer loop is at minimum; then test the outer boundaries.
Concatenated loopLoops where each follows the next in code; the next begins after the previous ends.Test each loop independently, then test the boundary between the first ending and the second starting.

What this means: nested loops multiply the work, so test the inner loop first while the outer loop is held still. Otherwise you cannot tell which loop caused the failure.

4. Example

sum = 0
for i = 1 to n do
    sum = sum + marks[i]
print sum

Test with n = 0 (fewer than the minimum, if the loop expects at least one mark), n = 1 (minimum), n = 50 (typical), n = 100 (maximum) and n = 101 (above maximum — the program should reject it, not crash).

Benefits: catches off-by-one, wrong initialisation, missing update and array-overflow defects. Limitation: it does not test the logic inside the loop body — combine it with branch and path coverage.

Real-life analogy: a revolving door must be tested with no one, one person, a normal queue, a full crowd and one person too many. The last case is where it jams.
Common confusion: loop testing is not just “run the loop many times”. It tests below the minimum and above the maximum as well, because those are the cases that crash.

Coverage strength (weak → strong)

Statement < Branch < Condition/Decision < Path
  • Statement: every line runs once.
  • Branch: every if/loop takes T and F.
  • Condition: every atomic condition takes T and F.
  • Path: every independent entry→exit path.
  • Loop: 0, 1, 2, typical, max, max+1.
  • Cyclomatic: V(G)=E−N+2.
