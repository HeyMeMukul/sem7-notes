6.1 Multithreaded fundamentals

Q1With respect to multithreaded algorithms explain: analyzing multithreaded algorithms, parallel loops, race conditions.

7 marks★★★ 3×

Asked in: 2022 Nov Q7(b) [7] · 2023 Nov Q7(b) [7] · related: 2025 May Q7(b) [4 — race condition]

(a) Analysing multithreaded algorithms

Two quantities describe a multithreaded computation:

  • Work T1 — total time on one processor (sum of all operations).
  • Span T∞ — critical-path length, i.e. the longest chain of dependencies (time on infinitely many processors).
TP ≥ T1/P   and   TP ≥ T∞
Idealised bound: TP = T1/P + T∞
Speedup = T1/TP   |   Parallelism = T1/T∞

If T1/T∞ = Θ(P), the algorithm scales linearly with P (linear speedup). For matrix multiplication: T1 = Θ(n³), T∞ = Θ(n), parallelism = Θ(n²).

(b) Parallel loops

The construct parallel for runs all iterations concurrently. It is compiled into recursive spawn/sync pairs (divide-and-conquer):

parallel for i = 1 to n
    body(i)

// equivalent to
P-FOR(1, n)
  if lo < hi then
     mid = ⌊(lo+hi)/2⌋
     spawn P-FOR(lo, mid)
     P-FOR(mid+1, hi)
     sync

Iterations must be independent. Span is O(log n) for the loop control; total work is n × work(body).

(c) Race conditions

A race condition occurs when two threads access the same shared memory location, at least one writes, and there is no synchronisation. The result then depends on the unpredictable interleaving.

Thread 1: x = x + 1     Thread 2: x = x + 1
Both read x = 5 → both write 6 → lost update (expected 7)

Prevention: locks/mutexes, atomic operations, sync barriers, or making the computation local and combining at the end (reduction).

Q2What do you understand by the spawn and sync keywords used in multithreaded programming? Explain with a suitable example.

6 marks★★ 2×

Asked in: 2024 May Q8(b) · 2025 May Q7(c) [6]

spawn
Creates a new logical thread of execution that runs a specified subroutine in parallel with the calling thread. The parent continues immediately; it does not wait.
sync
Waits for all spawned children of the current thread to finish. It is the join/barrier point; memory written by children before sync is visible after it.

Example — parallel Fibonacci

P-FIB(n)
  if n ≤ 1 then return n
  x = spawn P-FIB(n−1)     // run in parallel
  y = P-FIB(n−2)           // run in the current thread
  sync                     // wait for the spawned child
  return x + y

Without spawn, the two recursive calls are serial. With spawn, one runs concurrently; sync ensures x is computed before it is added.

Nested rule: a sync waits only for children spawned by the same thread since its last sync, not for all threads in the program.

6.2 Multithreaded matrix multiplication ★★★ 3×

Q1Write a simple multithreaded matrix multiplication algorithm based on parallelising the relevant loops of the conventional procedure.

8 marks★★ 2×

Asked in: 2025 May Q7(a) [8] · short note: 2022 Nov Q7(a) [10]

Conventional algorithm

MATRIX-MULT(A, B, C, n)
  for i = 1 to n
     for j = 1 to n
        C[i][j] = 0
        for k = 1 to n
           C[i][j] = C[i][j] + A[i][k] * B[k][j]

Work = Θ(n³). The two outer loops are independent, so they can be parallelised.

Parallel version

P-MATRIX-MULT(A, B, C, n)
  parallel for i = 1 to n              // each i is independent
     parallel for j = 1 to n           // each (i,j) is independent
        C[i][j] = 0
        for k = 1 to n
           C[i][j] = C[i][j] + A[i][k] * B[k][j]

Each of the n² entries is computed by an independent thread; the inner k-loop remains serial within a thread.

Analysis

T1 = Θ(n³)   |   T∞ = Θ(n)   |   parallelism = T1/T∞ = Θ(n²)
TP = Θ(n³/P + n)

With P = n² processors, TP = Θ(n) — near-perfect speedup.

Cache improvement — blocked version

The naive version accesses B column-wise, causing poor cache locality. Blocked multiplication processes b×b tiles that fit in cache:

for i = 1 to n step b
  for j = 1 to n step b
     for k = 1 to n step b
        multiply blocks A[i..i+b][k..k+b] × B[k..k+b][j..j+b]

Q2Compare and contrast row-wise and block-wise approaches in multithreaded matrix multiplication with respect to division of work, communication overhead and cache efficiency.

6 marks★ 1×

Asked in: 2025 Nov Q7(b)

PointRow-wiseBlock-wise
Division of workOne thread per row of C (or per row-pair). Each thread computes n entries. Simple static partition.Matrix divided into √P × √P tiles; each thread computes one or more tiles. Balanced, tunable tile size.
Communication overheadEach thread needs a full row of A and all columns of B → B is read by every thread → high shared-memory traffic.A tile of A and a tile of B are reused for b² outputs → far fewer global reads, lower communication.
Cache efficiencyPoor: B is traversed column-wise, so consecutive accesses are far apart → cache misses.High: tiles fit in cache and are reused → spatial and temporal locality.
ScalabilityLimited by memory bandwidth.Scales well; standard choice for high-performance BLAS.
ComplexitySimple to implement.More index arithmetic, but much faster for large n.
One-line answer: row-wise is simple but memory-bound; block-wise exploits cache reuse and is the preferred parallel decomposition.

6.3 Multithreaded merge sort ★★★★ 4×

Q1Write and explain the pseudocode for multithreaded merge sort. How does parallel merging give a significant parallelism advantage over ordinary merge sort?

9 marks★★★★ 4×

Asked in: 2022 Nov Q8(a) [9] · 2023 Nov Q8(a) [9] · 2024 May Q7(b) [8] · short note: 2022 Nov Q7(a)

Step 1 — parallel merge sort

P-MERGE-SORT(A, p, r)
  if p < r then
     q = ⌊(p + r) / 2⌋
     spawn P-MERGE-SORT(A, p, q)     // sort left half in parallel
     P-MERGE-SORT(A, q+1, r)         // sort right half in current thread
     sync                            // wait for left half
     P-MERGE(A, p, q, r)             // merge the two halves

Step 2 — parallel merge (the key idea)

Ordinary merge scans both halves sequentially: Θ(n). Parallel merge instead computes, for every element, its final rank in the merged output, then scatters all elements to their positions at once.

P-MERGE(A, p, q, r)          // merge sorted A[p..q] and A[q+1..r]
  for each element x = A[i], i = p..q, in parallel do
      rank[i] = (i − p) + COUNT-LESS(A, q+1, r, x)
      // COUNT-LESS = binary search: how many elements of the right half are < x

  for each element y = A[j], j = q+1..r, in parallel do
      rank[j] = (j − q − 1) + COUNT-LESS(A, p, q, y)

  for each element in parallel do
      B[ rank[i] ] = A[i]       // scatter directly to final position

  copy B[p..r] back to A[p..r]

Each COUNT-LESS is a binary search, so it costs O(log n). All ranks are computed concurrently.

Why this gives a parallelism advantage

  • Ordinary merge is a single serial scan: T∞(merge) = Θ(n). Even with infinitely many processors, the merge remains a bottleneck.
  • Parallel merge computes all ranks concurrently and scatters in one step. Its span is:
T∞(P-MERGE) = Θ(log n)
  • Sorting: T1 = Θ(n log n), T∞ = Θ(log² n) → parallelism = Θ(n / log n).
  • Serial merge sort: T∞ = Θ(n) → parallelism only Θ(log n).

So parallel merging lifts the available parallelism from logarithmic to nearly linear, which is what allows the sort to use many cores effectively.

For 9 marks: write P-MERGE-SORT, explain the binary-search split in P-MERGE, then give the T1/T∞ comparison. Draw the recursion tree showing the two halves merging concurrently.

6.4 Distributed breadth-first search ★★★ 3×

Q1Write the distributed breadth-first search algorithm. What is its advantage over the conventional approach?

8–10 marks★★★ 3×

Asked in: 2022 Nov Q7(a) [short note] · 2024 May Q8(a) [10 — with graph] · 2025 May Q8(a) [8]

Idea — level-synchronous BFS

The graph is distributed across processors: each vertex (or partition) runs on one processor and knows only its own adjacency list. BFS proceeds in rounds; in each round the current frontier sends a message to all neighbours.

Algorithm (per vertex v)

// Initially: dist[v] = ∞ for all v, dist[source] = 0
// frontier = {source}

DistributedBFS(G, source)
{
    dist[source] = 0;
    frontier = {source};
    level = 0;

    while (frontier is not empty) do
    {
        nextFrontier = ∅;

        // all vertices in the frontier work in parallel
        for each v in frontier (in parallel) do
        {
            for each neighbour u of v do
            {
                if (dist[u] == ∞) then
                {
                    dist[u] = level + 1;
                    add u to nextFrontier;
                }
            }
        }

        // global barrier: wait for all vertices of this level
        synchronize();
        frontier = nextFrontier;
        level = level + 1;
    }
}

Trace on the 7-vertex graph (2024 May)

Edges: A–B, A–C, B–D, B–E, C–F, C–G.

RoundFrontierMessages sentNewly discovereddist
0{A}A→B, A→CB, CB=1, C=1
1{B, C}B→D, B→E; C→F, C→GD, E, F, GD=E=F=G=2
2{D, E, F, G}all neighbours already visited——
3∅stop——
BFS tree: A → {B, C}; B → {D, E}; C → {F, G}
Distances: A=0, B=C=1, D=E=F=G=2

Complexity

  • Rounds = graph diameter D (longest shortest path).
  • Messages = O(V + E) total (each edge is examined once from each endpoint).
  • With an adjacency matrix, each vertex scans a row of length n → O(V²) work per level, O(D·V²) total.
  • Memory per processor = O(degree) + O(V) for distances.

Advantages over conventional BFS

  • Scalability — handles graphs too large for one machine's memory.
  • Parallelism — all vertices of a level are processed simultaneously.
  • Locality — each processor only reads its local adjacency list; no global shared queue.
  • Fault tolerance — the level-synchronous structure allows checkpointing between rounds.

Cost: global synchronisation per level and message latency; performance depends on the graph diameter (a long chain → many rounds).

6.5 Distributed minimum spanning tree

Q1Explain an algorithm for distributed minimum spanning tree.

8–10 marks★★ 2×

Asked in: 2023 Nov Q7(a)(i) [10 — part of the distributed short-note question] · 2025 Nov Q8(b) [8]

Problem

Given a connected weighted graph distributed across processors (each vertex knows only its incident edges), find an MST without a central coordinator, using only local messages.

GHS algorithm (Gallager–Humblet–Spira)

It is a distributed version of Borůvka's algorithm. It works in phases:

  1. Initialise — every vertex is its own fragment with a unique fragment ID and level 0.
  2. Find minimum outgoing edge (MOE) — each vertex finds its minimum-weight edge leaving its fragment. Vertices exchange messages along fragment edges to compute the fragment's overall minimum outgoing edge.
  3. Merge fragments — fragments connected by the chosen MOE combine:
    • if both have the same level, the new level = level + 1 and the new ID = weight of the chosen edge;
    • if levels differ, the lower-level fragment adopts the higher level and ID.
  4. Repeat until one fragment remains. The selected edges form the MST.

Message complexity

Each phase merges fragments, so there are O(log V) phases.
Messages per phase = O(E) → total O(E log V) messages.

Why fragment IDs/levels are needed

They prevent cycles: an edge is added only when it connects two distinct fragments. Without IDs, two fragments could both select the same edge or form a cycle.

Simpler alternative (for short answers)

Distributed Borůvka: in each round every component selects its cheapest outgoing edge and all selected edges are added simultaneously. Repeat for O(log V) rounds. MST is the union of selected edges. This is easier to describe and has the same O(E log V) message bound.

Key property (cut property): the minimum-weight edge crossing any cut is safe to include in some MST. Both GHS and Borůvka repeatedly apply this rule locally.

6.6 Naive string matching

Q1Write the naive string-matching algorithm and trace it for T = "KITCHEN", P = "HEN".

8–10 marks★★ 2×

Asked in: 2025 Nov Q8(a) [10] · pseudocode + analysis: 2022 Nov Q8(b) [8]

Algorithm

NAIVE-STRING-MATCHER(T, P)
  n = T.length
  m = P.length
  for s = 0 to n − m do            // every possible shift
  {
      if T[s+1 .. s+m] == P[1..m] then
          print "Pattern occurs with shift" s
  }

It checks every alignment character by character. Worst case O((n−m+1)·m) = O(nm); best case O(n) when the first character mismatches immediately.

Trace: T = K I T C H E N, P = H E N (n = 7, m = 3)

1I T CI ≠ Hmismatch at 1st char

Pattern found at index 4 (5th position).
Comparisons = 4 mismatches × 1 + 3 matches = 7 character comparisons.

In the worst case, e.g. T = "AAAAAA", P = "AAA", every window matches m characters before failing → O(nm).

6.7 Rabin–Karp algorithm ★★★★★ 5×

Q1Write the Rabin–Karp string-matching algorithm. For a text of length n and pattern of length m, give the expected and worst-case running times.

8–10 marks★★★★★ 5×

Asked in: 2022 Nov Q8(b) [8] · 2023 Nov Q7(a)(ii) [10 — part of the short-note question] · 2024 May Q7(a) [10] · 2025 May Q8(b) [10] · 2025 Nov Q7(a) [10]

Idea

Instead of comparing characters at every shift, compare hash values. Compute the hash of the pattern and of the first window of the text; then use a rolling hash to update the window hash in O(1) per shift. Only when the hashes match do we verify the characters (to rule out spurious hits).

Hash function

Interpret a string of m characters as a base-d number modulo a prime q:

h = ( c1·dm−1 + c2·dm−2 + … + cm·d0 ) mod q

Rolling update when the window slides by one character:

hnew = ( d · (hold − cold·dm−1) + cnew ) mod q

Algorithm

RABIN-KARP-MATCHER(T, P, d, q)
  n = T.length;  m = P.length
  h = d^(m−1) mod q
  p = 0;  t = 0

  // preprocessing: hash of pattern and first window
  for i = 1 to m do
  {
      p = (d·p + P[i]) mod q
      t = (d·t + T[i]) mod q
  }

  for s = 0 to n − m do
  {
      if p == t then                    // possible match
          if P[1..m] == T[s+1 .. s+m] then
              print "Pattern occurs at shift" s

      // rolling hash for next window
      if s < n − m then
          t = ( d·(t − T[s+1]·h) + T[s+m+1] ) mod q
  }

Complexity

Preprocessing = Θ(m)
Matching = Θ(n − m + 1) hash comparisons
Expected total = O(n + m)   |   Worst case = O((n − m + 1)·m) = O(nm)

The worst case occurs when many windows have the same hash as the pattern (many spurious hits), forcing full comparisons at every shift.
