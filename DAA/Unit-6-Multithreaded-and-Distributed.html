6.7 Rabin–Karp algorithm ★★★★★ 5×

Q1Write the Rabin–Karp string-matching algorithm. For a text of length n and pattern of length m, give the expected and worst-case running times.

8–10 marks★★★★★ 5×

Asked in: 2022 Nov Q8(b) [8] · 2023 Nov Q7(a)(ii) [10 — part of the short-note question] · 2024 May Q7(a) [10] · 2025 May Q8(b) [10] · 2025 Nov Q7(a) [10]

In simple words: Rabin–Karp turns each window into a number called a hash. It compares the pattern hash with the window hash first. Only when the hashes match does it compare actual characters. A rolling update makes each new hash cheap.

Why we do this

Comparing m characters at every position is slow. Comparing two numbers takes constant time. Rabin–Karp uses a cheap fingerprint to skip most windows, then checks characters only for likely matches.

Terms you need first

  • Hash — a number that represents a string or a window.
  • Hashing — turning data into a fixed-size number.
  • Radix-d — treat each character as a digit in base d. Decimal uses d = 10; binary uses d = 2.
  • Modulus q — the number we divide by and keep the remainder; it keeps hashes small.
  • Rolling hash — update the hash of a window in O(1) when the window slides by one.
  • Candidate — a window whose hash equals the pattern hash.
  • Spurious hit — a candidate whose characters do not actually match.
  • Horner's rule — build a number left to right by multiplying by d and adding the next digit.
  • Preprocessing — the initial work before the main scan.
  • High-order digit — the leftmost digit, which has the largest weight.

Idea — hashing instead of comparing every character

The book says Rabin–Karp is based on the hashing technique. Each character is treated as a digit in radix-d notation, and the algorithm uses the equality of two numbers modulo a third number q. For a decimal string d = 10; for a binary string d = 2.

Let T[1..n] be the text and P[1..m] the pattern. Define:

  • p = the decimal value of the pattern P[1..m].
  • ts = the decimal value of the substring T[s+1..s+m], for s = 0, 1, …, n−m.

If p = ts (mod q), the window is a candidate; the characters are then checked to confirm the match. A candidate that is not a real match is a spurious hit.

What this means: the hash is only a filter. A hash match is a maybe. A character check turns a maybe into a yes or no.

The book's three steps

  1. Compute p in O(m) time.
  2. Compute all ts values in a total of O(n) time.
  3. Find all valid shifts s in a total of O(n) time.

What this means: one pass builds the pattern hash. One pass rolls through the text. Most shifts cost only a hash comparison.

p is computed by Horner's rule:

p = P[m] + d(P[m−1] + d(P[m−2] + … + d(P[2] + d·P[1])))

What this means: start with the last character. Multiply by d and add the previous character. Repeat to the front. This builds the number in one pass.

Book's example: P = 41603, m = 5, d = 10, so

p = 3 + 10(0) + 102(6) + 103(1) + 104(4) = 41603

What this means: the digits 4,1,6,0,3 form the number 41603. Horner's rule gets it without any powers table.

After ts is known, the next window is obtained in O(1) time by the rolling hash:

ts+1 = d(ts − dm−1·T[s+1]) + T[s+m+1]

What this means: remove the leftmost digit's contribution, shift the rest left by one place, and add the new rightmost digit.

Because p and ts may be very large, all values are kept mod q. With h = dm−1 mod q, the update becomes:

ts+1 = (d(ts − T[s+1]·h) + T[s+m+1]) mod q

What this means: h stores the weight of the digit that is leaving. The modulo keeps every hash small, so arithmetic stays fast.

Algorithm (book)

RabinKarp(T[1..n], P[1..m], d, q)
{
    h = d^(m-1) mod q              // high-order digit position
    p = 0;  t0 = 0
    for i = 1 to m
    {
        p  = (d*p + P[i]) mod q
        t0 = (d*t0 + T[i]) mod q
    }
    for s = 0 to n - m
    {
        if (p = t_s) then
        {
            if (P[1..m] = T[s+1 .. s+m]) then
                write("pattern found with shift", s)
        }
        if (s < n - m) then
            t_(s+1) = (d*(t_s - T[s+1]*h) + T[s+m+1]) mod q
    }
}

Step by step:

  1. Compute h = dm−1 mod q.
  2. Build p and t0 with Horner's rule.
  3. For each shift s, compare p with ts.
  4. If they differ, skip the character check.
  5. If they match, compare the actual characters.
  6. Report s only if the characters also match.
  7. Roll ts to ts+1 in O(1), unless this is the last shift.

The example, step by step:

  1. Compute the pattern hash: 26 mod 11 = 4.
  2. Check 31, 14 and 41. Their hashes are 9, 3 and 8, so skip all three.
  3. Check 15. Its hash is 4, so compare 15 with 26. It is a spurious hit.
  4. Check 59. Its hash is 4, but 59 ≠ 26. It is a spurious hit.

Four windows hash to 4: 15, 59, 92 and 26. Only 26 is the real pattern, so 15, 59 and 92 are spurious hits; the book reports the valid match at the 7th position (shift s = 6). The rolling check from window 26 to 65 is exactly the book's line:

ts+1 = 10(26 − 10·2) + 5 = 60 + 5 = 65

What this means: the next window after 26 is 65. The rolling formula gets 65 directly, without rebuilding the number from scratch. Its hash is 65 mod 11 = 10, so the run of hash-4 windows ends.

Complexity

Preprocessing the pattern and first window = Θ(m)
Each shift = O(1) hash check, plus O(m) only when the hash matches
Expected total = O(n + m)
Worst case = O((n − m + 1)·m) = O(nm)

What this means: in the normal case, almost every shift is rejected by the hash, so the scan is linear. In the worst case, every window is a spurious hit, so every shift pays the full character check.

The worst case occurs when many windows have the same hash as the pattern (many spurious hits), forcing a full character comparison at every shift. This is the book's stated matching time, Θ((n−m+1)m).

Real-life analogy: a security guard compares a fingerprint before comparing the whole face. A matching fingerprint sends the person to a full check. A different fingerprint lets the next person pass quickly. A spurious hit is a similar fingerprint on the wrong person.
Common confusion: a hash match is not a real match. It is only a candidate. The worst case is still O(nm) when many spurious hits occur. Also, d is the alphabet size (10 for digits, 2 for binary), not the modulus q.

Why we do this

6.3 Multithreaded merge sort ★★★★ 4×

Q1Write and explain the pseudocode for multithreaded merge sort. How does parallel merging give a significant parallelism advantage over ordinary merge sort?

9 marks★★★★ 4×

Asked in: 2022 Nov Q8(a) [9] · 2023 Nov Q8(a) [9] · 2024 May Q7(b) [8] · short note: 2022 Nov Q7(a)

In simple words: Merge sort splits the array in half, sorts each half, then merges the two sorted halves. Multithreading sorts the halves at the same time. Parallel merging also splits the merge step, so many cores can help.

Why we do this

Sorting is a basic building block in many programs. Ordinary merge sort has one long serial merge at every level. That merge becomes the bottleneck. Parallel merging removes the bottleneck and lets large machines finish faster.

Terms you need first

  • Merge sort — split the array in half, sort each half, then merge the sorted halves.
  • Merge — combine two sorted lists into one sorted list.
  • Subarray — a contiguous piece of an array, written A[a..c].
  • Median — the middle element of a sorted list.
  • Binary search — repeatedly cut a sorted list in half to find a value's position.
  • Parallel merge — a merge that splits both lists and merges the parts at the same time.
  • Span — the longest chain of dependent steps.
  • Spawn — start a child task that runs in parallel.
  • Sync — wait for the tasks spawned by this call.
  • Pivot — the element used to split the lists; here it is the median x.

Step 1 — the book's merge and the simple parallel version

Merge(A, a, b, c) assumes that A[a..b] and A[b+1..c] are already sorted. It merges them into the sorted subarray A[a..c]. The book's first parallel version simply spawns the left recursive sort and does the right one in the current thread:

MergeSort(A, a, c)
{
    if (a < c) then
        b = floor((a + c) / 2)
        spawn MergeSort(A, a, b)
        MergeSort(A, b + 1, c)
        sync
        Merge(A, a, b, c)
}

Step by step:

  1. If the range has one element, it is already sorted; stop.
  2. Find the middle index b.
  3. Spawn a child to sort the left half A[a..b].
  4. Sort the right half A[b+1..c] in the current thread.
  5. Wait at sync for the left half.
  6. Merge the two sorted halves into A[a..c].
MS1(n) = 2MS1(n/2) + Θ(n) = Θ(n log n)
MS∞(n) = MS∞(n/2) + Θ(n) = Θ(n)
Parallelism = Θ(n log n)/Θ(n) = Θ(log n) — low

What this means: the sorting work is n log n, but the final merge is one serial scan of n elements. Even with infinite cores the span stays n. So only log n parallelism is available.

The two halves sort in parallel, but the final Merge is still one serial scan of n elements. Even with infinitely many processors the span stays Θ(n), so only Θ(log n) parallelism is available. Hundreds of processors will not help for large n.

Step 2 — parallel merge: split by the median (book Fig. 6.2.1)

To make the merge itself parallel, the book uses divide and conquer. Given two sorted lists T[a1..c1] and T[a2..c2]:

  1. Choose the longer list as the first list.
  2. Find the middle element (median) x of the first list, at position b1.
  3. Binary search x in the second list to find the position b2 where it would be inserted.
  4. Recursively merge, in parallel:
    • the part before x, T[a1..b1−1], with T[a2..b2−1];
    • the part after x, T[b1+1..c1], with T[b2..c2].
  5. Place x between the two merged parts. Its final position is b3 = a3 + (b1 − a1) + (b2 − a2).

What this means: x is a pivot. Everything before x is smaller, and everything after x is larger. The two sides can now be merged independently.

First list T[a1 ...... b1 ...... c1] : ≤ x | x | ≥ x Second list T[a2 ... b2 ...... c2] : < x | ≥ x | merge left parts + x + merge right parts | Final list A[a3 ............. b3 ............. c3] : ≤ x | x | ≥ x

What this means: the tree shows one split. Each side then repeats the same split, so the merge becomes a balanced recursion.

Step 3 — the complete pseudocode (book)

PMergeSort(Array A, a, c, Array B, m)
{
    n = c - a + 1
    if n == 1
        B[m] = A[a]
    else let T[1..n] be a new array
        b  = floor((a + c) / 2)
        b' = b - a + 1
        spawn PMergeSort(A, a, b, T, 1)
        PMergeSort(A, b + 1, c, T, b' + 1)
        sync
        PMerge(T, 1, b', b' + 1, n, B, m)
}

PMerge(T, a1, c1, a2, c2, A, a3)
{
    n1 = c1 - a1 + 1
    n2 = c2 - a2 + 1
    if n1 < n2                 // make the first list the longer one
        exchange a1 with a2
        exchange c1 with c2
        exchange n1 with n2
    if n1 == 0
        return
    else
        b1 = floor((a1 + c1) / 2)
        b2 = BinarySearch(T[b1], T, a2, c2)
        b3 = a3 + (b1 - a1) + (b2 - a2)
        A[b3] = T[b1]
        spawn PMerge(T, a1, b1 - 1, a2, b2 - 1, A, a3)
        PMerge(T, b1 + 1, c1, b2, c2, A, b3 + 1)
        sync
}

The top-level call is PMergeSort(A, 1, n, B, 1). The two recursive PMerge calls handle the left and right parts concurrently, and the median is written directly to its final position.

What the parameters mean:

  • A, a..c — the input range to sort.
  • B, m — the output array and the position where this range starts.
  • T — a temporary array that holds the two sorted halves.
  • b' — the number of elements in the left half.

What this means: each call sorts into a temporary array. Then PMerge writes the result into the correct place in B. The median goes straight to its final slot, so no extra merge pass is needed.

Step 5 — analysis and the parallelism advantage

PMS1(n) = 2PMS1(n/2) + PM1(n) = 2PMS1(n/2) + Θ(n) = Θ(n log n)
PMS∞(n) = PMS∞(n/2) + PM∞(n) = PMS∞(n/2) + Θ(log² n) = Θ(log³ n)
Parallelism = Θ(n log n)/Θ(log³ n) = Θ(n/log² n)

What this means: the total work stays n log n. The span falls to log³ n. So the available parallelism grows almost linearly with n.

Why this is a significant advantage:

  • Ordinary merge is a single serial scan, so T∞(merge) = Θ(n). An infinite number of processors cannot make it faster than n steps.
  • Parallel merge finds the median's rank by binary search and splits both lists, so the merge span falls to PM∞(n) = Θ(log² n).
  • The sort span falls from Θ(n) in the simple spawn version to Θ(log³ n). Parallelism rises from Θ(log n) to Θ(n/log² n), which is nearly linear in n.
  • The total work is still Θ(n log n), the same as ordinary merge sort; parallel merging does not add asymptotic work.

In short, parallel merging removes the serial merge bottleneck, which is exactly what allows many cores to be used effectively.

What this means: parallel merge does not sort faster by doing less work. It sorts faster by removing the long serial wait at each merge.

Real-life analogy: two teachers each sort half the exam papers. Then they merge the two sorted piles. Instead of one teacher scanning both piles alone, they split at the middle paper and merge the smaller piles in parallel.
Common confusion: parallel merge does not sort the two halves again. They are already sorted. Also, the total work remains Θ(n log n); only the span improves.

6.1 Multithreaded fundamentals

Q1With respect to multithreaded algorithms explain: analyzing multithreaded algorithms, parallel loops, race conditions.

7 marks★★★ 3×

Asked in: 2022 Nov Q7(b) [7] · 2023 Nov Q7(b) [7] · related: 2025 May Q7(b) [4 — race condition]

In simple words: A multithreaded program splits one job into pieces that run at the same time. We measure the total work, the longest chain of dependent steps, and the speed we gain. We also check that two threads never spoil a shared value.

Why we do this

One core can run only one instruction at a time. Extra cores help only when a job has independent parts. This analysis tells us how much speed a job can really gain. It also shows where a shared write can produce a wrong answer.

Terms you need first

  • Thread — one running sequence of instructions inside a program.
  • Strand — a straight-line piece of a thread with no parallel branch inside it.
  • DAG — a directed acyclic graph: tasks are vertices, arrows show dependencies, and no cycle exists.
  • Dependency — a rule that one task must finish before another can start.
  • Register — a tiny, fast storage slot inside the CPU.
  • Lock — a guard that lets only one thread use a shared value at a time.

(a) Model of a multithreaded execution

The book models a multithreaded computation as a computational DAG G = (V, E). Each vertex is an instruction or a strand. Each edge (u, v) is a dependency: u must finish before v starts. The book names four kinds of edge:

  • Continuation edge — horizontal; v is the next instruction in the same strand.
  • Call edge — downward; u calls v as a normal subroutine.
  • Spawn edge — downward; u starts v in parallel.
  • Return edge — upward; the next strand after a call returns, or after parallel work joins at a sync.

A strand with several successors means all but one of them were spawned. A strand with several predecessors is a join at a sync.

What this means: the DAG is a map of “what must happen before what”. Wide parts are parallel. Long chains are serial.

(b) Analysing a multithreaded algorithm — work and span

Let TP be the running time on P processors. The book measures a computation with two quantities:

  • Work T1 — total time to execute the whole computation on one processor. It is the sum of the times taken by all strands.
  • Span T∞ — the longest time along any path in the DAG. It is the time on an infinite number of processors.
Work law: TP ≥ T1 / P
Span law: TP ≥ T∞

What this means: with P processors you cannot beat total work divided by P. You also cannot beat the longest chain, even with unlimited cores.

Work is easy to analyse: ignore the parallel constructs and analyse the serial algorithm. For ParFib(n), T1(n) = T(n) = Θ(φn), where φ = (1+√5)/2 is the golden ratio. Span uses the two composition rules:

Series: T1(A∪B) = T1(A) + T1(B), T∞(A∪B) = T∞(A) + T∞(B)
Parallel: T1(A∪B) = T1(A) + T1(B), T∞(A∪B) = max(T∞(A), T∞(B))

What this means: in a series, times add. In parallel, only the slower branch counts. Work adds in both cases because every strand still runs.

For ParFib, T∞(n) = max(T∞(n−1), T∞(n−2)) + Θ(1) = T∞(n−1) + Θ(1) = Θ(n). Hence parallelism = T1/T∞ = Θ(φn/n).

What this means: the work grows exponentially, but the longest chain grows only linearly. So the job has a lot of parallel slack for large n.

Speedup = T1/TP. By the work law T1/TP ≤ P, so speedup cannot exceed the number of processors. If T1/TP = Θ(P), it is linear speedup; if T1/TP = P, it is perfect linear speedup.

  • Speedup — how many times faster the parallel run is than the one-core run.
  • Linear speedup — speedup grows in proportion to the number of processors.
  • Perfect linear speedup — P processors give exactly P times the speed.
  • Parallelism = T1/T∞ = work/span. It is the maximum useful speedup.
  • Parallel slackness = parallelism / P = T1/(P·T∞). It compares available parallel work with the number of processors.

If slackness is below 1, perfect linear speedup is impossible: there are more processors than the work can use. If it is above 1, work per processor is the limit, and a scheduler can still aim for linear speedup by spreading the work.

What this means: parallelism is a property of the algorithm. Speedup is what you actually get on P cores. Extra cores beyond the parallelism sit idle.

The book's own measure: the Fibonacci(6) DAG has 17 vertices (17 threads) and 8 vertices on the longest path. Taking one unit of time per thread, Work = 17 time units and Span = 8 time units.

What this means: even with unlimited cores this DAG needs at least 8 time units. With 2 cores it needs at least 17/2 = 8.5 time units.

(c) Parallel loops

A parallel for is a loop whose iterations may run at the same time. Instead of writing spawn for every iteration, the book uses parallel for. All iterations of the loop may execute concurrently. The book's example is matrix–vector multiplication y = A x:

MatrixVector(A, x)
1  n = A.rows
2  let y be a new vector of length n
3  parallel for i = 1 to n
4      y_i = 0
5  parallel for i = 1 to n
6      for j = 1 to n
7          y_i = y_i + a_ij * x_j
8  return y

Step by step:

  1. Find the number of rows n.
  2. Create the result vector y with n slots.
  3. Set every yi to 0 in parallel.
  4. Give each row i to a thread.
  5. Inside that thread, multiply row i by x in a serial j-loop.
  6. Return y.

Each i is independent, so all rows can be computed at once. Work T1(n) = Θ(n²). Span T∞(n) = Θ(log n) [parallel-for control] + Θ(n) [one row's serial multiplication] = Θ(n). The parallelism is Θ(n).

What this means: the total work is n² multiply-adds. The longest path is one row of n multiply-adds. So about n threads can be kept busy, and more than n give little benefit.

(d) Race conditions

The book defines a multithreaded algorithm as deterministic if it does the same thing on the same input no matter how the instructions are scheduled. It is nondeterministic if its behaviour can vary from run to run. A determinacy race occurs when two logically parallel instructions access the same memory location and at least one of them performs a write. This condition is called a race condition.

  • Race condition — two parallel tasks touch the same memory, and at least one writes it.
  • Lost update — one thread's write overwrites another thread's write, so an update disappears.
  • Atomic operation — an action that finishes as one indivisible step; no other thread can see it half-done.
a = 0
parallel for i = 1 to 2 do
    a = a + 1          // both write the same memory location
print a

Each a = a + 1 is three operations: (1) read a into a register, (2) increment the register, (3) write the register back to a. If both threads read a = 0 before either writes, both write 1, so the final value is 1 instead of 2 — a lost update. The book's Fig. 6.1.4 shows the interleaving. The orders (1, 2, 3, 4, 5, 7, 6, 8) and (1, 2, 4, 3, 5, 7, 6, 8) give the wrong answer. Most other orders give 2.

Step by step, the lost update:

  1. Start with a = 0.
  2. Thread 1 reads a and gets 0.
  3. Thread 2 reads a before Thread 1 writes, so it also gets 0.
  4. Thread 1 adds 1 in its register and gets 1.
  5. Thread 2 adds 1 in its register and gets 1.
  6. Thread 1 writes 1 to a.
  7. Thread 2 writes 1 to a.
  8. Final value is 1, but the correct value is 2.

What this means: the final answer depends on timing. The same program can print 1 or 2 on different runs. That is nondeterminism caused by a race.

To avoid it: make the updates independent. Use separate accumulators, then combine them after the loop. Or protect the shared read–modify–write with sync, an atomic operation or a lock. Then the update becomes one indivisible action.

Real-life analogy: two clerks update the same bank balance. Both read ₹100 and both add ₹50. Both write ₹150, so one ₹50 deposit vanishes. A lock forces one clerk to finish before the other starts.
Common confusion: parallelism is not the number of cores. It is the maximum useful speedup. A job with parallelism 4 gains almost nothing from 100 cores. Also, span is the longest dependency path, not the sum of all work.

In simple words: spawn starts a helper task and lets the parent keep working. sync waits until those helpers finish. Together they let one function run parts of itself in parallel.

Why we do this

Many recursive algorithms solve two independent subproblems. Running them one after the other wastes cores. spawn exposes the independence, and sync makes sure results are ready before they are combined.

Terms you need first

  • Spawn — a keyword that starts a child task and lets the parent continue.
  • Sync — a keyword that makes the parent wait for the children it spawned.
  • Parent thread — the thread that creates a child.
  • Child thread — the new thread created by spawn.
  • Dynamic multithreading — parallelism created while the program runs, not fixed in advance.
  • Join — the point where parallel branches meet and continue as one.

The book introduces three concurrency keywords: parallel (used with a for loop), spawn and sync. spawn and sync together give dynamic multithreading.

spawn

spawn creates a new sub-process (a child thread) that runs the named subroutine. The parent keeps executing the current process immediately. The parent does not wait for the child. In the computational DAG, a spawn edge points down to the child. The parent continues along a continuation edge.

What happens, step by step:

  1. The parent reaches a spawn statement.
  2. The runtime creates a child thread for that call.
  3. The child becomes ready to run on another core.
  4. The parent does not block; it executes the next statement.
  5. Parent and child now run at the same time.

sync

sync forces the current process to wait until all active parallel threads created by this instance of the program finish. It is the join point — a vertex with several predecessors in the DAG. After sync, all values written by the children are visible, so the parent can safely use them.

What happens, step by step:

  1. The parent reaches sync.
  2. It waits for every child it spawned.
  3. Each child finishes and stores its result.
  4. The parent continues with all child writes visible.

Example — parallel Fibonacci (book, p. 6-3)

ParFib(n)
{
    if n <= 1
        return n
    else
        x = spawn ParFib(n-1);   // child runs in parallel
        y = ParFib(n-2);         // parent does this itself

        return x + y;
}

Without spawn, Fib(n−1) and Fib(n−2) run one after the other. With spawn, ParFib(n−1) runs as a child while the parent computes ParFib(n−2). Both proceed in parallel. sync then waits for the child, and only after that are x and y added. Q1Write a simple multithreaded matrix multiplication algorithm based on parallelising the relevant loops of the conventional procedure.

8 marks★★ 2×

Asked in: 2025 May Q7(a) [8] · short note: 2022 Nov Q7(a) [10]

In simple words: Matrix multiplication fills each cell of C using one row of A and one column of B. Every cell is independent, so we give cells to different threads. A recursive version splits the matrices into blocks and does the same idea with bigger pieces.

Why we do this

The ordinary triple loop does about n³ multiply-adds. That is a lot of work, but most of it is independent. Parallel loops are the simplest way to use several cores without changing the math.

Terms you need first

  • Matrix — a rectangular table of numbers.
  • Row — one horizontal line of a matrix.
  • Column — one vertical line of a matrix.
  • Dot product — multiply matching entries and add the results.
  • Parallel for — a loop whose iterations may run at the same time.
  • Block (submatrix) — a smaller square piece cut from a matrix.
  • Spawn — start a child task that runs in parallel.
  • Sync — wait for the tasks spawned by this call.
  • Span — the longest chain of dependent steps.

Book's simple loop-parallel algorithm

The conventional matrix product C = A × B uses three nested loops. The two outer loops (i and j) are independent, so the book parallelises them and leaves the inner k-loop serial inside each thread.

Step by step, the serial version:

  1. Pick row i of A.
  2. Pick column j of B.
  3. Set cij = 0.
  4. For k = 1 to n, add aik · bkj to cij.
  5. Store cij in C.
  6. Repeat for every (i, j) pair.

Step by step, the parallel version:

  1. Make the i-loop parallel.
  2. Make the j-loop parallel inside it.
  3. Each (i, j) pair becomes one independent task.
  4. Each task runs its own k-loop and writes only cij.
  5. No two tasks write the same cell, so no race condition.
MatMul(matrix A, matrix B)
{
    n = A.rows;
    let C be a new n × n matrix
    parallel for i = 1 to n
        parallel for j = 1 to n
            c_ij = 0
            for k = 1 to n
                c_ij = c_ij + a_ik * b_kj;
    return C
}

There are n² independent (i, j) pairs; each thread does Θ(n) work for its entry.

What this means: the code has the same n³ arithmetic as the serial version. The difference is that many cells are computed at the same time.

Analysis (book)

T1(n) = Θ(n³)    (all n³ multiplications and additions)
T∞(n) = Θ(n)    (one entry's k-loop is the longest path)
Parallelism = T1/T∞ = Θ(n³)/Θ(n) = Θ(n²)

What this means: the total work is n³. The longest chain is one cell's n multiply-adds, plus loop overhead. So n² cells can run in parallel.

With P = n² processors, TP = Θ(n), i.e. near-perfect speedup. The book calls this parallelism very high.

Book's second version — divide-and-conquer block multiplication

Split A, B and C into four (n/2)×(n/2) blocks. The product needs 8 block multiplications and one block addition:

C11 = A11B11 + A12B21    C12 = A11B12 + A12B22
C21 = A21B11 + A22B21    C22 = A21B12 + A22B22

What this means: each quarter of C is the sum of two smaller matrix products. That gives 8 products in total.

Step by step:

  1. If the matrix is 1×1, multiply the two numbers and stop.
  2. Otherwise, cut A, B, C and a temporary matrix T into four blocks each.
  3. Spawn 8 recursive products: four write into C, four write into T.
  4. The parent computes the last product itself.
  5. Wait at sync for all 8 products.
  6. Add T to C in parallel, one cell per thread.
  7. Return C.

Eight recursive products run in parallel; the final addition of the T block is also parallelised over i and j.

What this means: the recursion turns one big product into many small independent products. The final add joins the two halves of each C block.

M1(n) = 8M1(n/2) + Θ(n²) = Θ(n³)
M∞(n) = M∞(n/2) + Θ(log n) = Θ(log² n)
Parallelism = Θ(n³)/Θ(log² n) = Θ(n³/log² n)

What this means: the work is still n³. The span falls to log² n because each level only needs a parallel add. The available parallelism is much larger than the loop version's n².

This is even higher than the loop version's Θ(n²), because the recursive calls expose much more independent work.

Real-life analogy: multiply two big tables by cutting each into four quadrants. Eight helpers compute the eight quadrant products. Then pairs of helpers add their quadrants to finish C.
Common confusion: the block version does not reduce the work. It still does Θ(n³) arithmetic. Only the span and the parallel structure improve. Also, it uses 8 products, not 7; 7 is Strassen's method, which is a different algorithm.

6.4 Distributed breadth-first search ★★★ 3×

Q1Write the distributed breadth-first search algorithm. What is its advantage over the conventional approach?

8–10 marks★★★ 3×

Asked in: 2022 Nov Q7(a) [short note] · 2024 May Q8(a) [10 — with graph] · 2025 May Q8(a) [8]

In simple words: BFS visits a graph level by level from a source. In a distributed version, each node tells its neighbours, and all nodes at the same level work in the same round. No central queue is needed.

Why we do this

Huge graphs may not fit on one machine. A distributed BFS spreads the graph over many processors. Each processor only needs its local neighbours, and messages travel in parallel.

Terms you need first

  • Graph — a set of nodes joined by edges.
  • Vertex (node) — one point in the graph.
  • Edge (link) — a connection between two vertices.
  • Source — the vertex where BFS starts.
  • BFS (breadth-first search) — visit nodes in order of distance from the source.
  • Frontier — the set of nodes at the current level that still have to send messages.
  • Round — one step in which all current frontier nodes send their messages.
  • Message — a small packet sent from one processor to another.
  • Parent — the node that first reached a new node; it becomes the new node's parent in the BFS tree.
  • BFS tree — the tree formed by parent links from the source.
  • Strongly connected — every node can reach every other node.
  • Diameter — the longest shortest-path distance between any two nodes.
  • Adjacency list — the list of neighbours of one node.
  • Level-synchronous — all nodes at one level finish before the next level starts.

What is a distributed algorithm?

The book defines distributed algorithms as algorithms that work on a distributed network or a multiprocessor, where the network is created by interconnected processors. They are a sub-type of parallel algorithms. Separate parts run at the same time on independent processors. Each part has only limited information about the others. The main challenge is coordinating the independent parts despite processor failures and unreliable communication links.

What this means: no processor sees the whole graph. Each one knows only its own neighbours. Coordination happens by sending messages.

Distributed BFS — the book's algorithm

Distributed BFS minimises the maximum communication time from the process at the distinguished node to all other processes in the network. The book assumes a strongly connected network with a distinguished source node i0. The output is a BFS tree rooted at i0. Every process other than i0 sets a parent field. That field names the node's parent in the tree.

Step 1: at any point during execution there is a set of processes that is marked; initially only i0 is marked.
Step 2: process i0 sends a search message at round 1 to all its outgoing neighbours.
Step 3: from round 2 to n, an unmarked process may receive a search message. It marks itself and chooses one sender as its parent. Then it sends the search message to all its outgoing neighbours.
Step 4: finally a BFS tree is obtained.

What this means: a node is marked the first time anyone reaches it. That first sender is its parent. Marking prevents a node from joining twice and creating a cycle.

Written as a level-synchronous loop, the same steps are:

DistributedBFS(G, i0)
    mark i0; parent[i0] = nil; round = 1
    frontier = {i0}
    while frontier is not empty and round <= n
        next = empty set
        for each v in frontier in parallel
            for each neighbour u of v
                if u is unmarked then
                    mark u
                    parent[u] = v          // choose one sender as parent
                    add u to next
        synchronize()                       // all processes finish this round
        frontier = next
        round = round + 1
    return parent[]                         // the BFS tree

Step by step, the pseudocode:

  1. Mark the source and give it no parent.
  2. Put the source in the frontier.
  3. While the frontier has nodes, create an empty set called next.
  4. In parallel, each frontier node looks at all its neighbours.
  5. If a neighbour is unmarked, mark it, set its parent, and add it to next.
  6. Wait until every process finishes this round.
  7. Replace the frontier with next and increase the round number.
  8. When the frontier is empty, return the parent array.

What this means: one round explores one more level. The synchronize step keeps all processors on the same level.

Analysis (book)

The concurrent execution uses at most |E| messages, where E is the number of edges (links) in the network graph and each message has b bits. The book states the number of communication bits as O(|E|²·b). Each process is marked once, so the number of rounds is at most n, and each edge is examined at most once from each endpoint.

What this means: every edge carries only a constant number of messages. The cost grows with the number of edges, not with the number of paths. The round count is bounded by the number of nodes.

Advantage over conventional BFS

  • Minimum maximum communication time — the book's stated objective. The BFS tree gives the shortest communication path from the source to every process.
  • No central queue — each process uses only its local adjacency list and its local parent variable; there is no shared global queue.
  • True parallelism — all vertices at the same level send their messages in the same round.
  • Scalability — the graph and the work are spread over the network, so graphs larger than one machine's memory can be handled.
  • Simple termination — when no unmarked process receives a message, the BFS tree is complete.

Cost: one synchronisation per level, and the number of rounds depends on the graph diameter; a long chain needs many rounds.

Real-life analogy: a rumour starts with one person. In round 1, that person tells all friends. In round 2, those friends tell their friends. Everyone at the same distance hears it at the same time, and nobody needs a central announcement board.
Common confusion: a node does not choose its parent randomly. It chooses one node that sent a message in the previous round, so the parent is always one level closer to the source. Also, plain BFS gives shortest paths only in unweighted graphs; weighted graphs need Dijkstra.

In simple words: An MST connects all nodes with the cheapest total edge cost and no cycles. In a distributed version, each group of nodes finds its cheapest outgoing edge and merges with another group. Repeat until one group remains.

Why we do this

Network designers want the cheapest set of links that keeps every site connected. No single machine may know the whole network. A distributed MST lets each part work with local information and a few messages.

Terms you need first

  • Graph — a set of nodes joined by edges.
  • Vertex (node) — one point in the graph.
  • Edge (link) — a connection between two vertices.
  • Weight — the cost of an edge.
  • Circuit (cycle) — a path that starts and ends at the same vertex.
  • Spanning tree — a subgraph with all vertices, no cycle, and enough edges to stay connected.
  • MST (minimum spanning tree) — a spanning tree with the smallest total weight.
  • Component (fragment) — a connected group of nodes that is being built into the final tree.
  • Leader — the node that coordinates one component.
  • MWOE (minimum weight outgoing edge) — the cheapest edge that leaves a component.
  • Phase — one round in which components find their MWOEs and merge.
  • Convergecast — collect answers from leaves up to the leader.
  • Cut property — the cheapest edge across a cut is safe to add to some MST.
  • Kruskal's strategy — add the cheapest edge that does not make a cycle.
  • Forest — a set of separate trees.
  • Cut — a split of the vertices into two groups.
  • Broadcast — send one message to every node in a component.

Spanning tree and MST (book definitions)

A spanning tree of a graph G is a subgraph that contains all the vertices of G and contains no circuit. A minimum spanning tree (MST) of a weighted connected graph G is a spanning tree with minimum (smallest) total weight.

The book's example (Fig. 6.3.1) is the graph G with edges A–E = 5, A–B = 10, E–D = 3, E–C = 7, D–C = 2, D–B = 6, B–C = 1. Two spanning trees are:

  • T1 = {A–E, E–D, D–C, C–B}, weight = 5 + 3 + 2 + 1 = 11.
  • T2 = {A–B, B–C, C–E, E–D}, weight = 10 + 1 + 7 + 3 = 21.

So T1 is the minimum spanning tree.

What this means: both trees connect all five nodes and have no cycle. T1 is cheaper, so it is the MST. A spanning tree on n nodes always has exactly n−1 edges.

How the answer 11 is built (Kruskal view)

  1. Sort the edges by weight: B–C 1, D–C 2, E–D 3, A–E 5, D–B 6, E–C 7, A–B 10.
  2. Take B–C (1).
  3. Take D–C (2).
  4. Take E–D (3).
  5. Take A–E (5).
  6. Skip D–B (6): B and D are already connected, so it would make a cycle.
  7. Skip E–C (7): E and C are already connected.
  8. Skip A–B (10): A and B are already connected.
  9. Stop after four edges. Total weight = 1 + 2 + 3 + 5 = 11.

What this means: always take the cheapest edge that does not create a cycle. After n−1 edges, every node is connected and the tree is complete.

Distributed MST — Gallager–Humblet–Spira (GHS)

The book says GHS uses Kruskal's strategy and works in phases. After each phase we have a spanning forest in which every component tree has a leader. In each phase, every component finds its Minimum Weight Outgoing Edge (MWOE). The components then merge along these MWOEs to form the next phase's components.

Initially: every node is a component by itself (a level-0 component).

Phase 1 (produces level-1 components):

  1. Each node uses its minimum-weight edge as the component MWOE.
  2. Send a connect message across the MWOE.
  3. There is a unique edge that is the MWOE of two components; the two components join across it.
  4. The leader of the new component is the higher-id endpoint of this unique edge.

What this means: single nodes look for their cheapest link. Two nodes that choose the same link merge into one component. The higher-id node becomes the leader.

Phase K+1 (produces level-(K+1) components):

  1. The leader of each component broadcasts initiate on the tree edges to start the search for the component's MWOE.
  2. Each node finds its own MWOE:
    • send test on potential edges and wait for accept (the other endpoint is in a different component) or reject (same component);
    • test the edges one at a time in increasing order of weight;
    • report the best edge to the leader by convergecast, remembering the direction of the best edge.
  3. The leader picks the MWOE for the whole fragment.
  4. Send change-root to the MWOE's endpoint, using the remembered best edges.
  5. Send connect across the MWOE.
  6. Again there is a unique edge that is the MWOE of two components; the leader of the new component is the higher-id endpoint of that edge.

What the messages do:

  • initiate — the leader starts a new phase.
  • test — “is this edge leaving my component?”
  • accept — yes, the other endpoint is outside this component.
  • reject — no, the other endpoint is inside this component.
  • report — a node sends its best edge up the tree.
  • change-root — make the MWOE endpoint the new root so the tree can grow there.
  • connect — merge across the chosen MWOE.

What this means: a component cannot see the whole graph. It tests edges one by one. The leader gathers the best local answers and chooses one edge to grow the tree.

Repeat until one component remains. The edges chosen across the MWOEs form the MST.

Analysis (book)

Message complexity = O(n log n + |E|)
Time complexity = O(n log n)

What this means: the number of messages grows slowly with n and linearly with the number of edges. The level structure keeps the number of phases logarithmic.

The level structure keeps the components balanced, so there are O(log n) phases. Within a phase each edge is tested at most once from each side, which gives the |E| term.

Why MWOE, component id and level are needed

The MWOE is the cheapest edge leaving a component, so adding it is safe by the cut property of MSTs. A node uses the component id and level to decide if a tested edge leaves its component (accept) or stays inside it (reject). These values also prevent two components from merging into a cycle. Choosing the higher-id endpoint as leader gives a unique leader for the merged component.

What this means: the component id answers “are we in the same group?”. The level answers “which group is more advanced?”. Together they stop cycles and keep merges balanced.

Real-life analogy: several neighbourhoods want the cheapest set of bridges that connects them all. Each neighbourhood picks its cheapest bridge to the outside. Two neighbourhoods that pick the same bridge join into one larger neighbourhood. Repeat until all are connected.
Common confusion: an MST minimises the total weight of all links, not the distance between two chosen nodes. A shortest-path tree is a different object. Also, the MWOE is the cheapest edge leaving a component, not the cheapest edge in the whole graph.

6.6 Naive string matching

Q1Write the naive string-matching algorithm and trace it for T = "KITCHEN", P = "HEN".

8–10 marks★★ 2×

Asked in: 2025 Nov Q8(a) [10] · pseudocode + analysis: 2022 Nov Q8(b) [8]

In simple words: Naive string matching slides the pattern over the text one position at a time. At each position it compares characters until a mismatch. It is simple, but it can be slow when many windows share a long prefix.

Why we do this

This is the baseline method for finding a word inside a text. It is easy to code and easy to trace. It also shows the worst case that faster methods such as Rabin–Karp try to avoid.

Terms you need first

  • Text T — the long string we search inside.
  • Pattern P — the short string we look for.
  • Shift s — the starting position where P is aligned under T.
  • Window — the m characters of T that line up with P at a given shift.
  • Match — every character in the window equals the pattern.
  • Mismatch — at least one character differs.
  • Brute force — try every possible position, one by one.
  • Prefix — the first few characters of a string.

String matching — the book's definition

String matching is used in text processing. Given a text T = t0t1…tn−1 and a pattern P = p0p1…pm−1. The job is to find one or all occurrences of P in T. The pattern is compared with every length-m window of the text.

What this means: n is the text length and m is the pattern length. There are n−m+1 possible starting positions.

Naïve (brute-force) algorithm

The book calls this the simplest method, working by the brute-force (“Just do it”) approach. It checks every position from 0 to n−m. After each attempt, it shifts the pattern right by exactly one position. It reports a match when the whole window equals the pattern.

Naive(T[1..n], P[1..m])
{
    for s ← 0 to n - m do
    {
        if (P[1..m] = T[s+1 .. s+m]) then
            print ("pattern found with shift", s);
    }
}

Here s is the shift: the pattern is aligned with T[s+1..s+m]. If the window does not match, the pattern moves one place right and the comparison is repeated.

Step by step:

  1. Read n and m.
  2. Set shift s = 0.
  3. Line up P with the window T[s+1..s+m].
  4. Compare characters from left to right.
  5. If all m characters match, report s.
  6. If a mismatch appears, stop this try.
  7. Move s one place right and repeat.
  8. Stop after s = n−m.

Analysis (book)

The outer for runs at most n−m+1 times, and the comparison inside can examine up to m characters. Hence the worst-case running time is

O((n − m + 1) · m) = O(nm)

What this means: in the worst case, every window matches almost all characters before failing. Then the work is about n times m.

For a typical word search in natural language, the average-case efficiency is Θ(n) (book). The worst case occurs when many windows match a long prefix before failing, e.g. T = "AAAAAA", P = "AAA".

Real-life analogy: you place a stencil with three holes over a word. You check the letters under the holes. If they fail, you slide the stencil one letter right and check again.
Common confusion: shift 4 is the fifth character, not the fourth. The last possible shift is n−m, not n. Also, the average case is fast, but the worst case is O(nm), not O(n+m).
