5.1 Amortized analysis — the three methods

Q1Explain the methods of amortized analysis with a suitable example.

6–9 marks★★★★★ 5×

Asked in: 2022 Nov Q5(a) [10 — short notes on all three] · 2023 Nov Q5(a) [9 — aggregate] · 2024 May Q6(a) [8] · 2025 May Q6(a) [6] · 2025 Nov Q5(c) [6 — any two]

What is amortized analysis?

Amortized analysis finds the average cost per operation over a sequence of operations, in the worst case, without using probability. A single operation may be expensive (e.g. MULTIPOP empties the stack), but that cost is "paid for" by many cheap operations before it. Amortized cost is not average-case cost.

Method 1 — Aggregate analysis

Show that a sequence of n operations costs T(n) in total; then the amortized cost per operation is T(n)/n.

  • Stack with MULTIPOP: n operations cost ≤ 2n → O(1) per operation.
  • Binary counter: n increments flip < 2n bits → O(1) per increment.

Method 2 — Accounting method

Charge each operation an amortized cost that may differ from its actual cost. The surplus is stored as credit on data objects. The rule: total credit must never become negative. Then total amortized cost ≥ total actual cost.

  • PUSH charges 2: 1 pays for the push, 1 is credit stored on the element.
  • POP and MULTIPOP charge 0 and spend the stored credit.
  • Total for n operations = 2n → amortized O(1).

Method 3 — Potential function method

Define a potential function Φ(D) over data structures, with Φ(D0) = 0 and Φ(Di) ≥ 0. The amortized cost of operation i is:

ĉi = ci + Φ(Di) − Φ(Di−1)

Summing over n operations gives total amortized = total actual + Φ(Dn) − Φ(D0) ≥ total actual.

  • Stack: Φ = size of stack → PUSH amortized 2, POP 0, MULTIPOP 0.
  • Binary counter: Φ = number of 1 bits → INCREMENT amortized 2.

Comparison

MethodIdeaBest used when
AggregateTotal cost / number of operationsAll operations have similar structure and the total is easy to bound
AccountingPrepay credit; spend laterDifferent operations have very different costs
PotentialFormal "energy" stored in the structureNeed a rigorous proof; complex data structures
Key line for the examiner: amortized analysis averages over a sequence, not over inputs — so it gives a worst-case guarantee, unlike average-case analysis.

5.2 Stack: PUSH, POP, MULTIPOP ★★★ 3×

Q1Explain amortized analysis using a stack with PUSH, POP and MULTIPOP. Find the amortized cost of each operation using all three methods.

9 marks★★★ 3×

Asked in: 2022 Nov Q6(a) [9] · 2023 Nov Q5(b) [9] · 2025 Nov Q6(a) [9]

Operations and actual costs

OperationActionActual cost
PUSH(S, x)push x onto stack S1
POP(S)remove and return top element1
MULTIPOP(S, k)pop min(k, |S|) elementsmin(k, |S|)

A MULTIPOP of k elements can cost O(k), which looks expensive. But each element can be popped only after it has been pushed, so across any sequence the total pops cannot exceed the total pushes.

Method 1 — Aggregate analysis

Start with an empty stack and perform n operations. Each element is pushed at most once, so it can be popped at most once.

Total cost of n operations ≤ (number of pushes) + (number of pops) ≤ n + n = 2n
Amortized cost per operation = 2n / n = 2 = O(1)

Method 2 — Accounting method

Charge 2 for PUSH, 0 for POP, 0 for MULTIPOP.

  • PUSH: 1 unit pays for the actual push, the second unit is stored as credit on the pushed element.
  • POP: uses the 1 unit of credit stored on that element.
  • MULTIPOP: each element popped uses its own stored credit.

Credit never goes negative, so total amortized cost = 2n → O(1) per operation.

Method 3 — Potential function method

Let Φ(S) = |S|, the number of elements in the stack. Initially Φ = 0 and Φ ≥ 0 always.

OperationActual ciΔΦAmortized ĉi = ci + ΔΦ
PUSH1+11 + 1 = 2
POP1−11 − 1 = 0
MULTIPOP(k)k′ = min(k, |S|)−k′k′ − k′ = 0
All three operations have amortized cost O(1).
Total for n operations = O(n), even though one MULTIPOP can cost O(n).
Common mistake: saying "MULTIPOP is O(n) so the sequence is O(n²)". That is the worst-case per operation, not the amortized bound. The total is O(n) because each element is popped once.

5.3 Binary counter ★★ 2×

Q1Prove that the amortized cost per operation of a k-bit binary counter is O(1), using the aggregate method.

5–6 marks★★ 2×

Asked in: 2025 May Q5(a) [6] · 2025 Nov Q5(a) [5]

Setup

A k-bit binary counter starts at 0 and supports INCREMENT. INCREMENT flips a suffix of 1-bits to 0 and the next 0-bit to 1. For example:

0000 → 0001 (1 flip) → 0010 (2 flips) → 0011 (1) → 0100 (3) → 0101 (1) → 0110 (2) → 0111 (1) → 1000 (4)

Aggregate analysis

In n consecutive INCREMENT operations, count how often each bit flips:

Bit positionFlips everyNumber of flips in n increments
bit 0 (LSB)1 operationn
bit 12 operationsn/2
bit 24 operationsn/4
………
bit k−12k−1n/2k−1
Total flips T(n) = n + n/2 + n/4 + … + n/2k−1 < n · Σi≥0 (1/2)i = 2n
Amortized cost per INCREMENT = T(n)/n < 2 = O(1)

Potential method (alternative, for full marks)

Let Φ = number of 1-bits in the counter. If an INCREMENT flips t trailing 1s to 0 and one 0 to 1:

actual cost ci = t + 1
ΔΦ = (1 − t)   (lose t ones, gain one 1)
ĉi = ci + ΔΦ = (t + 1) + (1 − t) = 2

Since Φ ≥ 0 and Φ starts at 0, total amortized cost ≥ total actual cost, so each operation is O(1) amortized.

Worst case vs amortized: a single INCREMENT can flip all k bits → O(k). But n increments cost O(n), so the amortized cost is O(1).

5.4 Tractable and intractable problems

Q1What are tractable and non-tractable (intractable) problems? Give examples.

6–7 marks★★★★ 4×

Asked in: 2022 Nov Q5(a) [part] · 2025 May Q5(b) [7] · 2025 Nov Q5(b) [6]

Tractable

A problem is tractable if it can be solved by an algorithm whose running time is a polynomial in the input size, i.e. O(nk) for some constant k. Such problems form the class P.

Examples: sorting (O(n log n)), searching a sorted list (O(log n)), shortest path (Dijkstra O(E log V)), minimum spanning tree, matrix multiplication, linear programming, string matching.

Intractable (non-tractable)

A problem is intractable if no polynomial-time algorithm is known and the best known algorithms are exponential or worse. These include NP-hard and NP-complete problems.

Examples: travelling salesman problem (decision version), 0/1 knapsack (decision version), graph colouring (decision version), Hamiltonian cycle, SAT / 3-SAT, vertex cover, subset sum.

Important nuance

  • P ⊆ NP. Whether P = NP is still open; most researchers believe P ≠ NP.
  • A problem can be NP-hard but still solvable for small inputs — "intractable" is about asymptotic worst-case growth, not about every instance.
  • Approximation algorithms and heuristics are used for intractable optimisation problems (e.g. 2-approximation for metric TSP).

Q2What are intractable problems? Does the Travelling Salesman Problem belong to this class? Justify.

6 marks★ 1×

Asked in: 2025 Nov Q5(b) [6]

Yes. The decision version of TSP ("is there a tour of length ≤ K?") is NP-complete: a candidate tour can be verified in polynomial time, and Hamiltonian cycle reduces to it. The optimisation version ("find the shortest tour") is NP-hard. No polynomial-time exact algorithm is known; brute force is O(n!), and DP (Held–Karp) is O(n²2n) — both super-polynomial.

But: for the metric TSP (triangle inequality) a 2-approximation exists via MST double traversal, and Christofides' algorithm gives 1.5-approximation. So TSP is intractable exactly, but approximable.

Q3Comment: "The problem of searching an ordered list or an unordered list belongs to the class of tractable problems."

4 marks★ 1×

Asked in: 2025 Nov Q6(c) [4]

The statement is true. Searching an unordered list takes O(n) (linear scan) and searching a sorted list takes O(log n) (binary search). Both are polynomial in the input size, hence both belong to P and are tractable. Even the O(n) linear search is linear — well within polynomial time.

5.5 Randomized algorithms ★★★★★ 5×

Q1What are randomized algorithms? Enlist and explain the primary reasons for using randomized algorithms.

8 marks★★★★★ 5×

Asked in: 2022 Nov Q5(b) [8] · 2023 Nov Q6(c) [8] · 2024 May Q5(a) [8] · 2025 May Q6(c) [4] · 2025 Nov Q6(b) [4]

Definition

A randomized algorithm makes random choices during execution (using a random number generator) rather than following a fixed deterministic path. Its running time or output may be a random variable, and we analyse its expected behaviour over all random choices.

Two types

TypeGuaranteeExample
Las VegasAlways correct; running time is randomRandomized quicksort, randomized min-cut
Monte CarloFixed running time; may be wrong with small probabilityMiller–Rabin primality test

Reasons for using randomized algorithms

  1. Avoid worst-case inputs — a random pivot in quicksort prevents an adversarial already-sorted input from causing O(n²).
  2. Simplicity — randomized algorithms are often much shorter and easier to implement than deterministic ones with the same guarantee (e.g. hashing, min-cut).
  3. Speed — many randomized algorithms are asymptotically faster or have better constants (e.g. randomized primality testing).
  4. Symmetry breaking — random choices let distributed processes break ties without coordination (e.g. randomized leader election, contention resolution).
  5. Hashing — random hash functions give good expected O(1) performance regardless of the key distribution.
  6. Approximation — randomness helps in sampling, estimation (Monte Carlo integration) and approximation algorithms.
  7. Security — random keys and nonces are essential in cryptography.

Mathematics used

  • Random variable X — a function from the sample space to real numbers. Example: X = number of comparisons in quicksort.
  • Expected value: E[X] = Σx x · Pr(X = x); linearity E[X+Y] = E[X] + E[Y] holds even when X and Y are dependent.
  • Indicator variable: Ii = 1 if event i occurs, else 0; E[Ii] = Pr(event i).
  • Binomial random variable: X ~ B(n, p), the number of successes in n independent trials with success probability p. E[X] = np, Var(X) = np(1−p), Pr(X=k) = nCk pk(1−p)n−k.
  • Markov / Chebyshev / Chernoff bounds — bound the probability that a random variable deviates far from its mean.

Q2Does the randomized algorithm for quicksort improve the average-case time complexity? Discuss.

4 marks★★ 2×

Asked in: 2025 May Q5(c) [4] · 2025 Nov Q6(b) [4]

No — it does not change the average-case complexity, which remains O(n log n). What it improves is the worst-case behaviour on adversarial inputs.

  • Deterministic quicksort with first/last pivot is O(n²) on already-sorted input, because every partition is completely unbalanced.
  • Randomized quicksort picks the pivot uniformly at random. For any fixed input, the expected running time over the random choices is O(n log n).
  • The worst case O(n²) is still possible but has very low probability; no adversary can force it without knowing the random choices.
Expected T(n) = O(n log n)   |   Worst case = O(n²) with probability ≈ 0

One-line answer: randomization converts a bad input-dependent worst case into a low-probability event; the average case stays O(n log n).

5.6 Approximation algorithms ★★★★ 4×

Q1What are approximation algorithms? Based on the approximation ratio, classify them. How are performance ratios useful?

7–9 marks★★★★ 4×

Asked in: 2022 Nov Q5(b) [8] · 2023 Nov Q6(b) [4] · 2024 May Q5(b) [9] · 2025 May Q6(b) [7]

Definition

An approximation algorithm runs in polynomial time and returns a feasible solution that is guaranteed to be close to the optimal, for an NP-hard optimisation problem where finding the exact optimum is impractical.

Approximation ratio

For a minimisation problem with algorithm cost C and optimal cost C*:

ρ(n) = max( C / C*, C* / C )   →   ρ(n) ≥ 1
An algorithm with ratio ρ(n) is called a ρ(n)-approximation algorithm.

For maximisation, C ≤ C*, and the same max formula applies. Smaller ρ = better approximation; ρ = 1 means optimal.

Classification by approximation ratio

ClassGuaranteeExample
Constant-factorρ(n) = c, a constant2-approx vertex cover; 2-approx metric TSP (MST double traversal)
PTAS (Polynomial-Time Approximation Scheme)For every ε > 0, ratio (1+ε); running time polynomial in n for fixed εEuclidean TSP, scheduling on identical machines
FPTAS (Fully PTAS)Ratio (1+ε), running time polynomial in both n and 1/ε0/1 knapsack (scaling + DP)
Logarithmic-factorρ(n) = O(log n)Set cover — greedy gives H(n) ≈ ln n
APX-hard / no PTASConstant factor possible, but no PTAS unless P = NPGeneral TSP, bin packing

Why performance ratios are useful

  • They give a provable worst-case quality guarantee, unlike heuristics which have no guarantee.
  • They let us trade accuracy for speed in a controlled way — choose ε to meet a required quality.
  • They allow comparison of algorithms independently of input instances.
  • They help decide whether an exact algorithm is worth the exponential cost.

Example — vertex cover 2-approximation

Repeatedly pick an uncovered edge (u,v), add both endpoints to the cover, and remove all edges incident to them. The chosen edges form a matching, and any vertex cover must contain at least one endpoint per matching edge, so |C| ≤ 2·|C*| → ratio 2.

5.7 Embedded algorithms & power-optimized scheduling ★★★ 3×

Q1What is an embedded algorithm? Explain embedded system scheduling using a power-optimized scheduling algorithm.

9 marks★★★ 3×

Asked in: 2022 Nov Q6(b) [9] · related: 2023 Nov Q6(a) [6] · 2024 May Q6(b) [9]

Embedded algorithm

An embedded algorithm is an algorithm designed to run inside a dedicated embedded system (microcontroller/DSP/SoC) that interacts with the physical world in real time. It must satisfy non-functional constraints along with correctness:

  • Limited memory — small RAM/ROM, no virtual memory; avoid large tables and recursion.
  • Low power — battery or thermally constrained devices.
  • Real-time deadlines — hard/soft deadlines; worst-case execution time must be predictable.
  • Deterministic timing — avoid algorithms with high variance (e.g. quicksort worst case).
  • Small code size and no dynamic allocation.
  • Reliability — must recover from faults; often fixed-point instead of floating-point arithmetic.

Power-optimized scheduling

The dominant power in CMOS is dynamic power:

Pdynamic = α · C · V² · f

where V is supply voltage and f is clock frequency. Since f ∝ V, lowering frequency allows a quadratic reduction in voltage and hence a cubic reduction in power. DVFS (Dynamic Voltage and Frequency Scaling) exploits this.

A power-optimized scheduler assigns each task the lowest frequency/voltage that still meets its deadline, using the slack left by earlier tasks.

  1. Sort tasks by deadline (EDF — Earliest Deadline First) or by period (Rate Monotonic).
  2. Compute the required execution cycles for each task: Ci.
  3. Choose frequency fi such that Ci/fi ≤ deadlinei − current time.
  4. Run at that frequency; any leftover slack is used to lower the frequency further (slack stealing).
  5. If the total utilization Σ Ci/Ti ≤ 1, EDF guarantees all deadlines are met.
Energy saved ≈ Σ (Pmax − Pi) · ti,   with Pi ∝ fi3

Example: a task needs 300 ms of work with a 500 ms deadline; running at 60% frequency still meets the deadline and cuts dynamic energy to about 0.6³ ≈ 22% of the maximum.

Trade-off: lower frequency increases execution time, so the scheduler must keep enough slack. Too aggressive scaling causes deadline misses; too conservative scaling wastes energy.

5.8 Sorting algorithm for embedded systems

Q1Which sorting algorithm is best for embedded systems? Why? / Suggest a suitable sorting algorithm for a real-time medical device and justify.

6–9 marks★★ 2×

Asked in: 2023 Nov Q6(a) [6] · 2024 May Q6(b) [9 — medical device scenario]

Answer

Insertion sort is the best choice for the small data buffers typical of embedded systems. For larger buffers with hard real-time deadlines, heap sort is the safer choice.

Why insertion sort for small buffers

  • In-place — needs only O(1) extra memory, no recursion stack.
  • Adaptive — O(n) on nearly sorted data, which is common for sensor streams.
  • Low overhead — simple loops, small code size, no function calls.
  • Stable — preserves the order of equal readings (useful for timestamps).
  • For n ≤ ~32 it beats O(n log n) algorithms because of cache behaviour and constant factors.

Why heap sort for larger / real-time data

  • Guaranteed O(n log n) in the worst case — predictable timing, unlike quicksort's O(n²).
  • In-place, O(1) extra memory — unlike merge sort's O(n) buffer.
  • No recursion if implemented iteratively → no stack overflow.

Why not the others

AlgorithmProblem in embedded systems
Quick sortWorst case O(n²) and recursion stack → unpredictable latency
Merge sortO(n) extra memory — too costly on small RAM
Bubble / selectionO(n²) always — too slow for real-time streams
Counting / radixNeeds extra arrays proportional to range; only for integer keys

Medical device scenario (2024 May)

The device samples timestamps, temperature, heart rate and blood pressure continuously and must display results in real time. The buffer is small and often nearly sorted, so insertion sort is ideal: it is in-place, stable, O(n) on nearly sorted data, and has bounded low overhead. If the buffer grows large, switch to heap sort to keep a hard O(n log n) worst-case guarantee.

One-liners

  • Amortized = average over a sequence, worst case, no probability.
  • Aggregate = total/n; Accounting = prepaid credit; Potential = energy function.
  • Tractable = polynomial (P); intractable = NP-hard, exponential.
  • Las Vegas = always correct, random time; Monte Carlo = fixed time, may err.
  • Randomized quicksort = expected O(n log n), avoids adversarial worst case.
  • PTAS = (1+ε) for any ε; FPTAS = poly in n and 1/ε.
  • Embedded = memory, power, real-time, determinism.
  • DVFS = lower f and V → cubic power saving.
  • Embedded sort = insertion sort (small) / heap sort (large).
