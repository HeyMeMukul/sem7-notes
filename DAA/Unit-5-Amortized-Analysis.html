5.5 Randomized algorithms ★★★★★ 5×

Q1What are randomized algorithms? Enlist and explain the primary reasons for using randomized algorithms.

8 marks★★★★★ 5×

Asked in: 2022 Nov Q5(b) [8] · 2023 Nov Q6(c) [8] · 2024 May Q5(a) [8] · 2025 May Q6(c) [4] · 2025 Nov Q6(b) [4]

In simple words: A randomized algorithm uses a random number generator to make choices. It tosses a coin or rolls a die inside the code. Two runs on the same input can take different paths. Often this makes the code simpler, and it stops a bad input from forcing the worst case every time.
Why we do this: A fixed algorithm can be attacked by one nasty input. For example, sorted data makes fixed-pivot quicksort very slow. Random choices remove that fixed weakness. They also give simple solutions to hard problems, such as primality testing.

The words you need first

  • Randomized algorithm: an algorithm that uses random choices while it runs.
  • Randomizer: the random number generator that supplies those choices.
  • Deterministic algorithm: an algorithm with no randomness; the same input always follows the same path.
  • Expected time: the average time over all random choices, weighted by their probabilities.
  • Õ(log n): O(log n) with small extra log factors ignored.
  • Prime: a whole number greater than 1 with no divisor except 1 and itself.
  • Composite: a whole number that has a divisor other than 1 and itself.
  • Divisor: a number that divides another exactly, with no remainder.
  • mod n: the remainder after dividing by n.
  • Congruence: a ≡ b (mod n) means a and b leave the same remainder.
  • Cryptography: the science of secret codes and secure communication.
  • Las Vegas algorithm: always gives the correct answer; its running time may vary.
  • Monte Carlo algorithm: runs in a fixed time; it may give a wrong answer with a small probability.

Randomized algorithm — book definition

A randomized algorithm uses a random number generator (randomizer). It takes each decision from the current random output. It does not follow one fixed deterministic path. The book gives three properties:

  1. Execution time may vary from run to run.
  2. For different inputs there may be different outcomes on each execution.
  3. For the same input there may be different outcomes on each execution.

What this means: randomness is inside the algorithm, not in the input. The input can be fixed; the path through the code still changes.

Probability background used by the book

  • An experiment has outcomes called sample points; the set of all sample points is the sample space S.
  • An event E is a subset of S; its probability is P(E) = |E| / |S|. For m sample points there are 2m possible events.
  • Two events are mutually exclusive if A ∩ B = ∅; they are independent if P(A ∩ B) = P(A) × P(B).
  • A random variable F maps sample points to real numbers; it is discrete if its set of values is finite. Example: pick 4 balls from an urn of red and white balls; F = number of red balls, so F(RRRW) = 3 and F(RWWW) = 1.
  • A probability distribution lists P[F = ai] for all values, and Σ P[F = ai] = 1. For the 4-ball example: P[0] = 1/16, P[1] = 4/16, P[2] = 6/16, P[3] = 4/16, P[4] = 1/16.

Plain meanings:

  • Sample point: one possible result, such as H or T for a coin.
  • Sample space: the full set of possible results.
  • Event: a group of results we care about, such as “at least one head.”
  • Mutually exclusive: the two events cannot happen together.
  • Independent: one event does not change the chance of the other.
  • Random variable: a number attached to each result, such as the count of red balls.
P(E) = |E| / |S|   |   P(A ∩ B) = P(A) × P(B) if A and B are independent

What this means: for equally likely outcomes, probability is just “good outcomes divided by all outcomes.” For independent events, multiply the probabilities.

In standard exam language: Las Vegas = correct answer, random time; Monte Carlo = fixed time, small probability of error. The book's defining test is the “same/different outcome” line above.

Memory hook: Las Vegas keeps gambling until it wins, so it always wins but may take long. Monte Carlo places one fixed bet, so it finishes on time but may lose. For algorithms, “win” means “correct answer.”

Book examples

  1. Repeated elements (Las Vegas). An array of n elements has n/2 distinct and n/2 duplicate values. A deterministic algorithm may need n/2 + 2 steps. The randomized algorithm Repeated(a,n) repeatedly picks two random indices i and j until i ≠ j and a[i] = a[j], then returns i. Each trial is O(1); the expected number of trials is O(log n), written Õ(log n).
  2. Primality testing (Monte Carlo). A composite n has a divisor ≤ ⌊√n⌋; testing all divisors from 2 to ⌊√n⌋ is the deterministic way. The randomized version uses Fermat's theorem an−1 ≡ 1 (mod n): pick a random a and test the congruence. If it fails, n is composite; if it holds, n is probably prime. It may return a wrong answer with small probability. It is used in cryptography.
  3. Randomized quicksort (Las Vegas). RANDOMIZED-PARTITION picks the pivot index uniformly at random, swaps A[r] with A[i], and then calls PARTITION. The rest of quicksort is unchanged. It avoids the fixed-pivot worst case; expected time is O(n log n). See Q2 below for the full step-by-step.

Example 1 — repeated elements, step-by-step

  1. Pick a random index i from 0 to n − 1.
  2. Pick a second random index j from 0 to n − 1.
  3. If i = j, pick again. We need two different cells.
  4. If a[i] = a[j], return i. We found a duplicate pair.
  5. Otherwise repeat the trials.
  6. The book shows the expected number of trials is O(log n).
Expected trials = O(log n)  →  Õ(log n) time

What this means: the Õ hides small log factors. The randomized method beats the deterministic n/2 + 2 steps for large n.

Example 2 — primality testing, step-by-step

  1. Pick a random number a between 2 and n − 2. Pick one that shares no factor with n.
  2. Compute an−1 mod n.
  3. If the result is not 1, n is definitely composite.
  4. If the result is 1, n is probably prime. Repeat with more random a values to reduce the error chance.
  5. Report “prime” or “composite” after enough trials.
Fermat test: an−1 ≡ 1 (mod n)

What this means: a single failed test proves “composite.” A passed test is strong evidence for “prime,” but not a proof.

Primary reasons for using randomized algorithms

The book lists two major advantages:

  1. Simple to implement — the random choice often removes complicated case handling. For example, RANDOMIZED-PARTITION adds only a random index and a swap to ordinary PARTITION.
  2. Many times more efficient than traditional algorithms — random sampling and random pivots often give better expected performance. The repeated-element search takes Õ(log n) instead of n/2 + 2 steps, and randomized quicksort has expected O(n log n) on any input.

Two further reasons follow directly from the book's examples:

  1. Avoiding an adversarial worst case — randomizing the pivot means no fixed input order can force quicksort's O(n²) partition pattern every time.
  2. Good solutions quickly for hard problems — for primality, random witnesses replace a long deterministic search; for duplicate detection, random sampling is much faster than scanning.

Drawbacks (book §5.4.3)

  • The small degree of error may be dangerous for some applications.
  • It is not always possible to obtain better results using a randomized algorithm.

Binomial random variable (mathematics for randomized analysis)

Define: a binomial random variable counts the number of successes in n independent trials, when each trial succeeds with probability p.

If X counts the number of successes in n independent trials, each with success probability p, then X is a binomial random variable, X ~ B(n,p):

P(X = k) = nCk pk (1−p)n−k,   E[X] = np,   Var(X) = np(1−p)

What this means: nCk counts the ways to choose k successes. pk is the chance of those successes, and (1−p)n−k is the chance of the failures. The average count is np.

For a single trial, the indicator variable I is 1 on success and 0 on failure, with E[I] = p. Linearity of expectation says E[X+Y] = E[X] + E[Y]. It holds even when X and Y are dependent. This is the usual tool for analysing randomized algorithms. In plain words: the average of a sum is the sum of the averages. The book's 4-ball example is exactly a binomial distribution with n = 4 and p = 1/2: its probabilities 1/16, 4/16, 6/16, 4/16, 1/16 are the B(4, 1/2) values.

Step-by-step for the 4-ball example:

  1. Each ball is red or white with probability ½, so p = ½.
  2. There are 4 balls, so n = 4.
  3. For k red balls, use P(X = k) = 4Ck (½)4.
  4. k = 0 gives 1/16, k = 1 gives 4/16, k = 2 gives 6/16, k = 3 gives 4/16, k = 4 gives 1/16.
  5. The five probabilities add to 1, as they must.
Real-life analogy — rolling a die: A deterministic algorithm always takes the same road. A randomized algorithm rolls a die at each junction. Sometimes it reaches the goal faster, sometimes slower. But no traffic jam can block the same road every day, because the route changes.
Common confusion: Randomized is not the same as “random input.” The input is fixed; the algorithm's choices are random. Also, randomized does not mean “always faster.” It means the expected time is good, and the worst case is unlikely. A Las Vegas algorithm is always correct; a Monte Carlo algorithm may be wrong with small probability.

Q2Does the randomized algorithm for quicksort improve the average-case time complexity? Discuss.

4 marks★★ 2×

Asked in: 2025 May Q5(c) [4] · 2025 Nov Q6(b) [4]

In simple words: Quicksort picks a pivot and splits the list into smaller and larger parts. A bad pivot makes the split lopsided and the sort slow: O(n²). Randomized quicksort picks the pivot at random. Bad splits become unlikely. The average case stays O(n log n), but now it does not depend on the input order.
Why we do this: Real data is often already sorted, which is the worst case for fixed-pivot quicksort. Randomizing the pivot protects us from that trap. We keep the same expected speed and remove a predictable weakness.

The words you need first

  • Pivot: the item used to split the list into smaller and larger parts.
  • Partition: the step that rearranges items around the pivot.
  • Uniformly at random: every index has the same chance of being picked.
  • Expected time: the average over all random pivot choices.
  • Adversary: an imagined attacker who chooses a nasty input to trigger the worst case.
  • Average-case time: the average over all possible inputs, usually under some assumption about the input distribution.

The book's randomized quicksort

RANDOMIZED-PARTITION(A, p, r)
1  i = RANDOM(p, r)
2  exchange A[r] <-> A[i]
3  return PARTITION(A, p, r)

RANDOMIZED-QUICKSORT(A, p, r)
1  if p < r
2      q = RANDOMIZED-PARTITION(A, p, r)
3      RANDOMIZED-QUICKSORT(A, p, q - 1)
4      RANDOMIZED-QUICKSORT(A, q + 1, r)

How it works, step-by-step:

  1. Pick a random index i between p and r.
  2. Swap A[i] with the last element A[r].
  3. Run the ordinary PARTITION using A[r] as the pivot.
  4. Recursively sort the left part and the right part.
  5. Stop when the part has zero or one item.

The answer

No — it does not improve the average-case complexity, which remains O(n log n). What it improves is the dependence on the input order.

  • Deterministic quicksort with the first or last element as pivot is O(n²) on sorted input. This is also true for reverse-sorted input. Every partition is completely unbalanced.
  • Randomized quicksort chooses the pivot uniformly at random. For any fixed input, the expected running time over the random choices is O(n log n).
  • The O(n²) worst case is still possible, but its probability is very small and no adversary can force it without knowing the random choices.
Expected T(n) = O(n log n)   |   Worst case = O(n²) with small probability

What this means: the average is still n log n. The difference is that the average is now taken over the algorithm's random choices, so it holds for every fixed input, including sorted data.

Why a sorted list kills the fixed pivot

  1. Take the last element as the pivot.
  2. In a sorted list, the last element is the largest.
  3. Partition puts everything on the left and nothing on the right.
  4. The next call has n − 1 items and again picks the largest.
  5. The work becomes n + (n − 1) + … + 1 = n(n + 1)/2, which is O(n²).
n + (n−1) + … + 1 = n(n+1)/2 = O(n²)

What this means: each partition removes only one item. The recursion is a long chain instead of a balanced tree.

Why a random pivot is safe

  1. About half the possible pivots lie between the 25th and 75th percentiles.
  2. Such a pivot splits the list into parts of at most 75% and at least 25%.
  3. A random pivot lands in that middle half with probability ½.
  4. So a good split appears every couple of levels, on average.
  5. That keeps the recursion depth near log n and the total work near n log n.
Real-life analogy — cutting a queue: You must split a line of people into shorter and taller groups. If you always pick the tallest person as the divider, everyone goes to one side and nothing is solved. If you pick a random person, the line usually splits roughly in half. A bad pick is possible, but it is not forced.
Common confusion: “Randomized quicksort is O(n log n) in the worst case” is false. Its worst case is still O(n²); only its expected time is O(n log n). Also, it does not make the average case better than ordinary quicksort. It makes the good average hold for every input, instead of only for random-looking inputs.

5.1 Amortized analysis — the three methods

Q1Explain the methods of amortized analysis with a suitable example.

6–9 marks★★★★★ 5×

Asked in: 2022 Nov Q5(a) [10 — short notes on all three] · 2023 Nov Q5(a) [9 — aggregate] · 2024 May Q6(a) [8] · 2025 May Q6(a) [6] · 2025 Nov Q5(c) [6 — any two]

In simple words: Some operations are cheap almost every time. Once in a while, one operation is very expensive. Amortized analysis finds the fair cost of one operation across a long run. It spreads the rare big cost over the many small ones.
Why we do this: One scary operation can make a good data structure look bad. Amortized analysis shows the real long-run cost. That lets us promise a worst-case total time, not a guess.

The words you need first

  • Operation: one action on the data, such as PUSH or INCREMENT.
  • Data structure: a way to organise data in memory, such as a stack or a counter.
  • Sequence: a run of n operations, one after another.
  • n: the number of operations in that run.
  • Actual cost (ci): the real work done by operation i, counted in steps.
  • Amortized cost (ĉi): the fair share of the total cost that we charge to operation i.
  • O(1): constant time. The work does not grow as n grows.
  • O(n): linear time. If n doubles, the work doubles.
  • Worst-case sequence: the order of operations that makes the total cost as large as possible.

What is amortized analysis?

According to the book, amortized analysis means finding the average running time per operation over a worst-case sequence of operations. The average cost of a single operation is small when we average over the whole sequence. This holds even if one operation in that sequence is expensive. It therefore guarantees the time per operation in the worst case.

In one line: total work divided by the number of operations gives the fair cost per operation.

Amortized cost of n operations = total cost of the n operations / n

What this means: add the real cost of all n operations, then divide by n.

The book gives three commonly used techniques. All three find the same fair cost. They differ only in how they keep the accounts.

1. Aggregate analysis

Define: Aggregate analysis adds up the cost of the whole sequence first. Then it divides by n. We do not track single operations.

Analyse the whole sequence of n operations first. If the sequence takes worst-case time T(n), the amortized cost of each operation is:

T(n) / n

What this means: the total time T(n) is shared equally by all n operations.

Step-by-step:

  1. Write down the n operations you will perform.
  2. Find the total worst-case cost T(n) of the whole sequence.
  3. Divide T(n) by n.
  4. If the result is a constant, each operation is O(1) amortized.
  • Stack with PUSH, POP and MULTIPOP: n operations cost at most 2n, because each object is pushed once and popped once → O(1) per operation.
  • k-bit binary counter: n INCREMENTs flip fewer than 2n bits → O(1) per increment.
  • The book first gives a loose bound. A sequence with O(n) MULTIPOPs can cost O(n²). That bound is correct but not tight. The tight total is O(n).

2. Accounting method

Define: Credit is prepaid work. We charge an operation more than it really costs. The extra amount is saved on a data object. Later, that saved credit pays for a real operation.

Assign a different charge to each operation; this charge is its amortized cost. It may be more or less than the actual cost.

  • If amortized cost > actual cost, the difference is saved on a specific object as credit.
  • If amortized cost < actual cost, the stored credit is used up.
  • The total amortized cost must be an upper bound on the total actual cost. So total credit never becomes negative.
Amortized cost = actual cost + credit (deposited or used up)
Σ c′i ≥ Σ ci    and    total credit = Σ c′i − Σ ci ≥ 0

What this means: the charges we invent must cover all real work. The saved credit is the extra we charged, and it can never go below zero.

Step-by-step:

  1. Choose a charge (amortized cost) for each operation type.
  2. Compare the charge with the real cost.
  3. If the charge is bigger, store the difference as credit on an object.
  4. If the charge is smaller, spend credit that was stored earlier.
  5. Check that total credit never becomes negative.
  6. Add all charges. That sum is an upper bound on the real total.

Stack example: charge PUSH 2, POP 0, MULTIPOP 0. The extra 1 from PUSH stays on the pushed object and pays for its later POP or MULTIPOP. Total for n operations is at most 2n, so the amortized cost per operation is 2.

Binary counter example: charge 2 for setting a bit to 1. Of this, 1 pays the actual set and 1 is credit on that bit; when the bit is reset to 0, the stored credit pays for the reset. Total is O(n).

3. Potential function method

Define: a potential function Φ is a number that stores “saved energy” for the whole data structure. It works like a battery. An operation can charge the battery or drain it.

This is similar to the accounting method. Here the prepaid amount is potential “energy” attached to the whole data structure. It is not attached to individual objects. Let D0, D1, …, Dn be the data structure after each operation, ci the actual cost of operation i, and Φ(Di) its potential (a real number).

c′i = ci + Φ(Di) − Φ(Di−1)
Σ c′i = Σ ci + Φ(Dn) − Φ(D0)

What this means: the fair cost is the real cost plus the change in stored energy. If the operation charges the battery, the fair cost is higher. If it drains the battery, the fair cost is lower.

Choose Φ(D0) = 0 and Φ(Di) ≥ 0. Then the amortized cost is an upper bound on the actual cost. A positive potential change means the operation was overcharged; a negative change means stored potential is discharged to pay for the operation.

Step-by-step:

  1. Pick a potential function Φ for the data structure.
  2. Check Φ is never negative and Φ(empty) = 0.
  3. For each operation, write its actual cost ci.
  4. Find the change ΔΦ = Φ(Di) − Φ(Di−1).
  5. Add them: ĉi = ci + ΔΦ.
  6. If ĉi is a constant, the amortized cost is O(1).
  • Stack: Φ = number of elements. PUSH: ΔΦ = +1 → ĉ = 1 + 1 = 2. POP: ΔΦ = −1 → ĉ = 1 − 1 = 0. MULTIPOP of k′ elements: ΔΦ = −k′ → ĉ = k′ − k′ = 0.
  • Binary counter: Φ = number of 1 bits. If an INCREMENT resets t bits, actual cost = t + 1 and ΔΦ = 1 − t → ĉ = (t + 1) + (1 − t) = 2.

Comparison of the three methods

MethodIdeaBest used when
AggregateAnalyse the entire sequence first; amortized cost = total / nThe total cost of the sequence is easy to bound
AccountingAssign different charges; excess is stored as credit on objectsDifferent operations have very different actual costs
PotentialDefine a potential function Φ and prove it is a valid potentialA rigorous proof is needed; the structure has a natural “energy”
Key line for the examiner: amortized analysis averages over a sequence of operations, not over inputs — so it gives a worst-case guarantee, unlike average-case analysis.
Real-life analogy — the metro card: Most rides cost ₹20. One airport trip costs ₹400. Paying per ride makes that one trip look terrible. A monthly pass spreads the ₹400 over all rides, so the average ride is cheap. Amortized analysis is that monthly pass. It does not make the expensive trip cheap. It shows the fair cost per ride.
Common confusion: Amortized cost is not average-case cost. Average case averages over random inputs. Amortized cost averages over a sequence of operations and still assumes the worst-case input. Also, “amortized O(1)” does not mean every single operation is O(1). One operation can still be expensive.

5.4 Tractable and intractable problems

Q1What are tractable and non-tractable (intractable) problems? Give examples.

6–7 marks★★★★ 4×

Asked in: 2022 Nov Q5(a) [part] · 2025 May Q5(b) [7] · 2025 Nov Q5(b) [6]

In simple words: A tractable problem has a fast algorithm. “Fast” means polynomial time: n, n², n³, and so on. An intractable problem has no known polynomial-time algorithm. Its best exact methods grow exponentially, such as 2n or n!. Small inputs may still be solvable, but large inputs explode.
Why we do this: This split tells us what to expect. For tractable problems, we hunt for a better exact algorithm. For intractable problems, we often stop hunting and use approximation or heuristics. That saves months of wasted effort.

The words you need first

  • Polynomial time: running time bounded by nc for some fixed number c, such as n² or n³.
  • Exponential time: running time such as 2n or n!, which grows far faster than any polynomial as n grows.
  • Upper bound: a promise that the algorithm never takes more than this much time.
  • Lower bound: a proof that no algorithm can do better than this much time.
  • Asymptotic: describes behaviour as n grows very large.
  • Tractable: solvable in polynomial time.
  • P: the class of problems that have a polynomial-time algorithm.
  • NP: the class of problems whose yes answer can be checked quickly.
  • Intractable: no polynomial-time algorithm is known; the book says its lower bound is exponential.
  • NP-hard: a problem at least as hard as the hardest problems in the class NP. No polynomial exact algorithm is known for it.

Tractable problem

The book defines a tractable problem as a problem that can be solved by a polynomial-time algorithm; its upper bound is polynomial.

Examples (book): (i) searching an unordered list, (ii) searching an ordered list, (iii) sorting a list, (iv) multiplication of integers, (v) finding a minimum spanning tree in a graph.

Quick check: if n doubles, a polynomial algorithm slows by a fixed factor. For n², doubling n makes the work 4 times larger. That is manageable.

Intractable (non-tractable) problem

The book defines an intractable problem as a problem that cannot be solved by a polynomial-time algorithm; its lower bound is exponential.

Examples (book): (i) travelling salesman problem, (ii) knapsack problem.

Exam-safe wording: for NP-hard problems, say “no polynomial-time algorithm is known.” Proving that none can exist is the famous open P vs NP question.

How to classify a problem — step-by-step

  1. Write down the best exact algorithm you know for the problem.
  2. Find its growth rate in terms of input size n.
  3. If the growth is log n, n, n log n, n², n³, or any polynomial, call it tractable.
  4. If the best known growth is 2n, n!, or similar, call it intractable.
  5. Check the input size. A small TSP instance can still be solved exactly.
  6. If the problem is intractable, look for an approximation algorithm with a proven ratio.

What this means: the difference is the shape of the growth curve, not the size of the code or the difficulty of the exam question.

Why the difference matters

  • For a tractable problem, polynomial growth keeps the running time manageable as the input size increases.
  • For an intractable problem, the best known exact algorithms grow exponentially; even moderate n can be impossible.
  • Intractability is a worst-case asymptotic statement. Small instances of TSP or knapsack can still be solved exactly.
  • The book uses this distinction to motivate approximation algorithms in §5.5: for an NP-hard optimization problem, find a good solution quickly instead of the exact optimum.
Real-life analogy — the staircase and the wall: A tractable problem is a staircase. Each extra step costs about the same, so you can climb a hundred steps. An intractable problem is a wall that doubles in height with every step. The first few steps are easy. Then the wall becomes impossible, even though the rule is simple.
Common confusion: “Intractable” does not mean “impossible to solve.” It means “no polynomial-time exact algorithm is known.” A 10-city TSP can still be solved by brute force. Also, intractable is not the same as undecidable. Undecidable means no algorithm can ever solve it, even with unlimited time. An intractable problem has an answer; we just cannot find it fast in the worst case.

Q2What are intractable problems? Does the Travelling Salesman Problem belong to this class? Justify.

6 marks★ 1×

Asked in: 2025 Nov Q5(b) [6]

In simple words: The Travelling Salesman Problem (TSP) asks for the shortest tour that visits every city once and returns home. Checking one given tour is easy. Finding the best tour is hard. The decision version is NP-complete, and the optimization version is NP-hard. So yes, TSP is intractable. But we can still find a good tour quickly with approximation.
Why we do this: The examiner wants a chain of reasoning, not just “yes.” We must connect decision version, NP-complete, optimization version, and NP-hard. Then we add the exact costs to prove the problem explodes.

The words you need first

  • Tour: a closed route that visits every city exactly once.
  • Hamiltonian cycle: a cycle that visits every vertex exactly once.
  • Decision problem: a question with a yes/no answer.
  • Optimization problem: a question that asks for the best value, such as the shortest tour.
  • NP: the class of problems whose yes answer can be checked quickly.
  • NP-complete: an NP problem that is at least as hard as every other NP problem.
  • NP-hard: at least as hard as NP-complete problems; no polynomial exact algorithm is known.
  • Reduction: a fast way to turn one problem into another, used to prove hardness.
  • Exhaustive search: try every possible tour and keep the shortest.
  • Held–Karp: a dynamic-programming method that solves TSP exactly.
  • Super-polynomial: grows faster than any fixed power of n, such as 2n.

The book's rule

Yes, TSP is intractable. The book's rule is: if the decision version of a combinatorial optimization problem is proved NP-complete, then its optimization version is NP-hard.

  • Decision TSP: “Is there a tour of length less than K?” We can check a proposed tour in polynomial time. Hamiltonian cycle also reduces to it. So decision TSP is NP-complete.
  • Optimization TSP: “What is the shortest tour?” This is NP-hard. The book's Hamiltonian-cycle example makes the same point. The decision version asks if a cycle shorter than k exists; it is NP-complete. The optimization version asks for the shortest cycle; it is NP-hard. Checking whether a cycle is truly the shortest is hard.

Justify step-by-step

  1. Write the decision version: “Is there a tour shorter than K?”
  2. Show that a yes answer has a short proof. The proposed tour is the proof, and we can check its length quickly.
  3. Show that Hamiltonian cycle reduces to decision TSP. A Hamiltonian cycle is a tour; set K to the number of cities plus one.
  4. Conclude that decision TSP is NP-complete. It is in NP, and an NP-complete problem reduces to it.
  5. Write the optimization version: “What is the shortest tour?”
  6. Suppose we could solve the optimization version fast. Then we could answer the decision version fast: compute the shortest length and compare it with K.
  7. So the optimization version is at least as hard as the decision version. Therefore it is NP-hard.
  8. Conclude that no polynomial-time exact algorithm is known for TSP.

Why exact TSP explodes

Exhaustive search: O(n!)   |   Held–Karp DP: O(n²2n)

What this means: both functions grow faster than any polynomial. For n = 30, n! is already enormous. Held–Karp is better, but 2n still explodes.

No polynomial-time exact algorithm is known. Exhaustive search is O(n!), and the standard dynamic-programming solution (Held–Karp) is O(n²2n); both are super-polynomial.

But TSP is approximable

But TSP is approximable. For Euclidean (metric) TSP, the book gives the twice-around-the-tree algorithm, a 2-approximation: compute an MST, walk around it by DFS, and remove duplicate visits. So exact TSP is intractable, but a near-optimal tour can be found in polynomial time.

Approximate tour length ≤ 2 × optimal tour length

What this means: the tour we build is never more than twice as long as the true best tour. That is a proven guarantee, not a hope.

Real-life analogy — checking vs solving a puzzle: A teacher can check your solved maze in seconds by following the path. Solving the maze from scratch is much harder. TSP is the same. Checking a tour is easy; finding the best tour is hard. Approximation is like accepting a path that is a little longer, as long as it gets you out quickly.
Common confusion: “NP-hard” does not mean “no algorithm exists.” It means “no polynomial-time exact algorithm is known.” Also, the 2-approximation needs the triangle inequality (Euclidean distances). For general TSP with arbitrary distances, this guarantee does not hold. Finally, decision TSP and optimization TSP are different questions.

  1. Start at the first item.
  2. Compare the item with the target.
  3. If it matches, stop and return its position.
  4. If not, move to the next item.

Each step halves the list: n → n/2 → n/4 → … → 1
Number of steps = log2 n  →  O(log n)

What this means: doubling the list adds only one extra comparison. A list of 1,000 items needs about 10 checks.

5.6 Approximation algorithms ★★★★ 4×

Q1What are approximation algorithms? Based on the approximation ratio, classify them. How are performance ratios useful?

7–9 marks★★★★ 4×

Asked in: 2022 Nov Q5(b) [8] · 2023 Nov Q6(b) [4] · 2024 May Q5(b) [9] · 2025 May Q6(b) [7]

In simple words: Some problems are too hard to solve exactly in reasonable time. An approximation algorithm gives a “good enough” answer quickly. It also proves how far the answer can be from the best one. For example, a 2-approximation is never more than twice the optimum. We trade a little accuracy for a lot of speed.
Why we do this: A business cannot wait years for the perfect delivery route. It needs a good route today. Approximation algorithms give an answer with a proven quality bound. That is safer than a quick guess with no guarantee.

The words you need first

  • Decision problem: a question with a yes/no answer.
  • Search problem: a question that asks for a structure, such as a tour or a subset.
  • Optimization problem: a question that asks for the best value, such as the shortest route.
  • NP-complete: a decision problem in NP that is at least as hard as every other NP problem.
  • NP-hard: at least as hard as NP-complete; no polynomial exact algorithm is known.
  • Approximation algorithm: a fast algorithm that returns a near-optimal answer with a proven bound.
  • Heuristic: a common-sense rule that often works, but has no guaranteed bound.
  • Approximation ratio: the cost of the approximate answer divided by the cost of the best answer.
  • Performance ratio: the worst-case approximation ratio over all inputs.
  • c-approximation: an algorithm whose answer is always within a factor c of the optimum.
  • Objective value f(s): the number we minimise or maximise, such as tour length or profit.
  • DFS: depth-first search, a walk that goes as deep as possible before backing up.

NP-hard problems — the book's starting point

In complexity theory, some problems are decision problems (answer yes/no), some are search problems, and many are optimization problems. The book defines: if the decision version of a combinatorial optimization problem is proved NP-complete, then its optimization version is NP-hard.

Example (book): the Hamiltonian-cycle decision problem asks if a cycle shorter than k exists. It is NP-complete, because we can verify a cycle in polynomial time. The optimization version asks for the shortest Hamiltonian cycle. It is NP-hard, because checking whether the cycle obtained is the shortest is hard.

What is an approximation algorithm?

The book defines approximation algorithms as algorithms used to find approximate solutions to optimization problems. They are usually associated with NP-hard problems because an efficient polynomial-time exact algorithm is very difficult to obtain.

  • They are mainly useful when an exact polynomial algorithm is known but is too expensive for the size of the data set.
  • The philosophy is: find a “good” solution fast. You will not get the exact optimum, but you will get an approximate solution quickly.
  • They are useful when a near-optimal answer is good enough for the application, and an exact answer would cost too much.
  • They are based on heuristics — a collection of common-sense rules defined from experience (trial and error).

Book examples of heuristics: in TSP, go to the next nearest city; in knapsack, start with the item of highest value and minimum weight.

Accuracy ratio

Define: an instance is one concrete input, such as one map of cities. The accuracy ratio compares our answer on that instance with the true best answer.

For an approximate solution sa with objective value f(sa) and an optimal solution s* with value f(s*):

r(sa) = f(sa) / f(s*)    and generally   r(sa) ≥ 1

What this means: divide our cost by the best cost. A ratio of 1.16 means our answer is 16% worse. A ratio of 1 means we found the optimum.

When r(sa) is close to 1, the approximate solution is better. For a maximization problem the ratio is written the other way round so that it is still ≥ 1.

Maximization: r(sa) = f(s*) / f(sa)

What this means: for profit problems, we put the best value on top. The ratio stays at least 1, so “closer to 1” always means “better.”

Performance ratio and classification by ratio

The performance ratio RA is the best upper bound on the accuracy ratio taken over all instances of the problem. It is used to judge the quality of an approximation algorithm; a value nearer 1 is better.

If there exists a value c ≥ 1 such that r(sa) ≤ c for all instances, the algorithm is called a c-approximation algorithm. This is the book's classification:

Value of cClassMeaning / book example
c = 1OptimalExact algorithm; ratio 1 is the best possible
c > 1, constantc-approximationGuaranteed f(sa) ≤ c·f(s*); smaller c is better

What this means: the worst answer we can return is at most c times the best possible cost. For c = 2, we may pay twice as much, but never more.

Why performance ratios are useful

  • They give a provable worst-case quality guarantee, unlike a heuristic with no bound.
  • They let us compare two approximation algorithms independently of the input instance: the smaller RA or c, the better.
  • They show how much accuracy is traded for speed: c = 1 means exact, c = 2 means at most twice the optimum.
  • They help decide whether the approximate algorithm is good enough or an exact (possibly exponential) algorithm is required.
In one line: a ratio turns “trust me, it is close” into “it is at most twice the best, and here is the proof.”

Book example — nearest-neighbour TSP and its ratio

Graph: A–B = 2, B–C = 3, C–D = 2, D–A = 7, A–C = 4, B–D = 4. Start at A; the nearest unvisited city gives the tour A–B–C–D–A, with sa = 2 + 3 + 2 + 7 = 14. Exhaustive search gives the optimal A–B–D–C–A, with s* = 2 + 4 + 2 + 4 = 12. Hence

r(sa) = 14 / 12 = 1.16

What this means: the greedy tour is 16% longer than the best tour. That is close, but the algorithm has no fixed upper bound in general.

Step-by-step:

  1. Start at city A.
  2. From A, the nearest unvisited city is B, with distance 2.
  3. From B, the nearest unvisited city is C, with distance 3. B–D is 4, so C wins.
  4. From C, the only unvisited city is D, with distance 2.
  5. Return from D to A, with distance 7.
  6. Add: 2 + 3 + 2 + 7 = 14. This is our approximate tour.
  7. Try the best tour by inspection: A–B–D–C–A = 2 + 4 + 2 + 4 = 12.
  8. Divide: 14 / 12 = 1.16, so the greedy answer is 16% longer.

The approximate tour is 16% longer than the optimum. Its drawback is the long return edge D–A: if that edge has length w, then r(sa) = (7 + w)/12, which tends to infinity as w grows.

If D–A = w:   r(sa) = (7 + w) / 12  →  ∞ as w → ∞

What this means: one bad last edge can ruin the ratio. That is why nearest-neighbour has no finite performance guarantee.

Book example — twice-around-the-tree TSP

Define: Euclidean distances are straight-line distances on a map. They satisfy the triangle inequality: going through a third city never shortens the trip.

For Euclidean instances, distances satisfy the triangle inequality: dist[i,j] ≤ dist[i,k] + dist[k,j]. They are also symmetric: dist[i,j] = dist[j,i]. The book's algorithm is:

  1. Compute a minimum spanning tree (MST) of the graph.
  2. Start at any city and walk around the tree by DFS, recording the nodes visited.
  3. Eliminate duplicate visits from the recorded list; the remaining order is a Hamiltonian circuit.

What this means: an MST connects all cities with the cheapest total wiring. Walking around it visits every edge twice. Short-cutting repeated cities gives a tour that costs no more than twice the MST.

This is a 2-approximation (c = 2) for TSP with Euclidean distances. The book also gives the accuracy-ratio bound

r(sa) ≤ ½ (⌈log2 n⌉ + 1)

where n is the number of cities.

What this means: the guarantee depends on the number of cities. It grows slowly, because it contains log2 n. The 2-approximation bound is the simpler guarantee to quote.

In the book's example the MST is A–B (3), B–C (5), B–D (8), D–E (7); DFS records A–B–C–B–D–E–D–B–A; removing duplicates gives A–B–C–D–E–A. This is a valid tour but not necessarily the optimal one.

Step-by-step for the example:

  1. Build the MST: A–B, B–C, B–D, D–E.
  2. Start at A and walk around the tree: A–B–C–B–D–E–D–B–A.
  3. Remove repeated cities, keeping the first visit: A–B–C–D–E–A.
  4. This is a valid tour. Its length may be above the optimum, but it is within the proven bound.
Real-life analogy — the “good enough” taxi: You want the shortest route home. Finding the true shortest route may take forever. A good app gives a route that is at most 20% longer, and it proves that bound. You accept 20% extra fuel to reach home today. That is an approximation algorithm.
Common confusion: A ratio of 1.16 means 16% worse, not 16% better. Smaller ratios are better, and a ratio is never below 1. “2-approximation” means “at most twice the optimum,” not “exactly twice.” Also, a heuristic with no proven bound is not an approximation algorithm in the strict sense. Finally, the 2-approximation for TSP needs Euclidean distances.

5.2 Stack: PUSH, POP, MULTIPOP ★★★ 3×

Q1Explain amortized analysis using a stack with PUSH, POP and MULTIPOP. Find the amortized cost of each operation using all three methods.

9 marks★★★ 3×

Asked in: 2022 Nov Q6(a) [9] · 2023 Nov Q5(b) [9] · 2025 Nov Q6(a) [9]

In simple words: A stack is a pile of plates. PUSH adds a plate on top. POP removes the top plate. MULTIPOP removes many plates in one call. One MULTIPOP can look expensive, but each plate leaves the pile only once. So the total work for n operations is still linear.
Why we do this: One MULTIPOP call can cost O(n). If we multiply that by n operations, we get a loose O(n²) and reject a good design. The expensive call is paid for by the cheap PUSHes before it. Amortized analysis proves the true total is O(n).

The words you need first

  • Stack: a list where we add and remove only at one end, called the top.
  • Array: a row of memory cells, each reached by a position number.
  • LIFO: “last in, first out.” The last item pushed is the first item popped.
  • PUSH(S, x): put item x on top of stack S.
  • POP(S): remove and return the top item.
  • MULTIPOP(S, k): remove up to k items from the top in one call.
  • Credit: prepaid work saved on an item, used later to pay for its removal.
  • O(n²): quadratic time. If n doubles, the work becomes four times larger.

Operations and actual costs

The book implements the stack as an array: PUSH does s[top] = item; top++; and POP does top--; item = s[top];. Both run in O(1). MULTIPOP is:

Algorithm multiple_pop(st, k)
while ((!stempty(st)) AND (k != 0))
{
    pop(st);
    k = k - 1;
}

It removes at most k elements. For a stack of size 8, removing 4 elements costs 4 pops.

OperationActionActual cost
PUSH(S, x)push x onto stack S1
POP(S)remove and return top element1
MULTIPOP(S, k)pop min(k, |S|) elementsmin(k, |S|)

What this means: PUSH and POP do one unit of work. MULTIPOP does one unit per item it removes, so its cost can be large.

MULTIPOP looks expensive: if the stack has n elements, one call can cost O(n). The book says a sequence of n operations can contain O(n) such calls. In the loose worst case, that costs O(n²). That bound is correct but not tight. The tight bound follows because each object can be popped only once: total pops = total pushes.

Method 1 — Aggregate analysis

Step-by-step:

  1. Start with an empty stack.
  2. Perform n operations in total.
  3. Each element is pushed at most once, so there are at most n pushes.
  4. Each pushed element can be popped at most once, so there are at most n pops.
  5. Add both: total cost ≤ n + n = 2n.
  6. Divide by n: amortized cost per operation ≤ 2.
Total cost of n operations ≤ (number of pushes) + (number of pops) ≤ n + n = 2n
Amortized cost per operation = 2n / n = 2 = O(1)

What this means: even if one MULTIPOP removes n items, those items were already paid for by n PUSHes. The whole run of n operations does at most 2n units of work.

Method 2 — Accounting method

Assign: PUSH = 2, POP = 0, MULTIPOP = 0.

Step-by-step:

  1. Charge 2 for every PUSH.
  2. Use 1 to pay for the actual push.
  3. Save the other 1 as credit on the pushed item.
  4. Charge 0 for POP. The pop spends the item's saved credit.
  5. Charge 0 for MULTIPOP. Each removed item spends its own saved credit.
  6. Check the credit never goes negative. Every removed item was pushed first, so it always has its coin.
Total amortized cost for n operations ≤ 2n  →  amortized cost per operation = 2 = O(1)

What this means: we overcharge each PUSH by 1. That extra coin waits on the item and pays for its future removal.

Method 3 — Potential function method

Let Φ(S) = |S|, the number of objects in the stack. Φ(D0) = 0 and Φ(Di) ≥ 0. For MULTIPOP, let k′ = min(|S|, k).

Step-by-step:

  1. Define the potential as the number of items in the stack.
  2. Check the empty stack has potential 0, and potential is never negative.
  3. PUSH: actual cost 1, potential rises by 1, so ĉ = 1 + 1 = 2.
  4. POP: actual cost 1, potential falls by 1, so ĉ = 1 − 1 = 0.
  5. MULTIPOP(k): actual cost k′, potential falls by k′, so ĉ = k′ − k′ = 0.
  6. All three results are constants, so each operation is O(1) amortized.
OperationActual ciΔΦAmortized ĉi = ci + ΔΦ

What this means: PUSH stores one unit of “energy” in the stack. POP and MULTIPOP release that energy, so their fair cost is zero.

The book's MULTIPOP line prints the potential change as k′; because k′ objects leave the stack, the change is actually −k′, which gives the stated amortized cost 0.

All three operations have amortized cost O(1).
Total for n operations = O(n), even though one MULTIPOP can cost O(n).

What this means: the scary single call is rare and is paid for by many cheap pushes. The long-run total is linear.

Common mistake: saying “MULTIPOP is O(n), so the sequence is O(n²)”. That is the worst-case per operation, not the amortized bound. The total is O(n) because each element is popped once.
Real-life analogy — a ₹1 coin on every plate: PUSH costs ₹2. You spend ₹1 to place the plate and glue ₹1 to it. POP and MULTIPOP cost ₹0, because each plate pays with its own coin when it leaves. No plate can leave twice, so the coins never run out.
Common confusion: “Amortized cost 2” does not mean every operation takes 2 steps. PUSH really takes 1, POP takes 1, and MULTIPOP can take n. It means the average over the sequence is at most 2. Also, this is not probability: we assume the worst-case sequence, not random operations.

5.7 Embedded algorithms & power-optimized scheduling ★★★ 3×

Q1What is an embedded algorithm? Explain embedded system scheduling using a power-optimized scheduling algorithm.

9 marks★★★ 3×

Asked in: 2022 Nov Q6(b) [9] · related: 2023 Nov Q6(a) [6] · 2024 May Q6(b) [9]

In simple words: An embedded system is a small computer hidden inside a machine, such as a washing machine or a pacemaker. It must finish tasks on time and use very little power. A scheduler decides which task runs next. A power-optimized scheduler also lowers voltage and speed when there is spare time. This saves battery without missing deadlines.
Why we do this: A late task can be dangerous in a car brake or a medical device. A fast task that drains the battery is also useless. Power-aware scheduling balances both goals: meet every deadline and spend as little energy as possible.

The words you need first

  • Embedded system: a computer with a dedicated function inside a larger machine.
  • Embedded algorithm: an algorithm written for such a system, with tight limits on memory, power, and time.
  • Scheduling: deciding which task runs at which time.
  • Task: one job the system must finish, such as reading a sensor.
  • Deadline: the latest time by which a task must finish.
  • Time-bounded: must finish within a fixed time.
  • Priority: a rank that decides which ready task runs first.
  • Sleep queue: the list of tasks waiting for their next turn.
  • Ready queue: the list of tasks that can run now.
  • Mutual exclusion: only one task may use a shared resource at a time.
  • Synchronization: making tasks wait so shared data stays consistent.
  • Thread/process: one running program, or one part of it.
  • CMOS: the chip technology used in most digital circuits today.
  • Fixed priority: priorities are set at design time and never change.
  • Dynamic priority: priorities are computed at run time.
  • DVFS: dynamic voltage and frequency scaling. It lowers supply voltage and clock speed to save power.
  • Voltage (V): the electrical pressure that pushes current through a chip.
  • Frequency (f): the clock speed, measured in cycles per second.
  • Power: energy used per second. Energy: total power over time.
  • Microcontroller: a small processor on a single chip.
  • Slack: spare time left before a deadline.
  • Utilization: the fraction of CPU time that all tasks demand.
  • EDF: earliest deadline first, a rule that always runs the task with the nearest deadline.

Embedded system and embedded algorithm

The book defines an embedded system as “a computer system with a dedicated function within a larger mechanical or electrical system.” It usually does not look like a computer: there is often no keyboard, monitor or mouse, but it has a processor, memory and software. It is a permanent part of a bigger system. Examples: smart card, washing machine, microwave oven, answering machine, mobile phone, digital camera, vending machine.

An embedded algorithm is therefore an algorithm written for such a dedicated system. It must respect the system's constraints: limited memory, low power, real-time deadlines, small code size and predictable timing.

In one line: an embedded algorithm must be correct, on time, small, and cheap in power. Speed alone is not enough.

Characteristics of embedded systems (book)

  1. Single functional: designed to perform dedicated functions.
  2. Tightly constrained: tightly coupled hardware and software integration.
  3. Part of a large system: an integral part of a bigger system.
  4. Reactive and real-time: responds to events and triggers; generally time-bounded; modern systems have a user-friendly interface.
  5. Programmable: contains at least one programmable unit (microcontroller).

Embedded system scheduling (book §5.6.1)

The book defines scheduling as the method by which threads and processes access system resources at a specific time. It balances the load and shares resources effectively. In a real-time embedded system the scheduler must ensure that processes meet their deadlines. Priorities are assigned to tasks, and the OS always runs the ready task with the highest priority. Algorithms are classified as fixed priority, dynamic priority, or mixed/hybrid priority.

Fixed-priority scheduling

  • All priorities are assigned at design time and remain constant for the lifetime of the task.
  • Initially tasks reside in the sleep queue. When ready, they enter the ready queue. The system keeps one ready queue for each distinct priority.
  • The highest-priority ready task is executed first.
  • Advantage: simple to execute.

What this means: the rule is fixed before the system starts. The scheduler does not rethink priorities while it runs.

Dynamic-priority scheduling

  • All scheduling decisions, including assignment of priorities, are made at run time.
  • Task deadlines are taken into consideration when deciding priorities; mutual exclusion and synchronization are enforced.
  • Tasks start in the sleep queue and move to the ready queues. The scheduler checks the deadlines in the highest-priority queue. Then it runs that task.
  • Advantage: flexible; it adapts when tasks actually need resources.

What this means: a task that is close to its deadline can jump ahead. The scheduler reacts to the current situation instead of a fixed plan.

Power-optimized scheduling

A power-optimized scheduler is a deadline-aware dynamic-priority scheduler with voltage/frequency scaling. It uses the book's dynamic-priority idea: priorities are decided at run time from deadlines. It adds a power rule: run each task at the lowest voltage and frequency that still finishes it before its deadline.

Step-by-step:

  1. Assign each task a priority from its deadline at run time (earlier deadline = higher priority).
  2. Compute the required execution cycles Ci and the time left until the deadline.
  3. Choose the lowest frequency fi such that Ci/fi ≤ deadlinei − current time.
  4. Run at that frequency; if a task finishes early, use the slack to lower the frequency of later tasks.
  5. If the total utilization Σ Ci/Ti ≤ 1, earliest-deadline-first (EDF) meets all deadlines.
Required condition:   Ci / fi ≤ deadlinei − current time

What this means: divide the work by the speed to get the run time. That run time must fit in the time left before the deadline.

CPU utilization:   Σ Ci / Ti ≤ 1

What this means: Ci is the work per task and Ti is its period. The sum is the fraction of the CPU that all tasks need. If it is at most 1, the CPU is not oversubscribed.

The power saving comes from the CMOS dynamic-power relation

Pdynamic = α · C · V² · f

where V is supply voltage and f is clock frequency. α is the activity factor (how often the circuit switches), and C is capacitance.

What this means: power grows with the square of voltage and linearly with frequency. Lower either one, and power drops.

Since a lower frequency allows a lower voltage, power falls roughly as the cube of the frequency. Example: a task needs 300 ms of work and has a 500 ms deadline; running at 60% frequency still meets the deadline, and dynamic power falls to about 0.6³ ≈ 22% of the maximum.

Step-by-step for the 300 ms example:

  1. At full speed, the task needs 300 ms of work.
  2. The deadline is 500 ms away, so the task can take longer.
  3. The slowest safe speed is 300 / 500 = 0.6, or 60% of full frequency.
  4. At 60% frequency, the run time is 300 / 0.6 = 500 ms. It just meets the deadline.
  5. Lower the voltage along with the frequency.
  6. Power falls roughly as f³, so the book estimates 0.6³ ≈ 0.216, about 22% of the maximum.
  7. Keep a small safety margin for overhead, because 500 ms leaves no slack.
0.6³ = 0.216 ≈ 22%

What this means: a 40% cut in speed can cut dynamic power to about one fifth. The task runs longer, so the deadline check must come first.

Trade-off: lowering frequency increases execution time. Too aggressive scaling misses deadlines; too conservative scaling wastes energy. The scheduler must keep enough slack.

The book's §5.6.1 gives the fixed/dynamic priority scheduling framework; the voltage/frequency layer above is the standard power-optimized extension of the same deadline-driven rule.

Real-life analogy — the smart kitchen: One cook has several dishes with serving times. If a dish is due soon, the cook turns up the flame. If there is plenty of time, the cook uses a low flame to save gas. The cook never serves late, and never burns gas for no reason. That is power-optimized scheduling.
Common confusion: Power-optimized scheduling is not just “run everything slowly.” A slow task may miss its deadline. It is also not just fixed-priority scheduling: the priority and the speed both change at run time. Finally, lower frequency saves power, but the task runs longer, so always check the total time and the deadline.

5.3 Binary counter ★★ 2×

Q1Prove that the amortized cost per operation of a k-bit binary counter is O(1), using the aggregate method.

5–6 marks★★ 2×

Asked in: 2025 May Q5(a) [6] · 2025 Nov Q5(a) [5]

In simple words: A binary counter counts in bits: 000, 001, 010, 011, and so on. Adding 1 sometimes flips many bits at once. For example, 0111 becomes 1000 and flips four bits. But most increments flip only one bit. Over n increments, the total flips are less than 2n, so the fair cost per increment is constant.
Why we do this: If we look only at the worst single increment, we get O(k) and think the counter is slow. The expensive flips happen rarely. Amortized analysis proves the counter is O(1) per increment on average.

The words you need first

  • Bit: a digit that is either 0 or 1.
  • k-bit counter: a counter stored in k bits, from B[0] to B[k−1].
  • LSB: least significant bit, the rightmost bit B[0]. It changes most often.
  • Flip: change a bit from 0 to 1, or from 1 to 0.
  • INCREMENT: add 1 to the counter.
  • Geometric series: a sum where each term is half the one before, such as 1 + ½ + ¼ + … = 2.

Setup

A k-bit binary counter is stored in an array B[0..k−1], with B[0] the least significant bit. INCREMENT flips a suffix of 1-bits to 0 and the next 0-bit to 1. A suffix is a block of bits at the right end. The book's algorithm is:

Algorithm Increment(B[0..k-1])
i = 0
while ((i < length(B)) AND (B[i] = 1))
{
    B[i] = 0
    i = i + 1
}
if (i < length(B)) then
    B[i] = 1

The book's 8-bit example starts at 00000000. The costs of successive increments are 1, 2, 1, 3, 1, 2, 1, 4, 1, 2, 1, 3, 1, 2, 1, 5, giving a cumulative cost of 31 flips for 16 increments (Fig. 5.1.1).

31 flips / 16 increments ≈ 1.94 flips per increment

What this means: the pattern repeats in powers of two. One increment costs 5 flips, but the average stays below 2.

Aggregate analysis

In n consecutive INCREMENT operations, count how often each bit flips:

Bit positionFlips everyNumber of flips in n increments

………
B[i]2i⌊n/2i⌋

What this means: the last bit flips on every step, the next bit every second step, the next every fourth step, and so on. Higher bits flip very rarely.

Step-by-step:

  1. Count flips of B[0]: it flips on every increment, so n flips.
  2. Count flips of B[1]: it flips every 2 increments, so about n/2 flips.
  3. Count flips of B[i]: it flips every 2i increments, so about n/2i flips.
  4. Add all bit positions from i = 0 to k − 1.
  5. Replace the finite sum by the infinite geometric series. This only makes it bigger, so the bound stays safe.
  6. Use 1 + ½ + ¼ + … = 2 to get T(n) < 2n.
  7. Divide by n: amortized cost per increment < 2, which is O(1).
T(n) = Σi=0k−1 ⌊n/2i⌋ < n · Σi=0∞ (1/2)i = 2n
Worst case for the sequence = O(n)
Amortized cost per INCREMENT = O(n)/n = O(1)

What this means: the total flips for n increments is below 2n. So each increment gets a fair share below 2, even though one increment can flip k bits.

Potential method (alternative, for full marks)

Define: the potential function here is the number of 1-bits in the counter. It measures stored “energy” that the next increment may have to clear.

Let Φ(Di) = bi, the number of 1-bits after the i-th increment. Suppose the i-th operation resets ti bits. Its actual cost is:

ci = ti + 1

What this means: the increment clears ti ones and sets one new bit, so it does ti + 1 flips.

If bi = 0, the operation resets all k bits, so bi−1 = ti = k. Otherwise bi = bi−1 − ti + 1. Hence bi ≤ bi−1 − ti + 1, and the potential change is:

Φ(Di) − Φ(Di−1) = 1 − ti
ĉi = ci + ΔΦ = (ti + 1) + (1 − ti) = 2

What this means: clearing t ones releases t units of energy, and setting one new bit stores 1 unit. The two effects cancel, leaving a fair cost of 2.

Step-by-step:

  1. Define Φ as the number of 1-bits.
  2. Check Φ is never negative and the all-zero counter has Φ = 0.
  3. Let ti be the number of 1-bits that the increment resets.
  4. Write the actual cost: ci = ti + 1.
  5. Write the potential change: ΔΦ = 1 − ti.
  6. Add: ĉi = (ti + 1) + (1 − ti) = 2.
  7. Since Φ ≥ 0 and Φ(D0) = 0, total amortized cost is an upper bound on total actual cost.

Since Φ ≥ 0 and Φ(D0) = 0, total amortized cost is an upper bound on total actual cost, so each operation is O(1) amortized.

Worst case vs amortized: a single INCREMENT can flip all k bits → O(k). But n increments cost O(n), so the amortized cost is O(1).
Real-life analogy — the car odometer: The last digit rolls on every kilometre. The tens digit rolls every 10 km. The hundreds digit rolls every 100 km. The higher digits move very rarely. If you watch one roll-over, it looks busy. Over a long drive, each kilometre costs about one digit turn.
Common confusion: “One increment is O(k), so n increments are O(nk)” is wrong as a tight bound. The expensive all-ones case happens once every 2k increments. Also, n is the number of increments, not the number of bits. The O(1) result is per increment over a long sequence.

5.8 Sorting algorithm for embedded systems

Q1Which sorting algorithm is best for embedded systems? Why? / Suggest a suitable sorting algorithm for a real-time medical device and justify.

6–9 marks★★ 2×

Asked in: 2023 Nov Q6(a) [6] · 2024 May Q6(b) [9 — medical device scenario]

In simple words: Embedded systems have little memory, little power, and strict deadlines. Recursion and extra arrays are costly there. Insertion sort is a good fit: it sorts in place, needs no recursion, uses tiny code, and is fast on nearly sorted data. For large buffers, heap sort gives a safer O(n log n) worst case.
Why we do this: On a desktop, a fast sort with extra memory is fine. On a medical sensor, extra memory and unpredictable recursion can cause a late reading. We choose the sort that respects the device's limits, not the one with the best big-O on paper.

The words you need first

  • In-place: uses only O(1) extra memory; it rearranges the input array itself.
  • Recursive: a function that calls itself, which uses a call stack.
  • Stable: equal items keep their original relative order.
  • Adaptive: runs faster when the input is already nearly sorted.
  • Code size: the amount of program memory (ROM) the algorithm needs.
  • Buffer: a small block of memory that holds data before processing.
  • Auxiliary array: an extra temporary array used during sorting.
  • Real-time: the system must produce its result before a fixed deadline.
  • Sorted zone: the part of the array that is already in order.
  • ROM: read-only memory that stores the program permanently.
  • Call stack: the memory used to track recursive function calls.

What the book requires from an embedded sorting algorithm

  1. The sorting algorithm must be in place.
  2. The algorithm must not be recursive.
  3. The code size must be as per the need of the problem.
  4. The running time should increase linearly or logarithmically with the number of elements sorted.

The book defines an in-place algorithm as one that needs very little extra space beyond the initial array. The input is overwritten by the output. No second array is required. It lists bubble sort, insertion sort and heap sort as methods that can be used in embedded systems, and discusses insertion sort in detail.

Reality check: embedded buffers are usually small. For 20 readings, a quadratic sort finishes in microseconds, so its simple code is often the better engineering choice.

Insertion sort (book §5.6.2)

Insertion sort maintains a sorted zone. Each new unsorted element is compared with the elements in the sorted zone and inserted at its proper position. The process continues until the whole list is sorted.

Book example: 30 70 20 50 40 10 60 → the sorted zone grows as 30 | 30 70 | 20 30 70 | 20 30 50 70 | 20 30 40 50 70 | 10 20 30 40 50 70 | 10 20 30 40 50 60 70.

Step-by-step:

  1. Start with the first element. A single element is already sorted.
  2. Take the next element and store it in temp.
  3. Compare temp with the element on its left.
  4. If the left element is bigger, shift it one place right.
  5. Keep moving left until you find a smaller element, or reach the start.
  6. Put temp in the empty slot. The sorted zone is now one item bigger.
  7. Repeat until every element is in the sorted zone.
Algorithm Insert_sort(A[0..n-1])
for i = 1 to n-1 do
{
    temp = A[i]
    j = i - 1
    while (j >= 0) AND (A[j] > temp) do
    {
        A[j+1] = A[j]
        j = j - 1
    }
    A[j+1] = temp
}

The book notes that although insertion sort is naturally recursive (top-down), the bottom-up iterative version above is very efficient to implement.

What this means: the inner loop shifts bigger items right. The final A[j+1] = temp drops the new item into the gap. No extra array is needed.

What this means: a nearly sorted list is cheap. A reversed list is expensive, because every new item travels to the front.

The basic operation is the key comparison A[j] > temp; the book analyses it over the range 1 to n − 1.

Which is best for embedded systems?

Insertion sort is the natural choice for the small buffers typical of embedded systems. It is the algorithm the book develops for this purpose. Reasons:

  • In place — only O(1) extra memory, no auxiliary array.
  • Non-recursive when written as the bottom-up loop above — no recursion stack.
  • Small code size — simple loops, suitable for limited ROM.
  • Adaptive — Θ(n) on nearly sorted data, which is common for sensor streams.
  • Stable — equal readings keep their original order (useful for timestamps).

For large buffers with a hard real-time deadline, heap sort is safer. The book lists it as an embedded sorting method. It gives O(n log n) worst-case time with O(1) extra memory and no recursion. Merge sort is unsuitable because it needs O(n) extra memory. Ordinary recursive quicksort is unsuitable because of its O(n²) worst case and recursion stack.

Medical-device scenario (2024 May): the device samples timestamps, temperature, heart rate and blood pressure continuously, and the buffer is small and often nearly sorted. Insertion sort is ideal: in-place, stable, Θ(n) on nearly sorted data and very small code. If the buffer becomes large, switch to heap sort to keep an O(n log n) worst-case guarantee.

Real-life analogy — sorting playing cards in your hand: You hold the sorted cards in your left hand. You pick one new card and slide it into the correct gap. You do not need a second table, and you do not repeat the whole process recursively. That is insertion sort: small, in-place, and fast when the cards are almost in order.
Common confusion: “Insertion sort is O(n²), so it is always bad” is false. For 20 sensor readings, n² is tiny, and the small code and low memory matter more. “Best” depends on buffer size and deadlines. Also, heap sort is not stable, so keep a sequence number if equal readings must stay in order.
